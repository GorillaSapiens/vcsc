VCSC PROJECT CONTEXT
====================

Purpose and reading order
-------------------------
This is the compact durable handoff for continuing VCSC after a chat restart.
It records only current state, durable invariants, active problems, and the next
work. It is not a chronological diary.

When asked to read `.../context.txt` and continue in a **new chat**:

1. Read this file once near the start of the chat. This is bootstrap state, not a
   per-turn checklist. Do not reread the whole file on later turns unless it has
   materially changed and the current task genuinely requires the new contents.
   For later verification, prefer a targeted search, section, line range, or tail.
   Reinjecting the same handoff text every turn wastes the conversational context
   this file is intended to save.
2. Inspect the current tree and verify that it agrees with this record.
3. Follow the user's newest instruction. Otherwise continue the first item under
   "Immediate TODO."
4. Read focused internal documents only when relevant:

       .../roadmap.txt                 detailed main-project roadmap
       .../bankswitching.txt           bankswitching design and sub-roadmap
       .../enhanced.txt                enhanced multisprite side-quest handoff
       .../enhanced_asymmetric.txt     asymmetric-PF enhanced WIP handoff
       .../ram_optimization.txt         focused RIOT-RAM optimization roadmap
       .../instruction.txt             bounded-work and packaging procedure
       .../context-history/YYYY-MM-DD.txt
                                       historical daily development log

5. Do not read all of `context-history/` during an ordinary handoff. Search or
   open only the day needed to investigate an old decision or regression.

Keeping this file small
-----------------------
The point of this file is to reduce conversational context, not consume it.
Keep it below 50 KiB when practical and never allow it to exceed 100 KiB.

* Keep only facts needed to continue present or likely near-term work.
* Update existing current-state text instead of appending another version of it.
* Move completed-work narratives into the appropriate daily file under
  `.../context-history/`; use one file per local calendar date.
* Keep detailed acceptance criteria in `.../roadmap.txt` or the relevant focused
  design document. Point to that document instead of duplicating it here.
* Do not paste full compiler output, test logs, file inventories, or long lists
  of touched paths. Record the command, concise result totals, and only relevant
  failures or caveats.
* Remove superseded plans and stale measurements once a newer authoritative
  value exists. History already preserves the old version.
* When this file begins growing through repeated additions, stop and consolidate
  it immediately rather than postponing cleanup.

History-entry policy
--------------------
Every meaningful completed change or decision gets an entry in that day's file:

    .../context-history/YYYY-MM-DD.txt

Create the file when the first entry is written that day. Entries are oldest
first. Each entry may contain any number of continuation/detail lines, but its first
line is a strictly formatted ASCII header:

    YYYY-MM-DD HH:MM:SS PDT, short description

The description is mandatory and at most 50 characters. The complete header line is
at most 72 characters and contains ASCII only. Continuation/detail lines are not
subject to those length or ASCII restrictions. Do not leave a timestamp-only header
and do not use roadmap-item/task numbers as the entry-title shorthand.

Generate the timestamp with:

    TZ=America/Vancouver date "+%Y-%m-%d %H:%M:%S %Z"

During the project's current summer work this must produce `PDT`; the history-format
regression deliberately requires `PDT` in entry headers.

Never put a growing changelog back into this file. Update the current-state
sections here and append the historical narrative only to the daily history.

Single-chat source-lineage policy
---------------------------------
A VCSC source lineage must have only one active development chat at a time. Parallel
chats can each start from the same archive, make valid but different changes, and then
return tarballs that silently omit the other chat's work. A later timestamp does not
prove that one archive is a descendant of another.

* Treat the exact archive supplied by the user in the current chat as the authoritative
  starting tree for that chat. Do not substitute a working tree or tarball from another
  chat, even if it appears newer or familiar.
* Normal handoff is serial: finish the current chat's work, obtain its returned tarball,
  then use **that returned tarball** as the input archive when continuing in a new chat.
* Do not continue modifying the same project lineage in two chats at once. If another
  chat is still doing VCSC work, finish or abandon one lineage before starting new work
  in the other.
* If concurrent work happened accidentally, stop feature/bug work and reconcile the
  divergent trees first. Diff both descendants against their known common input, identify
  every unique change, and explicitly merge or choose changes. Never resolve divergence by
  simply picking the archive with the newest filename or timestamp.
* Before packaging a result, make sure the working tree descends from the archive supplied
  for the current task. Never overwrite newer user work with a stale tree carried over from
  another chat.

Project goal
------------
VCSC is a brutally pared-down Atari VCS/2600 C-like compiler and companion 6502
toolchain. It favors explicit, analyzable, cycle-aware behavior over general C
compatibility. Work proceeds in small vertical slices with focused regressions.

Current public tools are `vcsc`, `vcsc-cc1`, `vcsc-as`, `vcsc-ld`, `vcsc-ar`,
and `vcsc-sim`. Source uses `.c26`, maintained assembler source uses `.s26`,
relocatable objects use `.o26`, and archives use `.l26`. `vcsc-cc1` assembly
output defaults to stdout and `-o -` explicitly means stdout. The top-level
`vcsc` driver supports that convention for `-S -o -`; object and linked
outputs deliberately require filenames, so `vcsc -c -o -` and linked
`vcsc -o -` are rejected instead of creating literal dash-named files. Driver
`-v` command traces go to stderr so streamed `-S -o -` assembly stays clean;
`-###` remains a stdout-only dry-run command listing.

Core language and ABI invariants
--------------------------------
* Target CPU/machine: 6507 on the Atari VCS/2600. Multibyte data is always
  little-endian.
* Stock ordinary integer types are signed and unsigned 8, 16, 24, and 32 bits.
  Stock packed-decimal types are unsigned `bcd8_t`, `bcd16_t`, `bcd24_t`, and
  `bcd32_t`, storing two decimal digits per byte.
* `int`, `char`, and `bool` are ordinary identifiers, not reserved built-in type
  names. Programs may typedef them. There is no float or double.
* Binary literals may use `.` for zero and `X`/`x` for one after `0b`/`0B`.
* `__builtin_ntsc_rgb(r,g,b)` is a compile-time uint8_t expression selecting the
  nearest meaningful even NTSC TIA color; exact ties choose the lower TIA byte.
* Strings are NUL-terminated `uint8_t` arrays in ROM. Pointer access qualifiers
  are enforced: `const` rejects writes and `writeonly` rejects reads and hidden
  read-modify-write operations.
* Pointers are 16-bit little-endian values. Compatible pointer subtraction
  yields an `int16_t` element count. Aggregate and array returns are forbidden.
* Functions have ordinary lexical parameters and locals, but storage is static
  and non-reentrant. Parameters, automatic locals, expression scratch, and the
  return object belong to one linker-overlayable activation record.
* Calls are directly named only. Function pointers, indirect calls, variadic
  functions, direct recursion, mutual recursion, and callback re-entry are
  rejected so the complete call graph remains visible.
* Value returns use exact-sized callee-owned zero-page objects named
  `function$__return`; source writes them through `$$`. Every epilogue is plain
  `RTS`. A, X, and Y are caller-clobbered and do not carry language returns.
* Direct-call arguments are evaluated left-to-right into pooled caller scratch,
  then copied to callee-owned parameter symbols before `JSR`.
* There is no software argument/local stack, heap, `sbrk`, `malloc`, or `free`.
  `test/software_stack_inventory.pl` guards against restoration of removed
  `_vcsc_sp`, `_vcsc_fp`, `_pushN`, `_popN`, and related helpers.
* The linker overlays sibling activations using the complete acyclic call graph.
  RIOT RAM and the 6502 hardware return stack share the physical $80-$FF pool.
  `callstack=callgraph` reserves two bytes per active JSR node plus declared
  hidden assembly use through `.callstackextra` metadata.
* The discard pseudo-object `_` supports write-only hardware idioms such as
  `WSYNC := _;`; assigning to `_` evaluates and discards the expression. A bare
  directly addressed one-byte `foo := _;` lowers to exactly one `STA` regardless
  of fixed placement (zeropage, ordinary RAM, activation storage, or absolute
  hardware address), so A/X/Y/S/P are unchanged.
* Direct ordinary `uint8_t` prefix/postfix `++` and `--` truth tests lower in
  place without generic expression scratch. Postfix tests branch on the old
  value while still applying the side effect when that old value is zero; this
  keeps idioms such as `while (i--) { WSYNC := _; }` within one 6507 scanline.
* Source `ref` objects may have distinct read/write addresses. Inline assembly
  resolves supported official and recognized unofficial opcode operands by
  access type and rejects missing, mismatched, or unknown access semantics.
* Compiler-generated builtins and metadata use reserved VCSC namespaces. Do not
  revive obsolete N/n65 compatibility spellings or formats.

BCD arithmetic constraints
--------------------------
Packed BCD addition and subtraction use decimal mode. BCD multiplication,
division, remainder, and compound forms are accepted only for a positive
constant decimal power `10^n`; multiplication accepts the constant on either
side, while division and remainder require it on the right. Lowering uses byte
moves or four-bit shifts/masks and does not call general multiply/divide helpers.
Representation-changing runtime casts between binary and packed BCD remain
unsupported; constants convert numerically.

Current cartridge and bankswitching model
-----------------------------------------
Public C26 topology profiles currently cover 2K, 4K, direct 8K packaging, F8,
F6, F4, and their Superchip variants. Profile filenames have no semantics; the
actual `cart`, `bank`, and `mem` declarations are authoritative. The reduced
`vcs.cfg` retains generic machine/RIOT policy rather than duplicating cartridge
topology.

Full-window F8/F6/F4 uses the missing cartridge address lines as a logical bank
namespace. VCSC `BANK0` is the startup/home bank and final physical file chunk;
logical bank identity, physical/file index, and selector hotspot are distinct.
Cross-bank calls use linker-generated, deterministic bridges. Superchip RAM uses
direct split aliases and must not trigger bank selection.

Component placement constraints are carried in object metadata through
`.segmentregion`, `.segmentalign`, `.segmentprivate`, `.pagecontain`, and
`.callstackextra` as applicable. Explicit pins and hard ROM-data ownership are
semantic constraints, not heuristic hints. The linker's default
`--bank-placement=optimized` mode uses deterministic weighted soft-edge packing
plus guarded single-component local moves; `simple` provides stable first-fit
capacity placement for comparison and debugging. Neither mode may break a hard
component, move a pin, violate replica locality or capacity, or increase
weighted hardware-return depth during local optimization.

`--explain-bank-placement` reports component membership, allowed banks,
candidate capacity/cut decisions, accepted and rejected local moves, and final
byte/cycle/site cut weights plus weighted stack depth. Actual generated bridge
entries remain authoritative in the map's `TRAMPOLINES` section.

Main-roadmap Item 42 is complete. Automatic whole-layout CODE/RODATA placement now
works across both selector-controlled banks and selector-free direct regions. Explicit
region qualifiers remain hard pins; `main` and `_` startup/runtime functions remain in
the unique startup/home region, including direct topologies where `$startup` is only a
placement marker. Direct cross-region absolute calls/jumps/data references remain plain

RAM, while mapper-owned cartridge RAM must be explicitly named `cartram` by the

Testing policy and last verified baseline
-----------------------------------------
When removing or changing a feature:

1. remove obsolete positive tests whose only purpose was the removed feature;
2. retain or add focused negative tests for clean rejection;
3. rewrite still-useful tests to use supported behavior;
4. update documentation and source-tree hygiene checks in the same slice.

The current completely verified baseline is:

    compile-only:             495 passed
    end-to-end/generic:       303 passed
    staged installed tools:   passed, including all final cartridge builds

The current tree has been verified against all 495 compile-only tests and all
303 end-to-end tests. The end-to-end inventory is executed in ordered capped
batches because the container imposes a hard wall-clock limit on one monolithic
command; every listed case must run and pass. Exact raster, event-trace, frame-
length, bankswitching, installed-profile, assembly-policy, and source-hygiene
coverage remain active.

Compact unsigned-byte lowering shortened the compiler-generated tail after a
final WSYNC by nineteen cycles. Generic `vcs_ntsc_wait_scanlines()` intentionally
keeps that compact, uncalibrated return phase. Beam-sensitive helpers do not rely
on it: `vcs_ntsc_wait_component_scanlines()` explicitly preserves the established
cycle-3 component entry, and `vcs_ntsc_wait_visible_tail_scanlines()` preserves
the established final-visible-tail phase before overscan. Exact historical phase
and Stella raster oracles remain authoritative; do not recalibrate them merely
because compiler lowering gets shorter.

Important active constraints and open questions
-----------------------------------------------
* Inline/included assembly stack use is not inferred. Components must declare
  known hidden use explicitly; automatic analysis may be considered later.
* General cross-statement computed-address reuse remains conservative. One narrow
  proven frame-table case now survives across a counted loop: when later page-pointer
  offsets are byte-exact doubles of earlier masked/shifted offsets and the loop cannot
  modify the pointer or source values, the compiler reuses the low byte with `ASL`.
* Runtime binary/BCD representation conversion and general BCD multiply/divide
  helpers remain deferred.
* Segmented/value-controlled/historical mapper families are not generic variants
  of F8/F6/F4. Add a separate model only for a concrete program that requires
  one; do not build a universal mapper language speculatively.
* Multisprite renderer work remains on the main roadmap and must not be smuggled
  into bankswitching placement work.
