VCSC DISASSEMBLER CONTEXT AND ROADMAP
=====================================

Purpose
-------
Create a standalone Atari 2600 cartridge disassembler named `vcsc-disas`.
The implementation will live in a new top-level `disassembler/` directory.
Start that directory by copying `stego/` and then rename/adapt the program and
Makefile rather than inventing another command-line/program skeleton from
scratch.

The primary output is VCSC assembly source (`.s26`). Given a cartridge binary,
`vcsc-disas` must emit source that the existing `vcsc-as` assembler can consume
to reproduce the original cartridge image byte-for-byte exactly.

Human readability, reverse-engineering usefulness, and good inference are major
goals, but exact reconstruction is the governing invariant. When those goals
conflict, exact bytes win.

This file is the focused design/context document and ordered roadmap for the
side project. It is intentionally separate from `.../roadmap.txt`; work here
does not advance or reorder the main VCSC roadmap.

Status legend: [ ] not started, [~] partial, [x] complete.

Current implementation status (2026-08-20)
------------------------------------------
The first implementation is now usable and exact-round-trip driven. It builds
`disassembler/vcsc-disas` and the standalone `disassembler/roundtrip.pl`. The
implemented foundation includes all 256 opcode bytes, exact addressing-mode
emission, mandatory branch `.same`/`.cross`, recursive bank-aware control flow,
unbanked 1K/2K/4K, F8/F6/F4 plus Superchip variants, FA, DPC and WD, per-bank origin inference, overlapping
instruction streams, code-as-data, definite/possible/unreferenced ROM-use roles,
canonical and mirrored TIA/RIOT symbolization, conservative sprite rows, static
video/controller inference, manual mapper/origin/entry/code/data/video/controller
hints, deterministic output, and exact raw-byte fallback for uncertain regions.
A disassembly that finds zero instructions is a hard error; a 100%-data dump is
not considered successful analysis.

For Superchip cartridges, the physical low `$100` bytes of each 4K bank remain in
the emitted image exactly but are marked as hidden by the RAM window and excluded
from ordinary ROM code/data discovery. Mapper overrides control this behavior: a
forced SC mapper enables it and a forced plain F8/F6/F4 mapper suppresses it.

Permanent regressions cover all 256 opcodes, all eight branch opcodes in both page
classes, forward-branch relaxation edges, deterministic arbitrary-ROM fuzz,
BIT-skip and generic overlaps, instruction-as-data, known indirect reads,
unreferenced ROM, TIA/RIOT mirrors and RMW accesses, mapper/Superchip inference,
video/controller fixtures, manual overrides, deterministic output, and exact
reassembly. A 16-ROM real VCSC corpus including PAL, SECAM, controller, score,
F8/F6/F4, F8SC/F6SC/F4SC, FA, DPC and WD cartridges also round-trip exactly through the
standalone verifier.

Items still marked partial are intentionally broader than the current first
implementation. Speculative instruction-island discovery now rejects newly
speculative paths that can reach HLT/JAM/KIL, records three-rejected-start
sequential-flow barriers, and uses straight-line JAM endpoints plus the mature
`stego` credibility filters before promoting a lower-confidence island; graphics
recognition can still grow beyond strong GRP/PF provenance; video inference
now covers maintained and arbitrary known TIM64T values, parameterized timer-helper
call sites, broad counted-WSYNC kernels, and filename region hints, but can still
grow into a lightweight dynamic frame probe for kernels whose scanline count is
not statically recoverable; richer
pointer/color/table recognition remains useful; manual known-pointer/table hints
are not yet present; and final hardening still needs broad arbitrary-ROM
fuzz/corpus coverage and an exercised Windows cross-build. These are improvements
to analysis breadth, not exceptions to byte-exact output.

Core invariant: exact binary round trip
---------------------------------------
For every accepted ROM there must be a mechanically testable path:

    original.bin
        -> vcsc-disas
    original.s26
        -> vcsc-as direct assembly
    reconstructed.bin
        -> byte-for-byte comparison with original.bin

The comparison includes file length and every byte. A SHA-256 comparison may be
reported as a convenience but does not replace a `cmp`-equivalent comparison.

If a real ROM contains `JMP ($xxFF)`, preserve those three bytes as raw data in
the emitted source. `vcsc-as` intentionally rejects that mnemonic form because
of the NMOS 6502/6507 page-wrap hazard; raw spelling is therefore required for
exact reconstruction of cartridges that deliberately rely on the silicon bug.

Inference must never break this invariant. If a mapper, origin, instruction,
data type, label, pointer interpretation, controller type, video standard, or
other semantic interpretation is uncertain, preserve the original bytes and
state the uncertainty in comments. A completely unfamiliar cartridge must be
able to degrade to an exact `.byte` representation rather than becoming
undisassemblable.

The disassembler must be deterministic: identical input plus identical command
line must produce byte-for-byte identical `.s26` output.

Do not normalize ROM images. Duplicated banks, padding, unused fill, inaccessible
physical bytes, unusual vector contents, and other oddities are part of the
input image and must survive the round trip exactly.

Generated-file header
---------------------
Every generated `.s26` file should begin with deterministic comments summarizing
at least:

    input filename
    input byte size
    input SHA-256
    inferred mapper/bankswitching scheme and confidence
    physical bank layout
    inferred logical origin for each bank and confidence/evidence
    inferred power-on/reset bank
    inferred video standard and confidence
    inferred controller type for each port and confidence
    important ambiguities or unsupported hardware assumptions
    vcsc-disas version

For 50 Hz software, report PAL-versus-SECAM ambiguity honestly when the ROM does
not contain enough evidence to distinguish them. Stable 50 Hz timing by itself
is PAL-family evidence, not proof of PAL rather than SECAM.

Video inference should accumulate evidence rather than depend on a short list of
VCSC scheduler constants. In particular, use arbitrary statically-known RIOT
timer values, timer arguments passed through small helper subroutines, broad
counted-WSYNC loop lengths, and explicit NTSC/PAL/SECAM filename tokens as
secondary evidence. Timer/scanline ranges are heuristics and must retain honest
confidence levels. Filename hints must use token boundaries and must never outrank
contradictory strong timing evidence. A future dynamic frame probe may execute a
small bounded model of the cartridge when static timing remains inconclusive; it
must not become necessary for exact-byte disassembly.

Output-address model
--------------------
Keep physical cartridge-file position separate from the 6507 logical/runtime
address. This is the same distinction required by `.../bankswitching.txt`.

Use assembler `.org` to describe physical output position in the reconstructed
cartridge image and `.rorg`/`.rend` to describe the inferred logical CPU address
for a physical bank. Multiple physical banks can therefore be emitted in file
order while each is analyzed in its runtime address space.

Conceptually:

    .org $0000
    .rorg $F000
        ; physical bank 0
    .rend

    .org $1000
    .rorg $F000
        ; physical bank 1
    .rend

The origins above are examples only. Do not impose VCSC's own bank origins on a
foreign ROM. Historical cartridges often map all physical banks to the same
runtime window, but other layouts exist.

The 6507 exposes only A0-A12 to the cartridge. A13-A15 can therefore differ in
encoded 16-bit operands without changing the physical cartridge-bus address.
Preserve the original 16-bit operand value. Do not replace a mirrored address by
a prettier canonical address if doing so changes either operand byte.

Origin inference
----------------
Infer the most plausible logical origin independently for every physical bank.
Use all available constraints together rather than treating the reset vector as
the only source of truth.

Strong evidence includes:

* RESET/NMI/IRQ vector values and whether they land at plausible offsets in a
  physical bank.
* Absolute `JMP $hhhh` targets.
* Absolute `JSR $hhhh` targets.
* Resolved indirect-JMP destinations.
* Absolute ROM data references whose physical target can be identified.
* Bank-switch transitions followed by control transfer into the selected bank.
* Internal consistency of branches, labels, tables, and decoded control flow.
* Common cartridge-window mirrors, used as priors rather than proof.

Absolute JMP opcodes deserve aggressive use as origin evidence. If a `$4c`
occurs at file offset O and its encoded destination can plausibly refer to offset
T in a bank, the destination immediately constrains that bank's runtime origin.
Do not require the JMP itself to have already been proven RESET-reachable before
using it as an origin hypothesis. A coincidental `$4c` in data is evidence only,
not proof, so score hypotheses by the number of independent constraints they
satisfy.

Apply the same logic to direct JSR destinations. For `JMP (addr)`, the operand is
the pointer address, not the destination. Only a statically resolved indirect
JMP destination constrains the destination bank's origin.

When resolving NMOS 6502/6507 `JMP ($xxFF)`, model the original silicon page-wrap
behavior: the high destination byte is fetched from `$xx00`, not `$xx+1:00`.

Do not compare raw counts of unresolved/dynamic control exits between mapper
hypotheses. A wrong mapper can make the graph look deceptively clean by mapping
execution into an early RTS or otherwise truncating reachable code. Exit counts
remain useful diagnostics within one analysis, but they are not positive mapper
evidence. When multiple mapper hypotheses remain viable without discriminating
selector/flow evidence, retain the ordinary size/signature default rather than
choosing whichever hypothesis decoded less code.

A bankswitch access followed by a JMP/JSR into the newly selected bank is
particularly valuable because it can constrain the destination bank directly.
Solve mapper state, reset bank, and per-bank origins together rather than
assuming they are independent.

All supported cartridge bank placements preserve 256-byte page alignment. That
is a durable invariant for branch annotation: uncertainty in a bank's absolute
high-byte origin cannot change whether a relative branch is same-page or
cross-page, because the origin shift cannot alter the low eight address bits.

If several complete origin assignments remain equally plausible, report the
ambiguity and choose a deterministic representation that still reassembles
exactly. Origin ambiguity is never a reason to omit `.same`/`.cross` on a branch.

Mapper inference
----------------
Infer bankswitching from behavior and layout rather than file size alone. File
size is useful evidence, not proof.

Initial mapper support should cover the ordinary full-window family already
understood by VCSC:

    unbanked 2K / 4K
    F8 / F8SC       8K
    F6 / F6SC      16K
    F4 / F4SC      32K
    FA             12K + 256-byte RAM
    WD              8K corrected image + 64-byte RAM
    WDSW            8K+3 historical swapped-bank preservation dump

Use a scored/evidence-based classifier. Evidence includes:

* File size and candidate 2K/4K bank boundaries.
* Exact duplicated/padded-bank patterns, without stripping them.
* Executed or referenced F8/F6/F4 selector hotspots.
* Which physical bank contains a plausible reset path.
* Per-bank vectors and reset/vector bridge patterns.
* Superchip read/write-window accesses. A read from `$x080-$x0FF` by itself
  is ambiguous with ordinary ROM and must not promote a plain mapper to SC; a
  decoded write to `$x000-$x07F` (or an explicit mapper override) is required.
* Whether the resulting bank-aware control-flow graph is coherent.
* For every size-compatible supported mapper, trace RESET-reachable code and
  credible speculative islands under that mapper's real selector semantics until
  the reachable graph reaches a fixed point. Eliminate hypotheses whose possible
  established execution reaches HLT/JAM/KIL, and prefer surviving hypotheses that
  explain decoded selector accesses. Raw detector byte strings are supporting or
  tie-break evidence only; bytes spanning unrelated instructions must not select a
  mapper when executable control flow contradicts that interpretation.
* Whether JMP/JSR/data-reference constraints agree with the mapper's bank
  windows and inferred origins.

Track the power-on/reset bank separately from mapper type. Knowing that a ROM is
F8 does not by itself identify which physical bank supplies RESET.

Mapper state is part of control-flow state. An access to a selector hotspot can
change which physical bank supplies subsequent instruction fetches at the same
runtime address. Reads, writes, and read-modify-write operations must be modeled
according to the mapper's actual hotspot semantics. A physical old-bank byte after
the selector is not the successor instruction if the access selected another bank;
for example, `LDA $hotspot` followed by old-bank JAM/KIL is a valid execution line
when the new bank supplies a valid instruction at the continuation PC. This rule
applies equally to primary tracing and speculative-island validation.

FA is an explicit CBS RAM Plus model rather than an F8 variant. A 12288-byte
image consists of three 4K physical banks selected by `$1FF8-$1FFA`; physical
bank 2 is the hardware power-on bank. The 256-byte cartridge RAM write port
occupies `$1000-$10FF` and the read port `$1100-$11FF`, so the first `$200`
physical bytes of each bank are preserved exactly but excluded from ROM
code/data discovery. The 6507's 13-bit external address bus means valid mirrored
bank origins need not be `$F000`; commercial FA code may intentionally use
origins such as `$3000`, `$5000`, and `$7000`.

WD is an explicit Wickstead Design model for Pursuit of the Pink Panther rather
than an F8 variant. Runtime ROM is eight 1K banks arranged four at a time across
the cartridge window. Reads from TIA `$30-$3F` request one of eight fixed bank
arrangements; writes to those TIA addresses remain ordinary TIA writes. WD also
has 64 bytes of cartridge RAM, read at `$1000-$103F` and written at
`$1040-$107F`. Power-on arrangement 0 maps logical banks `0,0,1,3` into
`$1000,$1400,$1800,$1C00`. Stella distinguishes the two known dump layouts by
name while instantiating the same hardware model: `WD` is the corrected 8192-byte
image, detected by the `A5 39 4C` (`LDA $39; JMP`) signature; `WDSW` is the
historical 8195-byte 8K+3 preservation image. In WDSW, logical 1K banks 2 and 3
are reversed in the file and the last three bytes are outside the emulated 8K
ROM. Analysis must use the corrected logical ordering while source emission
preserves the original file ordering and all three trailing bytes exactly.
Because the selector change is hardware-delayed, static control flow should
conservatively retain both the old and requested successor arrangements when
exact cycle placement is not proven.

E0 is an explicit segmented Parker Brothers model. An 8K image is eight physical
1K banks. Runtime `$1000-$13FF`, `$1400-$17FF`, and `$1800-$1BFF` independently
select any physical bank via `$1FE0-$1FE7`, `$1FE8-$1FEF`, and `$1FF0-$1FF7`;
`$1C00-$1FFF` is permanently physical bank 7 and supplies the vectors. The
deterministic reset configuration is physical banks 4,5,6,7. E0 configuration
must travel with the CFG state, and both established tracing and speculative
island validation must fetch the instruction after a selector from the newly
selected physical bank. Detached E0 islands are promoted conservatively only
when their speculative path actually exercises an E0 selector, because a bare
physical 1K chunk has no unique runtime segment/configuration. 2026-08-20 corpus
refinement: on 8K images, established E0 detector evidence keeps Stella's E0-before-E7
precedence over an otherwise unsignatured E7 hypothesis. This prevents a wrong E7
mapping from manufacturing `$FFE4-$FFE6` selector traffic in Gyruss/Popeye-family
images whose real startup path begins with a static-analysis-resistant RAM-clear loop.
An explicit VCSC E7 signature or genuine E7 detector evidence still identifies E7.

Do not rank mapper hypotheses by raw hotspot count. Decoder alias breadth differs
radically among mapper families (0840 is the concrete failure case), so a false
mapper may appear to have more selector evidence merely because more addresses
alias its hotspots. A bank transition that avoids an old-mapping HLT/JAM/KIL and
continues with valid code in the new mapping is strong positive evidence.

Do not pretend that unrelated schemes are variants of F8/F6/F4. 3F, 3E, E7,
FE, DPC+, CDF, and coprocessor cartridges need separate mapper models. DPC has its own explicit model: its distinctive 10240/10495-byte layout
contains two 4K F8-style executable banks followed by 2K of DPC data ROM and, in
the standard 10495-byte dump, a 255-byte RNG table. File size is decisive evidence
for this historical format.

A successful disassembly must identify at least one executable instruction. If
analysis finds zero instructions, emit an error and do not create an `.s26` file.
Do not claim that an unsupported mapper was successfully disassembled merely
because its bytes can be reproduced as `.byte` directives. Raw-byte emission is
still the exactness fallback for uncertain regions of a supported, nonempty code
analysis.

Analysis model: byte roles are non-exclusive
--------------------------------------------
Do not classify each ROM byte with a single `code` versus `data` enum. Real 6502
software can deliberately use the same physical bytes in multiple ways.

A byte may simultaneously be:

    start of one decoded instruction
    operand of one or more decoded instructions
    part of another overlapping instruction stream
    read as ROM data
    sprite/font data
    pointer/vector/table data
    mapper metadata/hotspot-adjacent data
    possibly read through an unresolved dynamic access
    otherwise unreferenced

Store semantic roles independently and retain provenance/evidence for each role.
At minimum distinguish definite versus heuristic executable reachability, direct
versus possible data reads, overlapping instruction participation, and truly
unreferenced bytes.

Physical ROM layout has exactly one emitted representation. Analysis may attach
multiple semantic interpretations to those bytes, but the `.s26` source must not
emit the same physical bytes twice merely to show two views of them. Use labels,
aliases, and comments to expose alternate interpretations.

Control-flow discovery
----------------------
Seed definite executable control flow from plausible vectors and user-supplied
entry hints, then recursively follow:

    fallthrough
    all eight conditional branches
    JMP
    JSR and RTS
    resolvable indirect JMP
    provable RTS/stack dispatch idioms
    mapper-changing accesses and their successor bank states

Reuse/adapt useful abstract-analysis machinery from `stego`, including constant
register tracking, zero-page pointers, stack-built destinations, RTS-based
dispatch, and table-driven indirect control flow. Do not change `stego`'s public
behavior as part of this work; copied code can be factored later only if doing so
simplifies both tools and preserves independent regression coverage.

If control flow enters RIOT RAM, Superchip RAM, or another writable region, do
not invent ROM instructions. Follow dynamically generated/copied code only when
both the written bytes and execution destination are provable. Otherwise end
that static path with an explanatory annotation.

A second-pass instruction-island detector may identify plausible unreachable
utility code, but heuristic islands must remain lower-confidence than vector- or
control-flow-reachable code. Random data happens to decode as legal 6502 very
often; legal decoding alone is not meaningful evidence of execution.

Speculative island validation and negative evidence
---------------------------------------------------
Use HLT/JAM/KIL opcodes as strong negative evidence when discovering otherwise
unreferenced instruction islands. This is a speculative-code rule, not a claim
that a real cartridge can never intentionally execute a CPU-locking opcode. If
normal vector/control-flow analysis has already proved a HLT/JAM/KIL reachable,
preserve it as executable code. Do not invalidate established code merely
because it deliberately halts the processor.

For each otherwise unknown candidate instruction-start address in each mapped
4K cartridge bank/window, perform a speculative control-flow decode beginning at
that byte. At minimum:

    ordinary fallthrough       -> continue at the next instruction
    conditional branch         -> explore every statically reachable successor
    JSR                        -> explore the call target and return continuation
    RTS / RTI                  -> successful path termination
    unconditional JMP          -> successful transfer/termination for the local
                                  linear island; follow the target as appropriate
    previously proven code     -> successful path termination
    newly speculative HLT/JAM/KIL
                               -> reject the candidate flow

Abstract-state facts matter. The shared analyzer tracks A/X/Y plus C/Z/N/V/D
where they are statically known, so every conditional branch can prune an arm
when its controlling flag is proved. If one arm is provably unreachable, a
HLT/JAM/KIL on that impossible arm does not reject the candidate.
If both outcomes remain possible, every possible executable arm must be safe; a
possible path into HLT/JAM/KIL rejects that speculative candidate.

Do not turn rejection into an exclusive byte classification. A candidate start
can be rejected while a later byte in the same range is independently proven to
be an instruction start by a branch, JMP, JSR, vector, mapper transition, or
other established entry. This remains compatible with overlapping instruction
streams and code-as-data.

Retain rejected candidate starts as first-class negative evidence. The longest
6502/6507 instruction is three bytes, so three consecutive addresses that have
all been proven not to be instruction starts form a sequential-flow barrier:
no ordinary fallthrough instruction stream can cross that barrier. Explicit
control transfers may still jump over the barrier or enter code on either side,
so a barrier does not by itself prove that all later bytes are data.

Use these barriers to strengthen second-pass island and unused-ROM analysis.
For performance, first build one physical-ROM speculative control-flow graph and
reverse-walk it from every HLT/JAM/KIL byte. Mapper-selector edges cross to the
selected physical bank before the next opcode fetch; ordinary branch/JSR edges
remain bank-local. This cheaply marks the only unknown
starts that can structurally reach a halt. Run the more expensive stateful C/Z/N/V
validation only for those starts; a start outside that reverse-reachable set cannot
be rejected by the halt rule. Branch-state analysis still makes the final decision,
so a structurally reachable but provably dead halt arm remains safe. This prefilter
must preserve the same established-code/JMP/JSR/local-termination semantics as the
stateful walk.

The implementation bounds one stateful speculative candidate walk to 512 instruction
visits so adversarial/random legal-opcode padding cannot make corpus analysis
pathological; hitting that budget is inconclusive and never causes promotion or
rejection. Every three consecutive rejected starts are a sequential-flow barrier.
For the stronger claim that an entire interval through a JAM/KIL endpoint is
non-code, require all three rejected starts to reach their halt through pure
straight-line fallthrough (a proved not-taken branch may remain on that line).
Only that stronger barrier span supplies an automatic island boundary.

A candidate after such a span is still not code merely because it avoids JAM.
Adapt `stego`'s second-pass credibility checks: reject conflicts with established
code/data roles, require a coherent multi-instruction trace with a credible
terminal or join, require at least 80% official NMOS 6502 instructions with very
few unofficial opcodes, and treat an unresolved indirect JMP as weak rather than
a sufficient terminal. Prefer inbound branch/JMP/JSR references or meaningful
internal control flow; random legal-opcode runs must remain raw. Never let this
heuristic override definite control flow, overlaps, or definite code-as-data.

Overlapping instruction streams
-------------------------------
The analyzer must support branch/JMP/JSR targets that enter the middle of an
instruction decoded along another path. That does not invalidate either path.
Both instruction instances can be real and reachable.

A canonical example is the common three-byte BIT-skip trick:

    CheckStatus:
        LDA STATUS_REG
        BNE.same LoadAlternative
        LDX #$01
        .byte $2c
    LoadAlternative:
        LDX #$02
        STX player_speed

On the linear path the bytes `$2c $a2 $02` execute as `BIT $02A2`, consuming the
`LDX #$02` bytes. On the taken branch, execution begins at `$a2`, so those same
bytes execute as `LDX #$02`.

Internally this must be represented as two overlapping instruction instances,
not as a decoder error. A control-flow target landing inside an already decoded
instruction is strong evidence for an additional instruction start.

For generated source, prefer a representation such as `.byte $2c` immediately
before the alternate-entry label when spelling the outer `BIT` mnemonic would
prevent placing a label on the inner opcode byte. Annotate the fallthrough
interpretation in comments. General support must not be hard-coded only for
`$2c`; hand-written 6502 can overlap streams in other ways.

Instruction bytes and operands read as data
-------------------------------------------
Cartridges may intentionally read their own instruction bytes or operand bytes
as data. The analyzer must preserve both meanings simultaneously.

For example, an immediate operand may be used as a table constant elsewhere:

    Foo:
        LDA #$42
        RTS

    ...
        LDA Foo+1

`Foo+1` remains an operand of executable code and is also a definite ROM-data
read target. Data evidence must never cause the executable interpretation to be
removed, and executable decoding must never hide a proven data reference.

When possible, generated labels/aliases should make such self-references clear
without duplicating physical bytes. If no elegant source spelling exists, keep
the exact primary byte representation and explain the additional data use in a
comment.

ROM-read and unused-byte analysis
---------------------------------
Track reads from cartridge ROM separately from instruction fetches. Direct
absolute/indexed accesses with known bounds can mark definite data ranges.
Abstract-state analysis should narrow indexed and indirect accesses as far as it
can.

Use at least these usage states for reporting:

    definitely executed/fetched
    definitely read as data
    executed and read as data
    possibly referenced/read
    unreferenced by all discovered/provable accesses

A region should be called unreferenced only after known control flow and data
accesses have been analyzed. If an unresolved indexed or indirect access could
reach the region, classify it as possibly referenced rather than claiming it is
never read.

When the analyzer can prove that bytes are neither fetched as instructions nor
read as data, identify them explicitly as unreferenced/unused ROM. Do not
force-decode them merely because their bit patterns form legal opcodes. Emit
exact `.byte` data, preferably grouped into readable runs with comments such as:

    ; unreferenced ROM bytes

This information should also appear in an optional analysis summary, with byte
counts for executed, data-read, overlap, possibly referenced, and unreferenced
regions. Counts must define how overlaps are handled rather than pretending the
categories are mutually exclusive.

Instruction emission
--------------------
For bytes represented primarily as code, emit normal 6502 mnemonics whenever the
current `vcsc-as` opcode table and addressing-mode syntax reproduce the exact
original opcode and operands.

Support all 256 opcode bytes. For unofficial/ambiguous encodings where a normal
mnemonic would not uniquely preserve the byte, use the assembler's exact `opXX`
spelling and the correct addressing-mode suffix/operand form. Never silently
replace one opcode encoding by a semantically equivalent different opcode.

Preserve the original addressing mode explicitly when symbolization or normal
relaxation could cause a zero-page/absolute choice to change. Avoid redundant
suffix noise: ordinary named zero-page instructions normally omit `.z`, `.zx`,
and `.zy` because resolved 8-bit operands naturally select those modes. An
original absolute/absolute-indexed instruction whose resolved operand is below
`$0100` must retain `.a`, `.ax`, or `.ay` so it cannot relax to the shorter
encoding. Raw `opXX` spellings retain whatever explicit mode suffix the assembler
requires for an otherwise ambiguous operand shape. Other suffixes such as `.i`,
`.ix`, and `.iy` remain available where needed for exact reconstruction.

Branch page annotations
-----------------------
Every emitted conditional branch instruction must carry an explicit hard timing
annotation:

    .same   when the taken branch stays on the page containing PC+2
    .cross  when the taken branch crosses that page boundary

Never emit a bare branch or `.flex` from `vcsc-disas`.

Emit the exact numeric runtime target as the branch operand, even when analysis
has also generated a label at that destination. Put the deterministic target
label in a comment when useful. This avoids a `vcsc-as` forward-label relaxation
corner at original positive displacements +125 through +127: the assembler's
provisional long-branch form temporarily moves a forward label three bytes away,
which can otherwise prevent relaxation back to the original short branch. A
numeric target is fixed during relaxation and therefore preserves the original
two-byte branch exactly without changing the assembler.

This classification is always determinable for a decoded branch. Relative
branch displacement gives the target low-byte relationship directly, and every
supported cartridge mapping/origin shift preserves 256-byte page alignment.
Absolute origin uncertainty therefore cannot change `.same` versus `.cross`.

The comparison is between the page of PC after the two-byte branch instruction
and the page of the branch target, matching NMOS 6502/6507 taken-branch timing.
Test all eight branch opcodes in both same-page and cross-page cases, including
branches near `$xxFE/$xxFF` boundaries and bank origins that differ by page-
aligned amounts.

TIA and RIOT symbolic register accesses
---------------------------------------
Generated assembly should use the project's canonical Atari hardware register
names rather than unexplained numeric addresses whenever doing so can preserve
the original instruction bytes exactly.

The canonical vocabulary is currently defined by:

    libraries/vcs/tia.c26
    libraries/vcs/riot.c26

TIA examples include:

    VSYNC VBLANK WSYNC RSYNC
    NUSIZ0 NUSIZ1 COLUP0 COLUP1 COLUPF COLUBK CTRLPF
    PF0 PF1 PF2 RESP0 RESP1 RESM0 RESM1 RESBL
    AUDC0 AUDC1 AUDF0 AUDF1 AUDV0 AUDV1
    GRP0 GRP1 ENAM0 ENAM1 ENABL
    HMP0 HMP1 HMM0 HMM1 HMBL HMOVE HMCLR CXCLR
    CXM0P CXM1P CXP0FB CXP1FB CXM0FB CXM1FB CXBLPF CXPPMM
    INPT0 INPT1 INPT2 INPT3 INPT4 INPT5

RIOT examples include:

    SWCHA SWACNT SWCHB SWBCNT INTIM TIMINT
    TIM1T TIM8T TIM64T T1024T

The current assembler expands `.include` source text but does not make ordinary
constant assignments from an included file available afterward in the way a
generated disassembly would need. Do not change assembler semantics merely for
the disassembler. `vcsc-disas` therefore emits the canonical TIA/RIOT equates it
actually needs into each generated `.s26`, derived from the same canonical names
in `libraries/vcs/tia.c26` and `riot.c26`. The output remains self-contained and
round-trips with the existing assembler.

Symbolization must preserve exact encoded addressing mode and operand value. For
example, if `COLUBK` is `$09`:

    original two-byte zero-page access -> use `COLUBK` with `.z` as needed
    original three-byte absolute $0009 -> use `COLUBK` with `.a`

Do not let the assembler shorten an original absolute access into zero page.

TIA and RIOT are mirrored in the VCS address space. If the ROM intentionally
uses a noncanonical mirror, do not rewrite the encoded address to the canonical
one. Prefer an exact symbolic expression such as a canonical register plus the
appropriate mirror offset when the assembler can encode that exact numeric
operand; otherwise retain the numeric operand. In either case, every preserved
noncanonical mirror access must carry an end-of-line or immediately adjacent
comment naming the canonical hardware register actually selected by the decoded
bus address and access direction, for example `; mirror of COLUBK ($09)` or
`; mirror of SWCHA ($0280)`. The original operand bytes remain authoritative.

Choose symbols according to access semantics, not address alone. TIA read and
write register sets differ. Loads should name the appropriate readable TIA
register; stores should name the appropriate writable register. Read-modify-
write instructions or unusual mirrored/open-bus accesses may not have one clean
symbolic name; preserve the exact operand and annotate both effects rather than
inventing a misleading symbol.

Hardware-register recognition feeds higher-level analysis. SWCHA/INPT accesses
are controller evidence; VSYNC/VBLANK/WSYNC/timer accesses are video/frame
evidence; GRP0/GRP1/PF0/PF1/PF2 data flow is graphics/sprite evidence; mapper
hotspots remain mapper semantics rather than ordinary hardware-register data.

Data emission
-------------
Bytes not primarily represented as instructions must still be readable and
exact. Use labels for proven ROM-data targets and deterministic names for
anonymous targets.

Emit `.word` only when a two-byte region is proven to be a little-endian pointer
or vector and symbolic assembly reproduces the exact original 16-bit value.
Otherwise use bytes. Never rewrite a mirrored pointer value to a prettier
bus-equivalent address.

A symbolic reference may point into the interior of an emitted source container.
This includes instruction operands and the high byte of a two-byte vector `.word`.
Such an interior byte cannot own a standalone source label. Promote the label to
the emitted container boundary and reference the exact byte as `label + offset`.
For example, an IRQ vector containing `$FFFF` in a 4K `$F000` cartridge may be
emitted as `L_FFFE: .word L_FFFE + 1`; never emit an unresolved `L_FFFF` merely
because analysis marked `$FFFF` as a target.

Vector-table bytes are not inherently data-only. Commercial cartridges can
deliberately execute bytes at `$xFFA-$xFFF`, including entering at the high byte
of a vector word. If either byte of a candidate vector `.word` is established as
an executable instruction start, the `.word` container must yield to the normal
overlapping-code emitter so every executable entry can own a real source label.
Preserve the vector meaning in a comment, but emit the executable bytes/instructions
as the primary physical representation. Only use the container-relative
`label + offset` form when the vector remains an indivisible emitted `.word`.

Do not reinterpret arbitrary tables just because a higher-level type would be
possible. Conservative `.byte` output is always acceptable and safer than a
wrong semantic guess.

Sprite/font visualization
-------------------------
Recognize conservative sprite/font/playfield byte tables when a short,
straight-line dependency path carries a ROM load into a TIA graphics write.
Track source bytes loaded into A/X/Y through register transfers and simple ALU
or accumulator-shift transforms, and recognize STA/STX/STY writes to
GRP0/GRP1/PF0/PF1/PF2. Runtime-indexed tables may be bounded by a proven
countdown or by the next known code/vector/label boundary; do not carry graphics
provenance across calls, branches, unknown raw opcodes, or unrelated loads.

For sprite-like bytes emit exactly one assembler-native binary byte per source
line and put the X/dot picture beside it, for example:

    .byte %00011000    ; ...XX...
    .byte %00111100    ; ..XXXX..
    .byte %01100110    ; .XX..XX.

The current `vcsc-as` binary literal syntax is `%[01]+`; it does not accept X or
dot characters inside a numeric literal. `X` in the comment means a set bit and
`.` means a clear bit. This preserves the human-scannable form without changing
the assembler language merely for the disassembler.

One byte per line is intentional so humans can visually scan the glyph. Preserve
byte order exactly; do not vertically reverse, bit-reverse, rotate, trim blank
rows, or otherwise improve the art.

Use sprite formatting only when evidence is reasonably strong. Numeric lookup
tables, random constants, call-mediated/compressed-looking graphics, and ordinary
data should not be turned into fake pictures merely because some rows look
attractive. A mask or transformed table that is directly proven to feed PF0/PF1/
PF2 is graphics data and should use visual rows; a merely mask-shaped byte table
without that provenance should stay numeric.

Video-standard inference
------------------------
Infer NTSC versus PAL-family behavior and include the result in the generated
header with confidence/evidence.

Evidence can include:

* VSYNC/VBLANK/WSYNC structure.
* RIOT timer values and frame scheduling.
* Stable frame-line count inferred statically or by optional emulation.
* Audio timing constants when recognizable.
* Color-value usage as weak supporting evidence only.

Prefer static analysis, but use VCSC/Stella/simulator machinery for an optional
dynamic measurement pass when static evidence is insufficient and execution is
safe/deterministic enough.

Do not claim that 312-line/50 Hz timing distinguishes PAL from SECAM. If the ROM
cannot prove the distinction, report `PAL-family (PAL/SECAM ambiguous)` or
similar. Explicit user override remains available.

Controller inference
--------------------
Infer the expected controller independently for each port and report confidence.
Initial models should include:

    joystick
    paddles
    keypad
    driving controller
    unused
    unknown/ambiguous

Evidence includes:

* SWCHA bit usage and direction masks.
* INPT0-INPT5 reads.
* VBLANK paddle discharge/charge behavior.
* keypad row-drive/column-read patterns.
* driving-controller quadrature patterns.
* fire-button reads.
* timing loops associated with analog paddle reads.

Mixed-port cartridges are valid. Do not collapse both ports to one type merely
because one port is obvious. Multiple plausible controller interpretations may
be reported when static evidence is insufficient.

Labels and comments
-------------------
Generate deterministic labels for definite control-flow targets, ROM-data
targets, vectors, tables, and bank-local entry points. Bank-qualified names are
required where the same runtime address exists in multiple physical banks.

Prefer semantic hardware symbols over generic labels for TIA/RIOT accesses, as
described above.

Comments should expose useful alternate interpretations without becoming a
trace dump. Particularly valuable comments include:

* inferred mapper transitions.
* overlapping instruction interpretations.
* instruction bytes/operands also read as data.
* unreferenced/unused ROM runs.
* sprite/font confidence.
* ambiguous origins/controllers/video standard.
* dynamic-code transfers static analysis cannot follow.

Provide a separate verbose analysis/report mode for detailed evidence scores so
normal `.s26` output remains readable.

Manual overrides and analysis hints
-----------------------------------
Static analysis cannot perfectly recover every deliberately tricky ROM. Give the
human precise overrides rather than forcing them to edit generated source after
the fact.

Plan for options/hints covering at least:

    mapper
    reset/power-on bank
    per-bank logical origin
    video standard
    controller type per port
    bank-qualified entry points
    forced code ranges
    forced data ranges
    known generic-table and little-endian pointer-table ranges

Contradictory hints must produce diagnostics rather than silently corrupting the
analysis. Forced code/data roles still do not have to be exclusive: an advanced
hint should be able to say that a range is executable and also read as data.

Unknown/unsupported mapper handling
-----------------------------------
Do not report a 100%-raw file as a successful disassembly. If the mapper is
unknown and no executable instructions can be established, fail with a clear
`no instructions found` diagnostic and do not create `.s26` output. This keeps
`roundtrip.pl` honest: byte reproduction alone is not proof that disassembly
succeeded.

Within a supported mapper, or once executable code has otherwise been established,
uncertain physical regions may still be emitted conservatively as raw `.byte`
data to preserve exact reconstruction. Do not fake bank origins or branch targets
that depend on unsupported mapping. Any branch actually decoded as an instruction
still receives its mandatory `.same`/`.cross` annotation.

Command-line conventions
------------------------
`vcsc-disas` must follow the command-line usage/help conventions established by
the other public VCSC tools rather than preserving `stego`'s current minimal
one-line interface. In particular:

* `-h` and `--help` print the complete usage/options text and exit successfully.
* `-V` and `--version` print version information and exit successfully, using
  the same generated project version mechanism as the other tools.
* An unsupported option reports the offending option and then prints the same
  guidance used elsewhere in VCSC:

      Try 'vcsc-disas --help' for a list of supported options.

  Use the actual invocation name (`argv[0]`) in the implementation rather than
  hard-coding `vcsc-disas` into that diagnostic.
* Missing option arguments and other command-line errors use the same concise
  diagnostic style and nonzero exit behavior as the other VCSC tools.
* The help text documents every supported option, normal input/output naming,
  important inference overrides, and at least one ordinary invocation example.
* Command-line regressions must pin help, version, unsupported-option guidance,
  missing-argument diagnostics, and exit status so this interface cannot drift.

Standalone corpus round-trip verifier
-----------------------------------------
Provide a standalone executable Perl development utility at
`disassembler/roundtrip.pl` with a normal Perl shebang. It is deliberately
separate from the normal `test/` directory and test-runner inventory so it can
be pointed at arbitrary external cartridge corpora without copying those ROMs
into the VCSC source tree.

Its command line is exactly two positional arguments:

    perl disassembler/roundtrip.pl INPUT_DIR OUTPUT_DIR

An incorrect argument count prints a concise usage line and exits nonzero.

Required behavior:

* `INPUT_DIR` and `OUTPUT_DIR` must resolve to different directories; reject a
  configuration that could overwrite the source cartridges.
* Create `OUTPUT_DIR` if it does not exist.
* Enumerate regular files whose names end in `.bin` directly in `INPUT_DIR`, in
  deterministic lexical order. Do not recurse into subdirectories unless a
  future option explicitly requests recursion.
* For each `NAME.bin`, run `vcsc-disas` on the input cartridge and write
  `OUTPUT_DIR/NAME.s26`.
* Assemble that generated source with the project `vcsc-as` and create a raw
  `OUTPUT_DIR/NAME.bin` containing the reconstructed cartridge image.
* The current assembler writes final direct assembly as Intel HEX rather than a
  raw `.bin`. The standalone script should therefore invoke `vcsc-as` with an
  explicit temporary/output `.hex`, decode that Intel HEX itself in Perl, and
  write the raw `.bin`. This is a verifier implementation detail, not a reason
  to change `vcsc-as` or the generated `.s26` language.
* Remove or replace stale per-ROM output before processing so a failed command
  can never accidentally compare an old reconstructed file. Temporary files
  should not masquerade as successful output.
* Compute and print the MD5 digest of both the original and reconstructed
  cartridge for every case. Use Perl's MD5 support rather than depending on an
  external `md5sum` executable so the script remains self-contained.
* Any MD5 mismatch is a failure. Also perform an exact size/byte comparison so
  the project's stronger byte-for-byte round-trip invariant remains the final
  authority even if two MD5 values happen to match.
* Optionally accept `--stella STELLA` and compare the mapper in generated source
  with `STELLA -rominfo ROM`'s resolved Bankswitch Type. This is a differential
  diagnostic, not an oracle: Stella's result combines its MD5-keyed property
  database with its own autodetector, so a disagreement must be surfaced rather
  than silently deciding which implementation is right. `--stella-strict` may
  promote mapper disagreement to command failure for an explicitly requested
  zero-difference gate.
* Keep SHA-256 in the generated source header. MD5 exists in the corpus verifier
  specifically for Stella/database interoperability and round-trip reporting; do
  not replace the stronger source-identity digest with MD5.
* A `vcsc-disas` failure, assembler failure, malformed Intel HEX, missing output,
  size mismatch, byte mismatch, or digest mismatch must mark that ROM failed.
* Continue through the whole input directory after an individual failure, print
  a concise PASS/FAIL line for each ROM, print final totals, and exit nonzero if
  any ROM failed. Exit zero only when every discovered `.bin` round-trips
  exactly. Treat an input directory containing no `.bin` files as an error.
* Handle spaces and shell metacharacters in filenames safely; use Perl list-form
  process invocation rather than constructing shell command strings.
* By default locate the development-tree `disassembler/vcsc-disas` and
  `assembler/vcsc-as` relative to the script/repository rather than relying on
  the caller's current directory. If overrides are later added, document them
  and keep the no-option two-directory invocation working.

The output corpus is intentionally useful after a run: each successful input
keeps both the human-readable `.s26` and the reconstructed same-named `.bin` for
manual inspection or emulator testing.

Unbanked 1K topology extension (2026-08-20)
-------------------------------------------
* A 1024-byte image is one physical 1K ROM mirrored four times through the
  4K cartridge window. Runtime targets therefore resolve modulo `$0400` while
  source emission preserves exactly the original 1024 physical bytes.
* Origin inference supports the four 1K mirror positions and normally presents
  a top-mirror image at `$FC00`; `--mapper 1k` explicitly selects the topology
  and rejects other file sizes.
* The final six physical bytes are NMI/RESET/IRQ-BRK vectors. Normal analysis
  seeds every vector whose target resolves into cartridge ROM, so an IRQ-only
  routine is recovered even when RESET never references it. RESET-only seeding
  remains intentionally limited to temporary mapper-hypothesis validation.
* `c33caa7d6ac7251bb804e0473198901d.bin` is the real regression: RESET `$FC96`
  and IRQ/BRK `$FC80` both decode under the 1K topology and the file reconstructs
  byte-for-byte exactly.

Definition of first useful milestone
------------------------------------
The first useful milestone is reached after roadmap items 0 through 3:
`vcsc-disas` can take arbitrary unbanked/F8/F6/F4/FA cartridges, infer plausible
bank origins and executable control flow, emit exact branches and instruction
bytes, and reassemble the original image exactly.

Items 4 through 8 turn the analysis model into one capable of handling the
things real hand-written Atari code does: Superchip state, overlapping streams,
code read as data, truly unused bytes, and symbolic hardware accesses. Those are
not cosmetic extras; they are required before calling the disassembly robust.

Sprite rendering, video/controller inference, richer labels, and documentation
then make the output pleasant and useful to humans. The standalone corpus
round-trip verifier provides the final practical way to throw large external ROM
collections at the exact-reconstruction invariant without enrolling those ROMs in
the repository test suite.

Do not invert the priority. A disassembler that produces beautiful comments but
cannot reproduce the input ROM exactly is not a disassembler we can trust.

Corpus differential note (2026-08-19): `roundtrip.pl --stella` assumes the input
set has already been filtered to Atari 2600/VCS ROMs. Stella `-rominfo` resolves
a VCS mapper; it is not a generic Atari-platform classifier, so unrelated 5200,
7800, or Atari 8-bit binaries of a supported size can receive a plausible-looking
size-default mapper. Such rows are corpus errors, not mapper-reference evidence.


Doubled 2K preservation images
------------------------------
A 4096-byte file made from two byte-identical 2048-byte halves is a logical 2K cart. Analyze one half and preserve the duplicate half raw for exact round trip.
