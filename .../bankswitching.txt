VCSC BANKSWITCHING: DURABLE MODEL AND OPEN WORK
==============================================

Purpose
-------
Keep only cartridge-model rules that future mapper work must not rediscover and
unfinished bankswitching items. Completed implementation narratives are archived
under `.../context-history/`; the pre-cleanup full document is in 2026-08-22.

Durable identity model
----------------------
Never use bare "bank 0" without saying which identity is meant. Keep these three
facts separate:

1. **VCSC logical bank** -- source/linker namespace. For the classic full-window
   family BANK0 is the $F000 home/startup bank, BANK1 is $D000, then descending
   by $2000.
2. **Physical/file bank index** -- zero-based emitted chunk number. Output is in
   ascending logical-address order, so VCSC BANK0 is always the final 4K chunk
   in the file for F8/F6/F4.
3. **Mapper selector hotspot** -- hardware address selecting a physical chunk.

Classic full-window mapping:

    mapper  file index  VCSC bank  linker range  selector
    ------  ----------  ---------  ------------  --------
    F8      0           BANK1      $D000-$DFFF   $1FF8
            1           BANK0      $F000-$FFFF   $1FF9

    F6      0           BANK3      $9000-$9FFF   $1FF6
            1           BANK2      $B000-$BFFF   $1FF7
            2           BANK1      $D000-$DFFF   $1FF8
            3           BANK0      $F000-$FFFF   $1FF9

    F4      0           BANK7      $1000-$1FFF   $1FF4
            1           BANK6      $3000-$3FFF   $1FF5
            2           BANK5      $5000-$5FFF   $1FF6
            3           BANK4      $7000-$7FFF   $1FF7
            4           BANK3      $9000-$9FFF   $1FF8
            5           BANK2      $B000-$BFFF   $1FF9
            6           BANK1      $D000-$DFFF   $1FFA
            7           BANK0      $F000-$FFFF   $1FFB

    file_index(BANKn) = bank_count - 1 - n

E0 is segmented rather than full-window: eight physical 1K chunks feed three
independently selectable windows plus a fixed top chunk. `$1000-$13FF` selects
with `$1FE0-$1FE7`, `$1400-$17FF` with `$1FE8-$1FEF`, and `$1800-$1BFF` with
`$1FF0-$1FF7`; `$1C00-$1FFF` is always physical bank 7. Power-on mapping is
physical banks 4/5/6/7. One physical chunk may appear in more than one window,
so do not model E0 as one selector per bank or as four F8-style whole windows.

FE/SCABS is also not an F8-style hotspot mapper. The released two-bank
layout stores physical/file bank 0 as the `$F000-$FFFF` startup view and
physical/file bank 1 as the `$D000-$DFFF` alternate view. Any access to mirrored
`$01FE` arms a latch; the **following** bus cycle's data selects the bank
(`E/F` high nybbles select physical bank 0, `C/D` select physical bank 1).
With `SP=$FF`, a top-level `JSR $Dxxx` pushes its low return byte to `$01FE` and
the following target-high fetch selects bank 1. `RTS` later reads `$01FE`,
arming the same latch so the following caller-high stack byte restores bank 0.
VCSC therefore pins automatic FE ROM to startup bank 0, permits explicit bank-1
placement, and only lowers a cross-bank JSR directly when its caller is
`main`; cross-bank data, branches, jumps, and nested calls are rejected rather
than pretending FE has a generic trampoline corridor.

WD/Wickstead Design uses eight physical 1K chunks and eight complete four-segment
arrangements. Power-on arrangement 0 is `0,0,1,3`; reads of TIA `$30-$3F` select
arrangements 0-7 only after the hardware delay, while writes to those addresses
remain ordinary TIA writes. WD also owns 64 bytes of split RAM: reads
`$1000-$103F`, writes `$1040-$107F`. The corrected public 8192-byte `WD` layout
is distinct from the historical 8195-byte `WDSW` preservation dump, although
both instantiate the same mapper behavior. Public WD C26 code uses the `$40-$7F`
TIA mirror so ordinary collision/input reads cannot become selectors.

Classic 3F and 3E reserve the low TIA write page for mapper control. Public
profiles therefore bind ordinary TIA accesses through the equivalent `$40-$7F`
mirror; 3E mapper selection itself remains literal `$3E`/`$3F`. Do not depend
on an emulator forwarding non-hotspot low-page writes to the TIA.

FA2 extends the FA split-RAM model to six or seven directly selected 4K ROM
banks. Public VCSC profiles are clean 24K and 28K payloads: physical/file bank 0
is the startup bank, `$1FF5-$1FFA` select banks 0-5, optional `$1FFB` selects bank
6, and the first `$200` bytes of every selected bank are hidden by the 256-byte
cartridge-RAM ports (write `$1000-$10FF`, read `$1100-$11FF`). VCSC emits the
native 24K/28K payload rather than Harmony's 29K/32K wrapper forms. Harmony
`$1FF4` flash persistence is optional external behavior and is not part of the
core compiler/linker/simulator contract.

DPC is F8 program banking plus two non-CPU-addressable image regions. Physical
file chunks 0/1 are the ordinary 4K F8 program banks; file chunk 2 is 2048 bytes
of display data consumed by the DPC fetchers; file chunk 3 is the conventional
255-byte Poly8 sequence tail. Model the latter two as `$data_only` topology banks
backed by read-only `$data_bank:bankN` allocator regions, never by invented 6507
addresses. The runtime register window is `$1000-$107F`, so the program banks map
only `$1080-$1FFF`. The Poly8 generator is hardware state: resetting the RNG sets
it to 1 and each DPC access clocks it before the addressed register operation.
The 255-byte image tail is therefore reference/format data, not CPU-mapped ROM.

Ordinary linker symbols remain 16-bit. Do not invent far pointers for this
family. Selector-controlled families, segmented-window families, direct islands,
and coprocessor formats are different hardware models and must not be forced into
an F8-shaped abstraction.

C26 topology/placement rules
----------------------------
* Cartridge **bank** topology and allocatable **mem** regions are separate
  namespaces and separate concepts. A bank describes an emitted/mapped hardware
  unit; `mem` describes bytes available to the allocator.
* Names such as `bank0` have no magic compiler meaning. Startup/home behavior
  comes from topology metadata, not spelling.
* Explicit source placement is a hard pin. Automatic placement may move ordinary
  CODE/RODATA only where topology and timing constraints permit it.
* Selector-free direct regions are ordinary 16-bit address spaces and do not
  require generated bank-switch trampolines.
* Selector-controlled cross-bank calls/jumps use generated transitions; preserve
  hardware-return-depth accounting and branch/page timing constraints. Mapper
  diagnostics must distinguish "every selector was touched" from exhaustive
  ordered source/destination bridge coverage. The durable regression is
  `test/vcs_bankswitching_call_matrix.pl`: one ROM per source bank calls every
  destination bank so every legal generated JSR/RTS pair is executed. The legacy JSR path emits one 15-byte replicated entry per unique source-bank/
  target-function pair, so target diversity consumes the common corridor. Migrated
  profiles use the fixed inline-target block instead; keep the legacy path only
  for mapper families/lower-level inputs not yet migrated.
* Split-address cartridge RAM keeps distinct read/write aliases. Do not collapse
  them into one address for RMW or initialization semantics.
* Mapper hotspots, vector bridges, RAM-port prefixes, signatures, and other
  nonallocatable holes are not ordinary ROM placement space.
* `$data_only` banks have file identity and size but no CPU/link address, selector,
  or startup state. Their `$data_bank:NAME` read-only `mem` regions allocate in
  bank-local file-offset space; code and ordinary 6507 relocations into them are
  errors.

Mapper signature convention
---------------------------
Public VCSC cartridge profiles reserve four bytes at logical `$xFF8-$xFFB` in
the final CPU-mapped program bank. This normally is the final file chunk; DPC is
the exception because its data-only chunks follow the program ROM. Short
signatures are padded with ASCII NUL, never space or underscore. Current
signatures include:

    4KSC  F8\0\0  F8SC  F6\0\0  F6SC  F4\0\0  F4SC  FA\0\0
    CV\0\0  OMNI  JANE  0840  UA\0\0  UASW  0FA0  E0\0\0  FE\0\0  WD\0\0  DPC\0  FA2\0  3F\0\0  3E\0\0

The bytes are metadata; real hardware switches because the hotspot address is
accessed, not because of the stored byte value.

Open work
---------
Generic inline-target cross-bank JSR contract
---------------------------------------------
The F8/F6/F4(+SC), FA, DPC, FA2, JANE, and 0840 profiles use the compact generic call path only when
the cartridge declares `$inline_bankcall`; the stock profiles expose this via
`VCSC_INLINE_BANKCALL`. Unmigrated profiles remain on the legacy bridge ABI. Explicitly bank-pinned
cross-bank C calls emit a five-byte `JSR` + `.banktarget target` bundle. The
linker redirects the JSR to one fixed mapper-specific replicated entry/return
block; these calls consume no legacy per-target 15-byte JSR entries. F8/F8SC/F6/F6SC/F4/F4SC/FA/DPC each carry an identical mapper-local `inline_bankcall.s26`; the linker builds the shared template from the F8 copy and regressions prevent drift. Existing legacy bridge support remains available for mapper
families not yet migrated and for lower-level object/S26 inputs.

The entry reads the inline logical target before switching banks, advances the
original stacked JSR return PC by two with full 16-bit carry propagation, and
uses an internal JSR to create the synthetic return. The callee ends with normal
RTS. The generic return preserves A:X, derives the source selector from the
unchanged original 16-bit logical return PC, restores that bank, and RTSes
directly to the logical continuation; do not rewrite the saved PC to `$Fxxx`.
Distinct logical ORGs encode bank identity even though the cartridge bus mirrors
the high address bits. Nested calls therefore compose naturally in LIFO order.

A call bundle may cross an ordinary 256-byte page. `(ptr),Y` target fetches and
stacked-PC adjustment are carry-correct. The five-byte bundle remains inside one
indivisible function layout and therefore cannot spill across a bank allocation
boundary. `test/vcs_bankswitching_inline_call_pages.pl` locks an ordinary bundle,
both page-edge forms, an exact fit against the end of allocatable bank ROM, and
rejection one byte later; it also checks exact continuation and A:X preservation.
The public `examples/09_bankswitching/01_f864` executes every ordered JSR
and JMP source/destination pair for F8/F6/F4(+SC) from every physical start bank,
with zero legacy JSR entries. `03_fa_ram_plus` uses the same mechanism for all
six ordered FA call pairs while preserving its complete 256-byte RAM test.
`test/vcs_bankswitching_call_matrix.pl` independently executes all ordered pairs
and keeps not-yet-migrated families on the legacy path.

`.banktarget` uses a relocation marker combination that cannot be confused with
an actual indirect JMP; NMOS indirect-JMP page-wrap validation remains independent.
The fixed generic block, not the old 224-byte corridor size, is the durable JSR
ABI. Cross-bank JMPs remain a separate per-target mechanism for now.

Done: F8/F8SC, F6/F6SC, F4/F4SC, FA, DPC, FA2-24/28, JANE, and 0840.
F8-family/FA/DPC use the shared 80-byte geometry. FA2 is 83/84 bytes
(`generic-jsr=$054`); JANE is 95/96 (`$060`) with bank1 startup and selectors
0,1,8,9. 0840 is 75/80 (`$050`): PC bank identity becomes Y=$00/$40 and
`LDA $0800,Y` performs the read-only selector access. Migrated profiles have
zero legacy JSR entries; public diagnostics use complete ordered call matrices.
[ ] UA/UASW -- next, together; same two-bank read-hotspot mechanism with swapped mapping.
[ ] 0FA0 -- last existing migration; same read-hotspot class with its masked aliases.
Do not force FE, E0, 3F, 3E, WD, OMNI, CV, or 4KSC through this migration:
their latch/window/direct-memory contracts either need mapper-specific calls or no
cross-bank call trampoline at all. After the queue is green, implement FC then F0
using the inline-target ABI from the start rather than creating new legacy debt.

Diagnostic optimizer wart: F864 direct-JMP targets use inline `TSX/STX`, so the
current whole-function asm safety rule can leave generated
`BNE near / JMP false / near: JMP true`. Pure C26 should not normally see it;
this is future optimizer-locality cleanup, not bankswitching work.

[ ] 38. Complete the remaining mapper tier in this order: **FC, F0**.

        FA2 is complete. Keep treating each remaining mapper as its own hardware
        contract rather than forcing new mechanisms into an F8-shaped abstraction.

        [ ] 38b. FC -- do this next.

            FC is now considered straightforward rather than risky. Current
            Stella FC is a staged direct selector, not an F0-style incrementing
            mapper: write the low target-bank bits at $1FF8, write the upper
            target-bank bits at $1FF9, then access $1FFC to commit the selection.
            Because the target bank is explicitly chosen before the commit, a
            normal replicated cross-bank transition corridor should be simple.
            Preserve FC's exact image topology, simulator/disassembler round
            trip, and a Stella-visible diagnostic; do not change existing mapper
            implementations merely to generalize the FC mechanism.

        [ ] 38c. F0 -- do this after FC.

            F0 is mechanically simple but less attractive for new VCSC code:
            its 16 x 4K / 64K capacity is selected by repeatedly advancing the
            bank through the $1FF0 hotspot instead of directly selecting an
            arbitrary bank. Basic profile/linker/simulator/disassembler support
            and a diagnostic are worthwhile for compatibility and for exercising
            a stateful/incremental mapper.

            Use the shared inline-target JSR design above; no ROM bank-identity
            byte is needed. At entry, the stacked logical caller PC identifies the
            source bank and the inline logical target identifies the destination,
            so the trampoline computes `(target - source) mod 16` and advances
            through $1FF0 exactly that many times before entering the callee.

            F0 cannot directly select the source bank on return, so preserve the
            reverse advance count as call-frame metadata rather than rediscovering
            mapper state. A simple implementation may push the one-byte count
            `(source - target) mod 16` beneath the synthetic `__bankreturn` address;
            nested calls then naturally carry independent reverse counts in LIFO
            order. After the callee's RTS consumes the synthetic return,
            `__bankreturn` recovers that count, advances $1FF0 exactly that many
            times, preserves/restores A:X, and performs the final RTS to the
            unchanged original logical caller PC. Account for the extra F0 frame
            byte explicitly if this implementation is chosen.

            The repeated hotspot accesses may be unrolled or driven by a small
            counter loop; choose the smaller/timing-appropriate form when
            implementing it. All code executed across a bank change must remain
            byte-identical at the same CPU addresses in every bank. Manual code
            that changes F0 banks behind the compiler's back is responsible for
            preserving its own mapper state. Do not alter existing mapper
            implementations for this F0-specific mechanism.
