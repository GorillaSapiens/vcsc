VCSC RIOT RAM OPTIMIZATION ROADMAP
=================================

Purpose
-------
This document records the RAM problems exposed by the animated-sprite gallery
and turns them into an ordered compiler/runtime/renderer roadmap. The gallery is
a useful stress case, but the goal is not to special-case one example. The first
priority is to stop the compiler and linker from reserving static scratch whose
lifetimes do not overlap. Renderer capability must not be removed merely to hide
compiler waste.

This is a focused roadmap. `.../roadmap.txt` remains the main project roadmap.
The items below should be selected explicitly when RAM optimization becomes the
active workstream.

Guiding rules
-------------
* Measure every change from linker maps and emulator-backed frame tests.
* Distinguish persistent application state, renderer-owned state, expression
  scratch, activation storage, and hardware-return-stack reservation.
* Prefer whole-program lifetime reuse over hand-written assembly in examples.
* Public examples should contain little or no assembly; ordinary application logic
  must exercise the high-level language and drive compiler improvements.
* Do not remove Ball support from the existing player-color renderers merely to
  make this gallery fit. First complete the compiler scratch work and remeasure.
* Keep the 181-line and 192-line public renderer contracts stable unless a new
  renderer profile is deliberately introduced.
* Never trade a RAM reduction for unstable visible timing or an unprovable
  activation/stack overlap.

Measured animated-gallery baseline
----------------------------------
The source-derived-color animated gallery currently fills all 128 bytes of RIOT
RAM. The measured ownership is:

    VCSC runtime pointer/argument scratch                 8 bytes
    player_color_192 renderer                            69 bytes
      public renderer state                              13 bytes
      private workspace and object schedule              56 bytes
    mutable P0/P1 row-color tables                       16 bytes
    persistent animation/control state                    7 bytes
    main activation/expression scratch                   20 bytes
    hardware return-stack reservation                     8 bytes
                                                        --------
                                                         128 bytes

The 480-byte packed source-color table is ROM, not RAM. Only the selected P0 and
P1 eight-row color tables occupy RAM.

What `game_object_masks` is
---------------------------
`game_object_masks` is not the playfield. The gallery's 48-byte playfield is
already immutable ROM data.

The renderer's `game_object_masks[48]` is a writable, frame-rebuilt vertical
object schedule and preparation workspace. Its layout is sparse and driven by
visible-loop timing:

* The twelve bytes at offsets 0, 4, 8, ... 44 hold Ball enable bits for the
  renderer's twelve four-byte playfield rows / ninety-six two-scanline pairs.
* The remaining addresses are reused during VBLANK for P0/P1 height thresholds,
  range endpoints, loop limits, and mask-generation temporaries.
* During visible drawing, instructions such as

      lsr.zx game_object_masks,x

  destructively consume the Ball schedule while X simultaneously follows the
  four-byte playfield-row stride. The 48-byte shape is therefore partly a
  cycle-scheduling choice, not forty-eight independent pieces of game state.

The current array cannot simply be made `const` or moved to ROM: the renderer
writes it during VBLANK and shifts it in place during drawing. A different
representation or renderer schedule could reduce it, but that is a renderer
redesign and must be proven against the beam.

What the faithful legacy renderer proves
----------------------------------------
The retained faithful legacy player-color renderer supports arbitrary P0, P1,
and Ball Y positions and heights without `game_object_masks` or any equivalent
48-byte object schedule. During visible drawing it destructively counts the
three object Y values down, compares them directly with their heights, and emits
`GRP0`, `GRP1`, and `ENABL` from those live counters. It saves the public Y
values before drawing and restores them afterward.

That implementation uses unofficial `DCP` instructions and has other legacy
constraints, so it cannot simply replace the maintained official renderer.
Nevertheless, it proves that arbitrary P0/P1/Ball vertical positioning does not
inherently require a 48-byte RAM schedule. The maintained renderer's array is an
implementation choice, not a TIA requirement.

A serious redesign must therefore investigate an official-opcode direct-countdown
schedule before deleting Ball support. The result must preserve the maintained
renderer lifecycle, composable handoff, ROM playfield, per-row player colors,
legal-opcode contract, arbitrary object positions/heights, and exact beam timing.

Why `main` owns twenty scratch bytes
------------------------------------
The animated gallery's current `main` activation record includes approximately:

    vcs_ntsc_wait_scanlines parameter                     1 byte
    VSYNC expression scratch                              2 bytes
    pause-condition scratch                               1 byte
    first inlined next_pair expansion                     6 bytes
    control-expression scratch                            4 bytes
    second inlined next_pair expansion                    6 bytes
                                                        --------
                                                          20 bytes

None of those values is useful during the visible renderer. Most are dead after
one expression or one VSYNC/overscan path, but VCSC currently gives `main` one
static, non-returning activation record and does not overlay scratch whose
lifetimes occur at different points inside the function.

The worst symptom is that the two expansions of the same inline `next_pair()`
helper receive separate six-byte scratch groups even though those expansions
cannot execute simultaneously. Duplicating scratch groups for duplicated inline
functions has got to stop.

Why eight bytes are reserved for the hardware stack
----------------------------------------------------
The 6507 hardware return stack shares the physical RIOT $80-$FF RAM. The linker
therefore reserves real RAM for the deepest possible JSR chain.

The current player-color VBLANK path declares hidden assembly stack use and may
execute a chain equivalent to:

    runtime startup -> main -> prepare_object_masks -> prepare_one -> set_range

Four simultaneous return addresses require eight bytes. Most source helpers are
already inline; the remaining depth comes largely from handwritten renderer
assembly and the deliberately out-of-line `install_frames()` routine.

Inlining everything is not automatically correct. `install_frames()` is large
and called repeatedly; blindly duplicating it would waste ROM and may overflow
4K. Stack reduction must use measured whole-program inlining, helper flattening,
or renderer redesign only when the linked result improves.

Why `install_frames()` is full of assembly
------------------------------------------
`install_frames()` is not beam-critical renderer code. It runs during startup or
outside visible drawing and performs ordinary data work:

* choose one of the hard ROM pages for each player's bitmap;
* compute the selected frame offset;
* choose the packed row-color page;
* unpack two four-bit source palette indices from each byte;
* translate those indices through `pico8_tia_palette`;
* fill the two eight-byte mutable player-color tables; and
* install the two graphics pointers.

That work is written in assembly because the current compiler makes the obvious
high-level formulation too expensive. Dynamic pointer/page selection, pointer
arithmetic, indexed ROM loads, nibble extraction, and small loops currently
produce excessive generic expression scratch and/or larger code. The cartridge
was already close to both its 4K ROM and 128-byte RAM ceilings, so the example
used hand-written 6502 to control every byte. Keeping the routine out of line was
then necessary to avoid duplicating the large body at each call site.

This is an implementation failure, not a timing requirement. Examples exist to
show users how to write VCSC programs; ordinary startup, animation, table lookup,
and color-expansion logic should be VCSC source. Assembly in examples should be
reserved for genuinely cycle-exact TIA sequences, explicit hardware idioms not
yet expressible by the language, or narrowly documented compiler gaps that have
an associated roadmap item and regression.

Ordered roadmap
---------------

[x] 0. Add authoritative RAM-accounting fixtures before optimizing.

    * Build the animated gallery and retain a machine-readable symbol/segment
      accounting report that classifies every byte as persistent state,
      renderer state, activation scratch, runtime scratch, or hardware stack.
    * Pin the current 128-byte baseline and the twenty-byte `main` activation
      breakdown so later reductions are measurable rather than anecdotal.
    * Add diagnostics capable of explaining why two scratch objects cannot
      overlap and why each hardware-stack depth edge exists.
    * Keep exact 262-line frame, sprite, source-derived row-color, control, and
      animation-sequence emulator oracles active throughout this roadmap.

    Completed baseline:

    * `test/fixtures/vcs_animated_gallery_ram_accounting/golden.json` is the
      canonical machine-readable 128-byte report. It classifies every physical
      address from `$80` through `$FF`, including the renderer's 13 public bytes,
      56 private bytes, sixteen mutable row-color bytes, seven gallery-state
      bytes, twenty activation bytes, eight runtime bytes, and eight stack bytes.
    * Compiler `-X scratch` reports each fixed scratch slot's expansion scope,
      activation owner, size, and the current
      `no-intra-function-lifetime-overlay` reason. The fixture pins both
      sequential `next_pair()` expansions as separate six-byte groups.
    * Linker maps now list compiled call-graph edges, their source/bridge stack
      slots, one deterministic deepest weighted path, each object-level
      `.callstackextra` contribution, and the reconciled source/hidden/total
      hardware-stack bytes.
    * `test/vcs_animated_gallery_ram_accounting.pl` regenerates and compares the
      report while the independent animation emulator remains the pixel, color,
      control, sequence, and exact-frame oracle. No allocation or cartridge bytes
      changed in this item.

[x] 1. Add lifetime overlay between separate expressions inside one function.

    This is the highest-priority compiler optimization and is expected to yield
    broad savings well beyond the gallery.

    * Compute scratch liveness across the function control-flow graph instead of
      assigning every expression a permanent disjoint region in the function's
      static activation.
    * Allow non-overlapping expression temporaries to occupy the same bytes even
      when they occur in different statements, branches, loop phases, or frame
      phases.
    * Retain a scratch lease until the expression's final copy-out or side effect
      is complete; never reuse storage merely because code generation for one
      subtree has returned.
    * Handle joins conservatively: objects live on either predecessor remain live
      at the join until proven dead. Loops require fixed-point liveness rather
      than source-order assumptions.
    * Preserve address-taken, inline-assembly-referenced, volatile hardware, and
      ABI-visible objects. Only compiler-owned temporary storage is eligible.
    * Emit map/debug information showing lifetime groups and overlaid offsets.

    Acceptance criteria:

    * Sequential expressions of equal or different sizes reuse the same maximal
      scratch region when their lifetimes do not overlap.
    * Mutually exclusive branches reuse scratch safely.
    * Nested expressions and loop-carried values do not alias prematurely.
    * Existing task-15e nesting-depth/LIFO guarantees remain intact.
    * The gallery's VSYNC, control, and animation expressions no longer reserve
      disjoint bytes merely because they appear in one non-returning `main`.

    Completed implementation:

    * Scratch pools are now keyed by runtime activation owner rather than by each
      textual compiler context. Inline expansions inherit the caller's owner, so
      separate statements, branches, loops, and frame phases reuse the same
      active-lease depth slots.
    * Compiler-owned scratch cannot be named, addressed, declared volatile, or
      referenced by inline assembly. Its structured lease remains active through
      final copy-out/side effect, so no scratch value can survive a statement
      join or loop back-edge; nested live leases still consume deeper slots.
    * `-X scratch` now reports each scope's shared lifetime group, symbol, size,
      and acquisition count. The linker map supplies the final overlaid address.
    * `scratch_lifetime_overlay.pl` executes sequential, branch, loop, three-call
      inline, and nested-inline cases in `vcsc-sim`. The complete compile-only
      suite retains the existing LIFO/nesting regressions.
    * The gallery activation fell from 20 bytes to 7: one inline parameter plus
      two three-byte lifetime groups. Total RAM fell from 128/128 to 115/128,
      leaving 13 bytes free, with the renderer, persistent state, and eight-byte
      hardware-stack reservation unchanged.
    * The compiler does not need a general named-object CFG dataflow pass for
      this class of storage: compiler-owned scratch is non-addressable and its
      structured lease encloses final copy-out/side effects. Activation-wide
      depth coloring is therefore the liveness result for these temporaries;
      ordinary locals and ABI-visible objects remain outside this optimization.
    * All 438 compile-only tests and all 253 end-to-end tests pass. The slow
      40-cartridge composition oracle also exposed and fixed a test-harness bug:
      SWCHA/SWCHB now default to released inputs, so line timing is independent
      of reset-startup BSS clearing cost.

[x] 2. Stop duplicating scratch groups for repeated expansions of one inline
        function.

    * Model each inline expansion's compiler-owned temporaries by lifetime and
      call-site reachability, not by assigning a permanent new group per textual
      expansion.
    * Reuse one scratch footprint for repeated inline calls when the expansions
      cannot be active simultaneously.
    * Support repeated expansions in separate branches, before/after loops, and
      from different callers whose activations already overlay.
    * Do not merge persistent inline-local objects whose source semantics require
      distinct storage. This item concerns expression/call scratch, not ordinary
      static locals.
    * Detect nested inline expansion correctly. A caller expansion and a callee
      expansion that are simultaneously live still require distinct storage.

    Acceptance criteria:

    * The two current `next_pair()` expansions share one scratch group instead of
      consuming six bytes each.
    * Adding a third sequential `next_pair()` call does not grow BSS scratch.
    * A deliberately nested inline case still receives enough non-overlapping
      storage.
    * Generated code and emulator behavior remain unchanged except for addresses
      and reduced RAM ownership.

    Completed as a direct consequence of item 1's activation-owner lifetime
    coloring:

    * Both gallery `next_pair()` expansions use `main:0` and `main:1`, one
      six-byte physical footprint instead of twelve bytes.
    * The dedicated regression adds a third sequential inline expansion without
      growing BSS and retains four deeper slots for a deliberately nested inline
      expression whose leases overlap.
    * Persistent inline parameters, locals, and return objects remain distinct;
      only compiler-owned scratch participates in lifetime coloring.

[x] 3. Improve compact lowering for simple byte state updates.

    The gallery currently routes operations such as `sprite0 += 2`,
    `sprite1 := sprite0 + 1`, increments, masks, and constant comparisons through
    generic multi-byte expression machinery in places where direct byte
    instructions are sufficient.

    * Extend the direct uint8_t assignment/update paths for constant add/subtract,
      increment/decrement, mask/test, compare, and copy-plus-constant forms.
    * Avoid generic pointer-width or three-byte temporary sequences for byte
      lvalues whose width and address are known.
    * Fold simple post-update comparisons where doing so is smaller and preserves
      source evaluation semantics.
    * Add exact assembly and zero/additional-scratch regressions.

    Completed:

    * Ordinary directly addressable `uint8_t` lvalues now lower constant `+=`,
      `-=`, `&=`, `|=`, and `^=` updates directly. Unit increments/decrements use
      `INC`/`DEC`; other add/subtract forms use one load, carry setup, immediate
      arithmetic, and one store. Absolute external bindings retain required
      read/write side effects rather than being treated as ordinary RAM.
    * `dst := src + constant`, `dst := src - constant`, commuted constant-plus-
      source, byte logical-not assignment, truth tests, constant-mask tests, and
      constant comparisons use direct byte loads/branches without generic
      pointer-width or three-byte expression groups. Comparisons immediately
      following updates therefore compile as direct reload/compare branches; no
      speculative cross-statement register state is assumed.
    * `direct_u8_state_update_codegen_test.c26` locks the exact documented-opcode
      sequences and forbids both expression-scratch symbols and Y setup.
      `e2e_direct_u8_state_update_verify.c26` executes wraparound arithmetic,
      masks, copy-plus-constant, truth, comparison, and logical-not behavior in
      `vcsc-sim`. Existing absolute-ref and packed-BCD regressions remain active.
    * The animated gallery's `main` activation fell from seven bytes to two: one
      scheduler inline parameter plus one one-byte VSYNC scratch slot. Both
      `next_pair()` expansions now allocate zero expression scratch. Total RIOT
      RAM fell from 115 to 110 bytes, free RAM rose from 13 to 18 bytes, and ROM
      fell from 3993 to 3662 bytes. The authoritative accounting fixture is now
      schema 3 and records the five-byte RAM and 331-byte ROM item-3 deltas.
    * Compact lowering exposed an accidental timing dependency in the shared
      frame helpers: the old generic byte loop happened to spend nineteen extra
      cycles after its final WSYNC. The first item-3 pass incorrectly changed
      phase fixtures to bless that shift, and the public basic score, fingerprint,
      and wide-score cartridges regressed on real Stella output. The correction
      restores the established cycle-3 visible-component entry with an explicit
      calibrated tail in `vcs_ntsc_wait_component_scanlines()` and adds
      `vcs_ntsc_wait_visible_tail_scanlines()` for a final blank visible gap before
      overscan. Generic `vcs_ntsc_wait_scanlines()` keeps the compact lowering and
      deliberately has no return-cycle contract.
    * The original exact phase and reviewed Stella raster oracles are retained;
      optimizer-induced beam shifts are fixed in the helper rather than accepted
      by moving the oracle. Gallery accounting remains 110/128 RAM and 3662/4090
      ROM because the gallery does not use these score-gap helpers.
    * Final verification: 439 compile-only tests and 254 end-to-end tests pass.

[x] 4. Make `install_frames()` ordinary VCSC and establish a minimal-assembly
        example policy.

    * Express bitmap-page selection, frame-offset calculation, packed color
      lookup, nibble extraction, palette translation, color-table expansion,
      and graphics-pointer installation in the high-level language.
    * Add or improve compiler lowering for the exact missing pieces rather than
      hiding them in one example: efficient ROM pointer selection, pointer-plus-
      byte-offset arithmetic, indexed const loads, direct nibble extraction,
      compact counted loops, and byte-array stores.
    * Combine this work with items 1-3 so the high-level implementation does not
      consume more activation scratch than the hand-written routine.
    * Keep `install_frames()` out of line unless whole-program measurement proves
      inlining wins. High-level source does not imply textual duplication.
    * Audit all public examples. Assembly should be absent unless it is genuinely
      beam-critical, a direct hardware idiom, or a documented language/compiler
      limitation with a focused test and roadmap entry.
    * Add an example-source assembly inventory/allowlist so ordinary application
      logic cannot quietly migrate back into large `asm` blocks.

    Acceptance criteria:

    * The animated gallery contains no assembly in `install_frames()`.
    * Generated behavior, all source bitmap/color hashes, controls, and exact
      262-line frames remain unchanged.
    * Final linked ROM fits the supported cartridge profile and activation RAM is
      no larger than the assembly version after items 1-3.
    * The source is readable as an example of VCSC table and pointer operations,
      not as a disguised assembly program.

    Completed implementation:

    * `install_frames()` is now ordinary VCSC. Page selection, byte-pointer offsets,
      packed color extraction, palette translation, color expansion, and graphics
      pointer installation are expressed directly in the high-level source. The
      adjacent animation-phase table update is high-level VCSC as well.
    * The compiler gained reusable compact lowering for array-to-pointer decay,
      pointer-plus-byte offsets, indexed one-byte ROM/pointer loads, constant byte
      masks/shifts, indexed byte-array stores, and a narrowly proven X-backed
      unsigned-byte counted loop. A separate fallback regression requires unsafe
      indirect-store loop bodies to retain a materialized local.
    * The animation emulator still verifies every source bitmap/color hash, all 120
      source frames, the modulo-3 special set, controls, palette expansion, installed
      pointer pairs, and exact 262-line frames.
    * Activation RAM is unchanged at 110/128 bytes with 18 bytes free and zero
      `install_frames()` activation bytes. After the compiler/assembler addressing-mode
      handoff below, ordinary ROM is 3854/4090 bytes with 236 bytes free: 192 bytes
      more than the 3662-byte hand-written-assembly baseline. `install_frames()` is
      now 462 final linked bytes versus 236 hand-written bytes. A measured optimizer
      follow-up immediately below separates compiler output, peephole behavior,
      assembler relaxation, and the remaining code-size work.
    * `test/example_assembly_allowlist.pl` pins all remaining public-example assembly
      by source, normalized-statement hash, policy category, and focused regression.
      Ordinary application assembly that still reflects compiler/language limitations
      is recorded in the named follow-up below rather than silently grandfathered.
    * An attempted shorter ordinary byte-comparison branch form was rejected after an
      exact renderer regression showed scheduler-owned VBLANK work moving by one
      scanline. Compact counted loops keep their proven branch form, while ordinary
      comparisons retain the established control-flow shape.
    * The smaller surrounding application can move the standard renderer component by
      whole pages. Its documented absolute pages are observations rather than ABI; the
      static regression now enforces page alignment, relative code/RODATA placement,
      and exact phase/raster behavior rather than stale `$F300/$F600` addresses.
    * Verification before the addressing-mode follow-up: 442 compile-only tests and
      255 end-to-end tests passed. The follow-up below carries its own expanded gates.

[ ] 4a. Recover high-level frame-installation ROM through the existing optimizer
         pipeline instead of accepting the pre-audit 540-byte routine as normal compiler cost.

    Measured baseline and attribution:

    * The pre-high-level implementation links `install_frames()` at `$00EC` = 236
      bytes. Before the addressing-mode audit, the high-level implementation linked
      at `$021C` = 540 bytes; it now links at `$01CE` = 462 bytes.
    * Before and after the addressing-mode handoff, `-fpeephole` and
      `-fno-peephole` produce byte-for-byte identical `install_frames()` bodies.
      The old linked span was 540 bytes and the current span is 462 bytes. The
      existing peephole pass saves eight bytes elsewhere in the complete gallery
      (currently 3854 versus 3862 ROM bytes), but still saves zero bytes in this routine.
    * The assembler already performs zero-page-family relaxation, but the compiler
      forces `.a`/`.ax` on 78 otherwise relaxable RAM accesses in this function. In
      an analysis-only assembly copy, removing only those forced absolute-family
      suffixes lets the existing assembler reduce the function from 540 to 462
      bytes: exactly 78 bytes saved. Fix the compiler/assembler handoff rather than
      adding a second addressing-mode optimizer.

    Completed compiler/assembler addressing-mode handoff:

    * Audited all compiler mnemonic emitters, not just the frame installer. The
      pre-change compiler source contained 87 ordinary addressing-mode suffix
      occurrences (75 in `compile_expr_flow.c`, 12 in `compile_lvalue.c`); it now
      contains zero. Compiler-lowered direct/indexed/indirect RAM references are
      unsuffixed and the assembler owns mode selection/relaxation. Explicit source
      `asm` suffixes remain untouched for programmers who need exact encoding/timing.
    * Split-address and non-zero-page regions remain safe through the existing
      `.segmentaddrsize ..., absolute` contract; the split-memory execution suite
      passes without per-instruction forced absolute modes. A compiler-policy test
      now rejects reintroduction of ordinary forced mode suffixes, and a codegen test
      proves that explicit handwritten `.a` requests survive unchanged.
    * This broad handoff realizes the analysis exactly inside `install_frames()`:
      `$021C` = 540 bytes becomes `$01CE` = 462 bytes, with zero RAM change. The full
      animated gallery falls from 3969 to 3854 ROM bytes (115 bytes recovered) while
      remaining 110/128 RAM bytes with 18 free. With `-fno-peephole` it is 3862 bytes,
      and `install_frames()` remains 462 bytes, so the existing peephole still saves
      eight bytes elsewhere and zero bytes in this routine.
    * Shorter compiler-owned zero-page accesses exposed several old beam-phase
      dependencies. They were not "fixed" by putting forced modes back in codegen.
      Cycle intent now lives where it belongs: calibrated frame helpers carry explicit
      delay instructions, the cycle-counted six-glyph row initialization is handwritten
      `sta.a`, and synthetic fixtures that deliberately use the uncalibrated generic
      wait add an explicit phase-normalizing NOP. Exact scheduler/raster oracles pass.
    * Verification after the handoff: 444 compile-only tests pass; all 255 end-to-end
      cases pass in bounded batches, including split-memory execution, exact scheduler
      phases, score/component rasters, official/unofficial renderer equivalence, banked
      renderer raster identity, and clean source-tree hygiene.
    * Ten generated conditional-branch-plus-`JMP` pairs are locally reducible to
      inverted bare branches. Applying only that rewrite after addressing-mode
      relaxation reduces 462 to 432 bytes, exactly 30 more bytes. This rewrite must
      be restricted to code whose cycle shape is not contractual; previous global
      comparison shortening moved VBLANK work by a scanline.
    * All six frame/color source arrays are hard page-contained and link on `$xx00`
      boundaries. Twelve generated page-base assignments unnecessarily materialize
      a zero low byte, and ten generic byte-pointer additions carry machinery even
      though the masked/shifted offsets provably stay within the selected page. An
      analysis-only page-aware rewrite reduces 432 to 326 bytes, exactly 106 more
      bytes, without relying on final accidental addresses.

    Exact final-linked section comparison:

        section                         high-level   after measured local rewrites   hand-written
        P0 packed-color setup               73                 37                       35
        P0 color expansion loop             43                 41                       38
        P0 bitmap setup                    121                 65                       38
        P1 packed-color setup              105                 56                       48
        P1 color expansion loop             43                 41                       38
        P1 bitmap setup                    154                 85                       38
        RTS                                  1                  1                        1
        total                              540                326                      236

    The remaining net 90-byte difference is also accounted for by concrete
    emitted patterns rather than an unexplained compiler tax:

    * Tail-merge identical pointer-high stores after page selection: 16 bytes.
    * Tail-merge the common shifted-frame/low-byte update after the P1 three-frame
      packed-color conditional: 6 bytes.
    * Preserve the already-loaded sprite value through the two additional compares
      in each four-page selection chain instead of reloading it: 8 bytes.
    * Reuse the packed-color pointer low byte for bitmap selection by doubling it,
      as the proven hand-written routine does, instead of reconstructing the bitmap
      offset after the color-expansion loop: 17 bytes for P0 and 37 bytes for P1,
      54 bytes total. The larger P1 saving comes from avoiding a second copy of the
      three-frame phase conditional.
    * The two statically nonempty `0,2,4,6` color loops each contain five bytes of
      control-flow overhead relative to the hand-written post-tested loop shape: 10
      removable bytes total. The analysis form is already two bytes smaller per loop
      because its color stores can relax to zero-page indexed while the hand-written
      reference explicitly forced `.ax`; that four-byte advantage makes the loop
      sections only three bytes larger each in the table above.

    Thus the named remaining waste is 94 bytes, offset by four bytes that the relaxed
    high-level form already does better than the 236-byte hand-written reference. If
    all named patterns are removed while retaining those safe zero-page indexed color
    stores, the measured path projects to 232 bytes rather than merely matching 236.

    Implementation direction:

    * Extend the existing peephole pass for generated branch/`JMP` inversion,
      duplicate load/store elimination across safe local control-flow joins, common
      suffix/tail merging, and other register-value round trips that the current
      emitted patterns expose. Add pattern-level and source-level on/off regressions
      for every new rewrite kind.
    * Do not use peephole text matching to rediscover semantic facts the compiler
      already owns. Emit relaxable direct RAM operands when the default writable
      segment carries a zero-page address-size contract; propagate hard `page`
      alignment and masked-offset range facts to pointer lowering so page-low and
      impossible-carry work disappears before assembly.
    * Treat reuse of the packed-color offset across the expansion loop as an IR/source
      value-lifetime problem, not a two-line peephole. Preserve zero activation RAM;
      do not materialize a byte merely to make common-subexpression reuse easy.
    * Preserve cycle-sensitive renderer/scheduler behavior. Size-changing control-flow
      rewrites need an explicit timing-safe scope or equivalent proof; passing the
      exact renderer phase/raster oracles is mandatory.

    Acceptance criteria:

    * [x] Replace the hard-coded "540-byte high-level cost" assumption with
      measurement from the final linked map and record peephole-on/off and
      addressing-relaxation deltas.
    * [x] Recover the mechanically proven 78-byte `install_frames()` addressing-mode
      loss by removing unnecessary forced modes throughout compiler lowering without
      weakening split-memory or timing contracts.
    * [ ] Recover the measured 30-byte ordinary branch-scaffolding loss, then
      implement the page-aware pointer reductions without introducing RAM or weakening
      page/timing contracts.
    * Continue toward or below the measured 236-byte hand-written reference by
      eliminating the remaining named patterns; the current accounting projects 232
      bytes if the safe zero-page indexed color-store advantage is retained. Any
      residual difference must be individually explained in bytes.
    * Keep the gallery at or below 110 RAM bytes and preserve all animation, exact
      262-line, raster, and complete compile/e2e regressions.

[ ] 5. Overlay scratch across frame phases when contracts prove the lifetimes do
        not overlap.

    * Describe VSYNC, VBLANK, visible draw, and overscan ownership for reusable
      renderer/application workspaces.
    * Allow application/compiler scratch used only after `game_draw()` to overlay
      renderer preparation storage that is provably dead after visible drawing,
      and vice versa.
    * Do not overlay persistent renderer inputs needed by the next frame or state
      restored during `game_overscan()`.
    * Prefer compiler/linker metadata over example-specific absolute aliases.
    * Add negative tests for phase objects whose lifetimes really do overlap.

[ ] 6. Reduce the gallery's persistent bookkeeping without changing behavior.

Expected direction
------------------
The twenty-byte `main` activation is mostly static-lifetime waste, not a visible
renderer requirement. Lifetime overlay between separate expressions and shared
scratch for repeated inline expansions should be completed before deciding that
Ball support must be removed. Those compiler changes are likely to benefit many
VCSC programs, especially non-returning frame loops, and may make the existing
three-object renderer entirely practical for this gallery.

The faithful legacy renderer proves that arbitrary P0/P1/Ball vertical motion can
also be implemented without a 48-byte object schedule. An official-opcode direct-
countdown redesign should therefore be attempted before deleting Ball support.

The animated gallery's ordinary data-selection and color-expansion code should
also return to high-level VCSC once compiler lowering and scratch allocation make
that practical. A compiler project whose examples become assembly programs has
missed the point.

A two-sprite-only renderer can still be valuable as an intentional low-RAM
profile, but it should be justified as a reusable capability choice after the
compiler stops wasting scratch and after direct countdown is measured—not used
as camouflage for either problem.
