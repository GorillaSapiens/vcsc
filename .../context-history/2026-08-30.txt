2026-08-30 15:29:33 PDT, clarify FC and F0 mapper plans
The remaining mapper order stays FA2, FC, then F0. FC is no longer considered
a concerning/stateful mapper: current Stella FC uses staged direct selection,
with target-bank bits written through $1FF8/$1FF9 and an access to $1FFC
committing the switch, so a normal replicated cross-bank transition corridor
should be straightforward. Do not alter existing mapper implementations merely
to generalize FC. For F0, preserve the increment-only $1FF0 hardware contract
and reserve a unique bank-ID byte at the same CPU address in every bank. A
replicated F0 trampoline can advance until the ID matches the destination bank;
the return corridor can similarly advance until the original/source bank ID is
seen before its final RTS. The ID/search mechanism is specifically an F0 design,
not a retrofit for existing direct-selector mappers.

2026-08-30 15:34:04 PDT, simplify planned F0 trampoline
Superseded the proposed per-bank identity byte. For compiler/linker-generated
F0 cross-bank transitions the linker already knows both source and target banks,
so it can compute the exact sequential-bank advance count at link time. Entry
uses `(target - source) mod 16` accesses to $1FF0; the return corridor uses
`(source - target) mod 16` accesses before its final RTS. The repeated accesses
may be unrolled or implemented as a small counter loop inside the byte-identical
replicated corridor, whichever is smaller/timing-appropriate. Manual code that
changes F0 banks behind the compiler's back owns its mapper state. Existing
mapper implementations remain unchanged.

2026-08-30 17:17:50 PDT, cross-bank JSR redesign candidates
The existing ordinary selector-controlled cross-bank JSR scheme is now explicit
design debt: each unique `(source bank, target function)` owns a 15-byte entry in
the byte-identical common corridor. The call site is compact, but target diversity
consumes replicated corridor capacity; the target word is already stored inline
inside each generated entry.

Recorded two replacement candidates in `bankswitching.txt` without implementing
either yet. Candidate A loads the target's 16-bit logical address into A:X then
calls one generic source-bank trampoline; the logical address encodes both target
bank and offset, giving a roughly seven-byte call site and fixed trampoline cost.
Candidate B emits `JSR __bankcall_from_SOURCE` immediately followed by `.word foo`.
Since NMOS 6502 JSR pushes the address of its own final operand byte, the trampoline
can inspect the stacked return address while the source bank is still selected,
read the next two bytes as the target logical address, add two to the stacked return
address so the final RTS skips the inline word, then use the normal synthetic-return
source-restore mechanism before switching and indirect-JMPing to the target. This
reduces the call site to five bytes and removes per-target corridor entries, at the
cost of extra trampoline cycles/code, stack-return manipulation, scratch pointer
state, and debugger/disassembler awareness of inline data. Preserve nested calls,
hardware-stack accounting, ordinary callee RTS, A:X return values, and exhaustive
ordered-pair coverage whichever design wins. Cross-bank JMP density is a separate
question. Mapper order remains FC then F0.

2026-08-30 17:35:12 PDT, choose inline-word bank calls
Selected the five-byte `JSR __bankcall` + inline `.word target` representation as
VCSC's planned replacement for per-target 15-byte cross-bank JSR bridges. The
seven-byte A:X-target form remains rejected rationale only.

Corrected the return-side model: the 6507 keeps a 16-bit PC even though only 13
address lines reach the cartridge, so the original stacked logical caller PC
already encodes the source bank through VCSC's distinct bank ORGs. A generic
`__bankreturn` should peek that unchanged PC, select its bank, preserve A:X, and
RTS directly to it; do not rewrite it to `$Fxxx` or any invented physical PC.
For F0, entry can compute the forward increment count from source/target and carry
the reverse count as per-call stack metadata beneath the synthetic return, avoiding
both a ROM identity byte and runtime bank discovery.
