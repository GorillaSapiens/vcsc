Resumed the live stripes=1 192-line all-five prototype and did instruction-level
cycle accounting of the positive-stripe paths. The ordinary steady P1/P0 body is
already exactly 152 CPU cycles, so it is not the source of the progressive phase
drift. The inherited packed-playfield row-transition path is 324 cycles from the
failed steady-loop branch through the resume jump, versus a 304-cycle four-line
budget: exactly 20 cycles too long per transition. There are eleven such
transitions in a 12-row 192-line frame, explaining 220 of the previously measured
225 excess draw cycles; only about five cycles remain in entry/terminal handling.

This changes the implementation direction. `stripes=1` has constant playfield data
across the whole visible region, so carrying the old packed-playfield row-transition
machinery into positive-stripe mode is needless work. The next implementation
should make row boundaries only roll the BL/M1/M0 mask source. A promising exact
budget is to keep X as the mask-row offset and remove the per-pair X countdown: an
unrolled eight-pair row changes the three scalar 5-cycle mask shifts into three
6-cycle indexed shifts (+3) but removes DEX/BNE (-5), saving two cycles per pair.
Across eight pairs that yields the exact 16-cycle budget needed for TXA/CLC/ADC
#4/TAX plus a zero-page row-count DEC/BNE. This also removes the scalar mask reload
and row-offset save/restore that currently dominate the bad transition. Do not
generalize to N>1 until this mask-row-only schedule is implemented and traced.
