2026-10-06 13:28:21 PDT, fold const element reads into link-time tables

Landed stripes item 0.  The generic positive-stripe emit was blocked on the
pair-indexed feed's ORIGIN, and this removes that block.  A file-scope `const`
object whose initializer is entirely constant is now folded at link time, and its
bytes are then readable as a constant expression, so a table DERIVED from another
table's element reads is itself link-time data.  That is exactly the shape the
renderer needs: its three pair-indexed feed tables are the logical eight-byte
stripe record transposed, so the public eight-byte authoring form is now the only
thing a program has to supply.  No RAM, no startup copy, no per-count data.

The change is small and localized.  emit_global_initializer optionally hands back
the bytes it built, compile_toplevel records them for a file-scope `const` object,
and eval_constant_initializer_expr_resolved folds a single-subscript read of such a
table.  Folding inside the evaluator rather than as a special case in the
initializer walk is what makes `record[2]+1` and `2*record[4]` fold too, which is
how a transposition is written rather than raw bytes.

Deliberately byte-granular.  A wider element type would need its own decode and
sign handling to yield a value rather than a byte, and nothing needs that yet, so
such a table is simply not recorded and keeps today's runtime-read behaviour.
An out-of-range read is refused with a located diagnostic instead of folding to an
adjacent byte, because a constant expression has no runtime bounds check left to
defer to; the regression pins both that refusal and its in-range neighbour so the
bound cannot be satisfied by refusing everything.

`direct_declarator '[' INTEGER ']'` is now `direct_declarator '['
conditional_expr ']'`, so an array extent is a compile-time integer constant
rather than a bare token: `WIDTH * 2`, `BASE + COUNT - 1`, an enum constant, a
shift, a conditional and a character difference are all extents.  This closes the
grammar-limitation sentence that stripes.txt and the feed bound had both been
carrying as a separate known limitation.

The extent is folded in the grammar action rather than stored as an expression, so
it stays an ordinary integer leaf in the AST.  That is why nothing downstream
changed: declarator_array_count, the size multiplier and abi_meta's bound text all
count AST_INTEGER children and now just read the resolved value.  Folding at parse
time also means the declared extent is known before any later pass needs it.

Integer rules are the ordinary ones, inherited from the shared constant evaluator:
long long, division truncating toward zero, remainder taking the dividend's sign,
and an out-of-range shift already diagnosed.  `-7 % 3` is -1 and is refused as a
negative size, and the diagnostic reports -1 rather than an absolute value.

Zero and negative are refused at the declaration.  declarator_array_multiplier_from
kept the identical check, which I confirmed by removing each layer in turn: either
one alone still refuses, and only removing both changes behaviour.  Worth knowing
that the guard is duplicated rather than single.

The "four arguments" confusion is worth recording because it came up twice and the
AST dump settles it.  A ternary takes three operands.  The node has four CHILDREN:
marker, test, true branch, false branch.

  conditional_expr
  +- identifier ?:      <- MARKER, not an operand
  +- lvalue (c)         <- test
  +- assign_expr (5)    <- true
  +- integer_literal 6  <- false

The marker exists only because MAKE_NODE names a node after its rule's left-hand
nonterminal, which for the ternary rule is conditional_expr -- and that name is also
used by the bare `conditional_expr: logical_or_expr` rule with one child.  So the
action stuffs an identifier leaf in as child[0] to say which kind it is.
MAKE_NAMED_NODE("?:", test, true, false) would have been three children with a
meaningful name; that is evidently what the grammar used to do, which is why the
two deleted copies were half-remembering it.  Also worth noting: in an array extent
the node does not survive at all, because the extent fold replaces it with
integer_literal 5.  The encoding is internal bookkeeping and was never visible.

NARROWED.  The detector now matches only a conditional_expr / case_conditional_expr
of four children with the "?: " marker.  The legacy `"?:"` branch is provably dead:
"?:" is not a nonterminal, so MAKE_NODE can never produce that node name, and
nothing calls MAKE_NAMED_NODE("?:", ...).  It was also not free -- two accepted
shapes meant all three accessors branched on the node name to pick child indices,
so every ternary paid a comparison that can no longer matter.  Accessors are now
fixed indices.

expropt.c turned out to hold a FOURTH inline copy of the same test, legacy
tolerance included.  It now calls the shared detector and accessors.  That is a
small widening I should flag rather than bury: expropt previously recognised only
conditional_expr ternaries, so it now also folds a case_conditional_expr one.  A
case term can syntactically be a ternary and folding it is the consistent
behaviour, but it IS a behaviour change and the 1031-test suite is what says it is
safe, not my say-so.

vcs_ternary_node_detection now pins the narrowing, which is the part that stops the
tolerance creeping back: the detector body must not test for a node named "?:",
and no file outside compile_expr_info.c may re-derive the shape at all.  Generated
