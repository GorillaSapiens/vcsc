Current contract
----------------
* 192 visible NTSC lines, modeled as 96 two-scanline logical bands.
* Six eight-row logical sprites may use P0 or P1.
* Public X range is 0..159; public Y range is 0..95. Events whose setup would
  begin above the visible top are preloaded during VBLANK.
* The diagnostic playfield is 12 rows of 16 physical scanlines. It is dynamic,
  asymmetric, non-reflected PF0/PF1/PF2 data rather than a static symmetric
  backdrop.
* Per-event sprite colors are supported.
* Persistent fairness tracks every omitted sprite, then stable-partitions omitted
  IDs ahead of shown IDs for the next frame. Fairness must not be confused with
  avoidable scheduler omissions.
* Normal same-lane setup reservations are intentionally long: P0 15 logical
  bands, P1 12. Directional cross-lane setup hazards are real timing constraints.
  A retained-P0 path has one narrowly tested exact-gap exception; do not weaken
  constants globally to improve an allocator score.
* Retained-X continuation is experimental: equal-X vertically disjoint sprites
  may reuse a lane without repeating normal RESP/HMOVE work.
* The equal-X 12-band endpoint / 7+5 bridge geometry has a forced physical
  orientation: endpoints on P1, bridge on P0. The VBLANK oracle scans only the
  future priority suffix, tests +/-12 Y before X, and caches proven future P1
  endpoint bits in `setup_line[6]` until that byte is cleared for its sort
  sentinel role. Keep that rule and scratch lifetime; all 720 priority
  permutations are verified against the real renderer.
* P0 top-preload Y=89..91 has an extra predecessor state so P0/P1 first visible
  GRP lines match across Y=85..95. Re-run the lane-stability GRP oracle after any
  raster-state change.
* Current `VCS_NTSC_EXTENDED_VBLANK` TIM64T split is **63/13**. Preserve the
  total blanking budget and this split until a deterministic timing witness proves
  another division is safe.
* Hand-written conditional branches in this renderer require explicit timing
  contracts; do not introduce `.flex` conditionals into beam/deadline paths.

Timing status
-------------
The bridge-oracle cost spike remains fixed: future-priority scanning, Y-first
+/-12 tests, and cached future P1 endpoints remove its pathological repeated
search cost. The permanent all-X bridge witness and all 720 priority
permutations remain valuable regressions.

Real Stella then exposed a separate 262/263 mechanism. With the 63/13 split, a
valid state X={14,0,25,88,114,140}, Y={76,67,95,95,95,95}, priority=
{2,3,4,5,0,1} returned from `vcs_ntsc_finish_deadline()` on scanline 52 at
horizontal CPU phase 72. The old `WSYNC := 0` materialized zero with a two-cycle
LDA before its STA; that pushed the TIA write across the 76-cycle boundary and
WSYNC then consumed another whole line. The host CPU harness still called the
frame 262 because its memory-write callback does not model this exact TIA
instruction phase, so real Stella is authoritative for this boundary.

The shared NTSC and PAL/SECAM 50 Hz scheduler cores now preserve A=0 by reading
INTIM into caller-clobbered X and use direct `STA WSYNC; STA VBLANK` at VBLANK
exit. An asserted TIMINT ($80) is normalized with ASL only on that already-late
path. Normal-path visible entry remains cycle 3. The 63/13 split is unchanged. In Stella 7 the witness now
passes 80/80 frames at 262, five other fixed stress scenes pass, and 384 held
real-Stella frames across 1/2/3/4/8/160-value X palettes with valid Y=0..95 all
reported 262. The maintained CPU test now also supports held ZP randomization and
exact pre-mutation failure dumps, and the asymmetric regression uses 16-frame
held dense-X layouts.

Allocator status
----------------
The user's staggered 0/1/2 witness X={62,72,62}, Y={86,82,76} is now solid:
0 and 2 share one hardware player by retained X while overlapping sprite 1 uses
the other. The exact-six P1->P0 decision is scan-order independent: an unresolved
P0 possibility is deferred as the otherwise-invalid $80 marker and becomes $81
only when a later backward-scan equal-X P0 proves retention; without that proof
it naturally decodes as no lane. The focused real-6502 regression pins identity
priority to all six visible sprites. The host C scheduler remains intentionally
a full-setup baseline oracle and no longer claims to model retained-X exactly.

Broader allocator quality is still unfinished for other occupancy<=2 layouts.
Do not lower the 15/12 reservation distances or broad directional hazard windows;
those shortcuts have already scheduled invisible sprites or lengthened frames.

A newly exposed retained-X rendering bug is active. `ChooseLane` used to form
$80/$81 for retained P0/P1 and then execute `LDX`, destroying the N flag before
the caller's `BMI`; that flag-clobber is now fixed by loading X before the final
A/flag-producing operations. With retained P0 now genuinely reachable, the
existing retained-P0 route is visibly wrong because it skips RESP/HMOVE but then
falls through the ordinary P0 setup pipeline.

The latest real-6502 tracing corrected an earlier diagnosis: the successor P0
bitmap itself ultimately starts at the requested Y. Corruption happens during
the handoff *before* that point. For the tight equal-X case, the predecessor
begins correctly, then the ordinary position/setup states stop advancing its
GRP0 rows. `COLUP0` can change to the successor color while predecessor GRP0 is
still latched, so a stale predecessor glyph row is displayed in the successor
color; P0 may then blank before the successor starts normally. This explains the
malformed/two-color 3/5 and 4/5 captures, including the apparent vertical jump.
The current visibility oracle can be fooled by exactly this stale-glyph/new-color
combination and must eventually verify actual glyph bytes/rows.

Keep the existing retained-P0 scheduling trigger at **Y+5**. For the tightest
same-X predecessor/successor relation, the intended handoff spans Y+5 trigger,
Y+4 position, Y+3 setup, Y+2 post-setup, Y+1 final predecessor row, then Y first
successor row. Do not move the trigger to Y+1 and do not weaken the exact-six
scheduler rules. The dedicated retained path must use the existing setup bands
to keep emitting/advancing the predecessor through its natural last row, delay
the successor color until predecessor graphics are retired, preserve the already
correct X position, and leave the successor's existing Y-start behavior intact.
It must not execute RESP0/HMOVE.

The retained-P0 implementation has now been cycle-budgeted far enough that the
next edit should be direct implementation, not more scheduler redesign:

* Keep the existing Y+5 trigger. A Y+1 trigger was explored and rejected because
  it changes event ordering relative to intervening P1 events and would invalidate
  already-proven exact-six scheduler assumptions.
* At the P0 trigger/position boundary, carry `current_gfx` across WSYNC just as the
  P1 path already carries its current glyph. Ordinary P0 enters with
  `current_gfx=0`, so an unconditional `STA GRP0` in the shared position entry is
  harmless for ordinary setup but preserves the predecessor for retained setup.
  This can replace the existing three-cycle `JMP Position0LineA` with a three-cycle
  `STA GRP0` plus fall-through, keeping the established beam phase unchanged.
* Remove/delay the successor `COLUP0` installation from `Position0LineA`; changing
  color there while predecessor GRP0 is still latched is the observed corruption.
* `P0RetainSlot` has enough otherwise-unused scanline budget to advance the
  predecessor's descending P0 graphics state for the following band while still
  servicing the asymmetric PF writes. A viable register plan finishes that slot
  with A=continuing P1 glyph and Y=continuing P0 glyph. The next retained setup
  line can therefore publish both players with two three-cycle stores instead of
  doing a graphics-table lookup under the beam.
* Retained setup must skip the ordinary HMOVE work. Either clear the pending HMP
  state in `P0RetainSlot` or enter after the HMOVE portion, whichever is smaller
  without perturbing ordinary P0 timing.
* Retained `Setup0LineB` must not overwrite `gfx_index[0]` with the successor state
  while predecessor rows remain. Preserve/advance the predecessor through Y+1;
  only then install successor color/state for the already-correct first row at Y.

Graphics-state chains run downward (for example sprite 0 uses
104,103,...,97,0), so preserve that direction when advancing predecessor state.
Production progress in this handoff
-----------------------------------
The first retained-P0 raster step has now landed. `Position0LineA` unconditionally
publishes `current_gfx` to GRP0. Ordinary P0 reaches that point with zero, while
retained P0 carries the predecessor row, so this is safe for both paths. The line
was kept cycle-neutral by replacing the later `LDY gfx_index+1` with `TAY` and
removing five cycles of tail padding. Focused asymmetric timing/visibility stress
passes unchanged. A separate VBLANK cleanup removed a redundant `LDA #0`, saving
two bytes and two VBLANK cycles; current accounting is 4087/4090 ROM, 115/128 RAM.

The deterministic equal-X trace now restores one of the missing predecessor rows:
GRP0 at lines 76..86 is `3c,66,c3,db,db,c3`. The remaining bug is explicit:
COLUP0 still changes to the successor at line 87, rows 88/90 are still absent,
and a stale `c3` can still appear later before the correctly-positioned successor
starts at line 96. Thus the first continuation write is correct but not sufficient.

A rejected experiment tried loading `current_gfx` before the trigger-line WSYNC
and replacing the post-WSYNC JMP with `STA GRP0`; the extra pre-WSYNC cycles pushed
the frame to 270 raw lines. It was fully reverted. Do not add work before that
WSYNC.

An exploratory P0RetainSlot predecessor-advance edit also exceeded the remaining
ROM budget before timing could be tested; it was not committed. Any remaining
handoff must reuse/replace existing instructions rather than simply add the full
state-advance sequence.
