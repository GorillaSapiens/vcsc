ENHANCED MULTISPRITE + ASYMMETRIC PLAYFIELD WIP
================================================

Purpose
-------
This is a checkpoint/handoff for the enhanced-multisprite side quest after the
player-only 192-line renderer became visually stable.  The current experiment
asks whether the same six logical sprites / two reusable TIA player lanes can
also support a genuinely dynamic asymmetric playfield.  Do not fall back to a
static playfield; the user explicitly considers that uninteresting because a
caller can set a static PF during VBLANK.

Current goal
------------
Keep all existing enhanced-multisprite behavior:

* six logical eight-row sprites;
* either logical sprite can occupy P0 or P1;
* two-way overlap is solid;
* three-or-more overlap gets fair persistent rotating 2-of-N arbitration;
* non-overlapping sprites can reuse either hardware player later in-frame;
* 192 visible NTSC lines / stable 262-line Stella frames;

and add a dynamic 32-bit asymmetric central playfield with independent left and
right halves.  PF0 is intentionally omitted for now.  The target is equivalent
in spirit to the maintained multisprite asymmetric PF model, not a static PF.

Playfield representation
------------------------
The renderer currently declares two 192-byte ROM tables:

    TEMPLATE_playfield_left[192]
    TEMPLATE_playfield_right[192]

There are 96 logical two-scanline bands.  Each 192-byte table is two 96-byte
planes:

    playfield_left[0..95]     -> left-half PF1
    playfield_left[96..191]   -> left-half PF2
    playfield_right[0..95]    -> right-half PF2
    playfield_right[96..191]  -> right-half PF1

The raster performs four timed PF writes on every physical scanline: PF1/PF2 for
the left half, then PF2/PF1 for the independently programmable right half.  The
example uses visibly different left/right patterns so a phase error is obvious.

What is already proven
----------------------
The important feasibility result is positive: the full dynamic asymmetric PF
fits alongside all six live sprite setup events.

Current WIP validation performed before this checkpoint:

* the asymmetric example builds as a 4K cartridge;
* current linked accounting is 3483/4090 ROM bytes used, 607 free;
* current linked RAM is 120/128 bytes used, 8 free (112 object + 8 hardware
  stack), so RAM is now the tighter resource;

  schedule with all six sprite events active;
* a PF-only Stella reference was compared against the live-sprite asymmetric
  renderer; after fixing the trigger-band PF phase, there were zero playfield
  pixel mismatches wherever the compared pixel was not covered by a sprite or
  the known TIA HMOVE comb artifact;
* renderer branch-contract audit passes;
* source-tree hygiene passes;

* example assembly allowlist passes.

The PF timing therefore appears viable.  Do NOT discard asymmetric PF merely
because the current sprites are horizontally wrong; horizontal positioning is
the remaining unfinished problem.

Current raster architecture
---------------------------
The ordinary raster and special event paths now preserve the four PF writes.
Sprite setup is spread over staged bands rather than trying to cram the old
player-only setup into one already-full scanline:

    ordinary/trigger band -> position band -> setup band

Both P0 and P1 have dedicated position/setup paths.  While one lane is being
repositioned the other lane's bitmap state continues to be serviced.  The PF
writes remain at fixed beam phases through ordinary, trigger, position, and setup
paths.

The existing VBLANK allocator/sorter from the hardened player-only enhanced
renderer is retained.  It already survived independent sprite motion,
randomized six-Y stress, and 3/4/5/6-way fairness tests in the player-only
checkpoint.  The asymmetric experiment has not intentionally changed the
arbitration policy.

KNOWN BROKEN: horizontal sprite positioning
-------------------------------------------
This checkpoint is NOT a finished renderer.

The asymmetric experiment currently has deliberately temporary horizontal
positioning.  The position bands strobe RESP0/RESP1 at fixed beam phases while
still loading the old packed HMP control.  The packed control's fine-motion
nibble can have an effect, but its coarse-count field is not being consumed by a
variable RESP countdown.  Consequently logical sprites are horizontally
bunched/misplaced and public X=0..159 is NOT currently honored.

This is expected and is the next task.  Do not waste time debugging the PF when
looking at the current bunched sprites; the PF itself already survived the
Stella reference comparison.

Why the old positioner cannot simply be copied
----------------------------------------------
The player-only enhanced renderer's 160-byte packed RESP/HMP table was calibrated
for its own exact RESP/HMOVE beam phase.  The asymmetric raster has four PF writes
that must remain at fixed phases, so its position scanline is a different timing
problem.  Reusing the player-only packed countdown verbatim would move PF writes
or RESP/HMOVE and would invalidate one or the other calibration.

The next positioning approach
-----------------------------
Continue from the current position-band implementation and calibrate the
asymmetric renderer itself in Stella.

Promising approach at checkpoint time:

1. Keep the four PF write phases fixed.  They are the part already proven.
2. Treat the remaining cycles on a position scanline as several legal RESP
   timing windows: before, between, and/or after the PF rewrite groups.
3. Use fixed-total-cost complementary delay paths so selecting a RESP slot does
   not shift either PF-half write or total scanline length.
4. Use HMP0/HMP1 for fine positioning inside each coarse RESP slot.
5. Calibrate P0 and P1 independently; do not assume their usable windows or
   resulting table bytes are identical.
6. Exhaustively verify all public X=0..159 in Stella, including X=0 and
   X=152..159 wrap-edge cases.
7. Only after a full 160-position map exists should the renderer expose the same
   X contract as the player-only enhanced renderer.

The rough phase-space estimate looked promising: the available fixed timing
windows plus HMP fine motion appear sufficient for the roughly eleven coarse
positions needed to span 160 color clocks.  This was not yet completed or
certified when this checkpoint was packaged.

Latest interrupted per-event X preload fix
-------------------------------------------
A subsequent continuation discovered a concrete horizontal-positioning bug in
this WIP: only the first accepted event loaded its packed X control into
`TEMPLATE_position_packed`.  Later setup events could therefore reuse sprite 0's
packed position control, independently of the still-unfinished early/late RESP
coarse dispatch.  That alone caused horizontal bunching/misplacement.

The current source fixes this without changing the physical scanline length or
PF write phases.  On both P0 and P1 setup paths, the seven-cycle tail of setup
line A that had previously been pure padding is now used to preload the *next*
event's packed X control:

    LDY setup_index     ; 3 cycles
    LDA draw_position,Y ; 4 cycles

A survives WSYNC/physical-line entry, and setup line B immediately stores it to
`position_packed` at cycle zero.  The old three-cycle tail padding in setup line
B is correspondingly removed, so the total timing of the two-line setup remains
unchanged.  This is deliberate use of work at the end of the preceding scanline,
as suggested by the user.

This change is real progress but does NOT complete public X=0..159.  The `$40`
late coarse-position class described above is still not fully consumed by a
finished early/late RESP dispatch.  Resume from this source; do not revert the
per-event preload and do not assume horizontal positioning is now correct merely
because each event has its own packed X control.

Continuation note -- 2026-08-19 X-position metadata correction
---------------------------------------------------------------
The 172915 handoff was later simplified back to a packed-HMP setup_position
representation. That simplification was a mistake for the asymmetric problem:
it makes lane identity fight the HMP sign bit and leaves too little useful
metadata for a staged RESP positioner.

The active WIP has restored the earlier, cleaner split:

    setup_code / event_code:
        bits 0..2  logical sprite id
        bits 4..7  full HMP fine-motion nibble

    setup_position / position_packed:
        bit 7      hardware lane (0=P0, 1=P1)
        bits 0..3  coarse RESP slot

Thus HMPx can be loaded directly from event_code (TIA ignores its low nibble),
while BIT position_packed gives deterministic lane dispatch without confusing
HMP bit 7 with lane identity.  Position0/1LineB continues to mask event_code
with #7 before logical-id table lookups.

This restored representation builds at 3498/4090 ROM and 120/128 RAM and the
renderer branch-contract audit passes. The asymmetric example Makefile now
depends on the correct asymmetric renderer, its README no longer claims that
the playfield is absent, and vcsc_branding.pl explicitly allowlists this handoff
file.

New positioning direction
-------------------------
Do not try to make one byte simultaneously be lane, coarse and HMP.  The split
above is deliberate.  Also keep exploiting the user's observation that beam
setup can happen at the END OF THE PREVIOUS SCANLINE.

The strongest current cycle-budget direction is:

* perform target color/HMP/other-lane-HMP preparation before the RESP-critical
  scanline whenever possible;
* let the position scanline concentrate on the four asymmetric PF writes plus
  RESP;

  previous-line strobe or a special PF1/PF2 ordering;
* the maintained multisprite renderer is useful precedent: it performs an
  in-raster packed P1 positioner while asymmetric PF is live, and its left-half

Checkpoint continuation -- 2026-08-20 absolute RESP vector geometry
--------------------------------------------------------------------
The next checkpoint replaces the abstract `slot * 3` offset idea with an actual
linker-safe coarse-RESP landing object, without yet entering it from the visible
raster.

`TEMPLATE_resp_ladders()` is a page-contained 96-byte code object with only
128-byte alignment.  Each coarse delay cell is exactly three ROM bytes and five
CPU cycles (`NOP` + zero-page `BIT`).  P0 entries are at base+$00..$1e; 33 bytes
of inert padding place P1 at base+$40..$5e.  Because the base is 128-byte
aligned, pointer-low bit 6 is always 0 for P0 and 1 for P1 while both ladders
remain in one 256-byte page.  The visible lane tests therefore changed from
BIT/BMI to BIT/BVS.

VBLANK now converts each raw coarse slot to the *absolute low byte* of its
landing.  `position_packed` holds that low byte and adjacent `event_stage` holds
`#>TEMPLATE_P0RespDelayBase`, so the two bytes already form a valid zero-page
NMOS indirect-JMP vector.  This removes the future raster-side slot multiply,
base addition, and pointer-high setup.

The current linked example places the object at `$F780`, with P1 beginning at
`$F7C0`; the map reports size `$0060`, `page=hard`, `component-align=$0080`.
Verified accounting is:

    RAM: 117 / 128 bytes used, 11 free

The visible raster still executes the fixed RESP0/RESP1 stores.  The temporary
landing endpoints are RTS placeholders and must not be called from the raster
yet.  Immediate next step: restructure the position scanline so its left PF

THE CENTRAL DESIGN CHANGE
-------------------------
Do not force every positioning event through one universal scanline schedule.
Classify the visible raster by the number of RESP strobes required on that
physical scanline, then schedule PF writes around the requested RESP times:

    0 RESP: no sprite reposition on this line
    1 RESP: one hardware player must be repositioned
    2 RESP: both P0 and P1 must be repositioned

The playfield is non-reflected and full 40-bit asymmetric.  Think of the three
right-half writes as ordered timing landmarks:

    R0 = right PF0
    R1 = right PF1
    R2 = right PF2

Use the END OF THE PREVIOUS SCANLINE aggressively.  Left-side state need not all
be loaded after the new line starts.  Any PF register whose previous right-half
bits have already been consumed may be loaded with the next line's left value in
the tail.  The current verified code already does this for left PF0.  The next
RESP implementation should attempt to stage left PF1 too, and if useful carry a
left PF2 value across the boundary in A/Y so the hot line starts with as little
left-PF work as possible.

0-RESP CASE
-----------
There is only one fundamental 0-RESP case.  It has abundant cycles.  Use it to:

* issue the normal six PF writes;
* perform as much next-line PF staging as possible;
* advance graphics state;
* preload upcoming event metadata/color/HMP when safe;
* pay scheduler/bookkeeping costs that do not belong on a RESP-critical line.

This case is the preferred place to hide work for following 1-RESP/2-RESP
lines.

1-RESP CASES
------------
The eleven coarse X slots are timestamps, not eleven different algorithms.
Classify a requested RESP relative to R0/R1/R2.  Fundamental one-RESP orderings
are:

    RESP R0 R1 R2
    R0 RESP R1 R2
    R0 R1 RESP R2
    R0 R1 R2 RESP

Boundary/collision variants around the preferred R0/R1/R2 phases may require
moving that PF write to the early or late edge of its legal window.  Conceptually
this gives seven useful scheduling classes:

    before R0
    around R0
    between R0/R1
    around R1
    between R1/R2
    around R2
    after R2

A compact four-class implementation was worked out on paper as a likely first
coding pass:

    coarse slots 0-2: RESP early, then remaining right PF writes
    coarse slots 3-5: R0 before RESP; R1/R2 after
    coarse slots 6-8: R0/R1 (and where legal R2) before RESP
    coarse slots 9-10: all right PF writes plus bookkeeping before late RESP

Do not treat those group boundaries as sacred; change them if Stella/pixel
calibration says a neighboring placement is cleaner.

DELAY / DISPATCH MECHANISM
--------------------------
A useful linker-safe primitive has already been proven in an earlier checkpoint:

    NOP             ; 2 cycles, 1 byte
    BIT zp          ; 3 cycles, 2 bytes

Together they are exactly 5 cycles / 3 ROM bytes.  A descending trampoline
ladder can therefore provide 0/5/10-cycle offsets with only three bytes per
step.  An earlier 128-byte-aligned, page-contained P0/P1 landing object linked
successfully.  A dedicated 256-byte-aligned page did NOT: its alignment
fragmented the 4K linker enough to overflow `main`.  Do not revive the 256-byte
layout.

Possible implementations, in preferred order of simplicity:

1. Keep the already split P0/P1 raster paths and use lane-specific handlers with
   literal `STA RESP0` or `STA RESP1`; this avoids paying a lane-selection tax at
   the actual RESP cycle.
2. Use compact per-player 5-cycle ladders in one 128-byte-contained object.
3. Reuse the existing `slot*3` predecode and bit-6 lane tag if it still saves
   code.  If pointer geometry becomes awkward, lane identity can instead be
   carried in event metadata and the pointer may use all eight low bits.
4. `position_packed:event_stage` are adjacent zero-page bytes and can form an
   NMOS indirect-JMP vector if an indirect dispatcher proves smaller.  This was
   demonstrated previously but removed while recovering ROM for frame stability.

Do not add a large branch chain in the beam-critical line.  The point of VBLANK
predecode/trampolines is to keep data-dependent timing out of the visible path.

REGISTER / SCANLINE-TAIL OPPORTUNITIES
--------------------------------------
Current verified code carries a continuing bitmap byte across the boundary and
uses PHA/PLA on line B.  Further cycle recovery candidates, NOT YET CODED:

* carry the continuing graphics-state INDEX in Y across the boundary and defer
  the actual `LDA graphics,Y` until the cheapest side of RESP; this can remove
  the PHA/PLA pair or move it out of the hot region;
* carry a next-line left PF value in A and another in Y when their lifetimes do
  not collide with the graphics state;
* pre-stage next-line PF0 and PF1 late in the previous line; PF2 may be the only
  left-half PF write that must remain early on the RESP line;
* move DEX, INC setup_index, next-event loads, and continuing-glyph preparation
  progressively BEFORE RESP as the requested RESP moves to later coarse slots;
  leave them after RESP for early slots;
* HMP and current-event color are already moved into line A in the current
  source.  Preserve that win unless a measured schedule proves a better home.

An earlier attempt simply moved the existing lane branch before WSYNC and caused
an extra scanline because the old line then exceeded cycle 75.  Do NOT repeat
that exact edit.  A pre-WSYNC lane decision is only worth revisiting after enough
other work has been moved earlier/later that the boundary is still exact.  If a
BIT/BVS lane flag is used, remember that loads/stores preserve V, which can make
V a useful lane-state carrier across non-flag-changing instructions.

2-RESP CASES
------------
The current scheduler has historically avoided overlapping setup/position events,
which helped create the overconstrained single-position-line design.  The final
case scheduler should allow a physical scanline to reposition both hardware
players when needed and select a true 2-RESP schedule.

Let A and B be the two RESP strobes ordered by required cycle (A <= B).  Ignoring
exact spacing, there are ten fundamental interleavings with R0/R1/R2:

    A B R0 R1 R2
    A R0 B R1 R2
    A R0 R1 B R2
    A R0 R1 R2 B
    R0 A B R1 R2
    R0 A R1 B R2
    R0 A R1 R2 B
    R0 R1 A B R2
    R0 R1 A R2 B
    R0 R1 R2 A B

Each ordering may have spacing subclasses:

* same coarse slot;
* adjacent slots (5-cycle separation);
* moderate separation where one useful operation fits between RESP writes;
* far separation where multiple PF/bookkeeping operations fit between them.

When both players want the same/near phase, test whether consecutive
`STA RESP0` / `STA RESP1` (or reverse order) plus independent HMP calibration is
cheaper than treating them as two fully separate timed islands.  Player identity
should be orthogonal to the ordering: support P0-then-P1 and P1-then-P0 without
duplicating the entire timing architecture where possible.

SCHEDULER CHANGES REQUIRED FOR 0/1/2 RESP
-----------------------------------------
Once the one-RESP path is proven, modify the VBLANK event scheduler so each
physical positioning line can be classified explicitly as 0, 1, or 2 RESP
operations.  Do not relax conflict rules blindly: setup/color/HMP writes that can
corrupt an already visible same-lane sprite still need their existing exclusion
windows.  The goal is to allow two independent hardware-lane RESP operations on
the same line when their setup lifetimes make that safe, not to permit arbitrary
same-lane overlap.

Precompute as much as possible during VBLANK:

* lane(s) to reposition;
* coarse slot(s);
* HMP fine nibble(s);
* case class / ordering where cheap to encode;
* event color and graphics start state;
* any dispatch entry low byte or compact case id.

The visible raster should consume a compact hot record rather than chase logical
sprite ids.
