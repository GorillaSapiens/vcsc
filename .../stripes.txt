VCSC RENDERER / STRIPES ROADMAP
================================

Goal
----
One generic positive-stripe renderer: `all_five`, then the remaining maintained
renderers, then the zero path.

Architecture (settled; no per-count specialisation)
---------------------------------------------------
* `stripes:=0` stays a special no-stripe path with no arrays; `stripes:=1` may
  stay a special case.
* `stripes:=N`, N=2..32, is ONE implementation parameterised only by
  `TEMPLATE_stripes`. Never add a per-count branch, scheduler, or renderer for
  2/8/16/32. The existing `stripes:=2` code is a prototype, not a contract.
* It is generic in BOTH axes. `TEMPLATE_lines` is the scanlines the renderer was
  allocated, not a fixed 192. No `stripes > 0 => lines == 192` requirement may
  exist, so a score/status or user component may own part of the raster.
* `(192, 32)` is the current worst case and proof target, not an architectural
  requirement: build a generic `(lines, stripes)` architecture whose hardest
  required case is currently `(192, 32)`.
* Invalid configurations are rejected at compile time, never rounded.

ABI
---
`parameter stripes := 0;` zero preserves the old path with no arrays.
`stripes:=N` requires `game_playfield_colors[N*2]` and
`game_playfield_data[N*6]`: COLUPF/COLUBK then PF0/PF1/PF2 per stripe. Preserve
raster/timing/handoffs/resources/write phases; no runtime division or per-line
feature test. Do not lock this ABI yet.

Source addressing: the raster cannot read the record. It reads three page-contained
tables with ONE index each (`stripe_generic_feed_source_bound.pl`, which supersedes
`stripe32_feed_layout.pl` as the authority and still reproduces it for `(192,32)`):
pair q of the region is read at Y = region-1-q in feed0=C0/C1/PF4,
feed1=PF0/PF2/PF5, feed2=PF1/PF3/spare, all fixed 4-cycle abs,Y with no stripe
index. Both record forms are rejected executably, each read on its own window:
X-held record offset (`stripe32_record_common_index_bound.pl`) and a zero-page
record pointer with a compile-time field offset
(`stripe_feed_pointer_source_search.pl`: color/p0_a_visible, even/p0_p1_feed,
odd/p0_p0_mid). The tables are load-bearing, not a convenience.

The layout generalises rather than being a `(192,32)` artefact: P pairs per stripe
give pair 0 a colour plus two PF bytes, pair 1 a colour plus two PF bytes, pair 2
two PF bytes, and pairs p>=3 nothing, so 3*P >= 8 forces P >= 3 -- exactly what the
geometry authority rejects below six scanlines. Containment for the fixed-cost
reads is already available: three 96-byte `page const` tables are placed
page-contained and the linker enforces it, including when the table is itself a
derivation rather than a literal.

Feed cost is 3*region bytes and is INDEPENDENT of the stripe count, because the
feeds are indexed by renderer pair rather than by stripe: 288 bytes at 192 lines for
every N. Logical stripe data is 8*N bytes (C0,C1 plus PF0..PF5), so smaller stripe
counts carry less DATA but not a smaller feed. That is not a blocker: the feed is
measured against what it replaces, and the stripes=2 prototype costs 2417 bytes
(3704 at stripes:=2 versus 1287 at stripes:=0), so a 288-byte feed leaves 2129
bytes for the generic body at the tightest stripe count. An earlier conclusion that
the feed left only 98 bytes was wrong: it measured against the free space of the
build being replaced. Pair-indexed feeds are therefore the uniform choice for the
whole 2..32 range at RUN time, and the six-scanline timing remains the binding
constraint. `stripe_generic_rom_bound.pl` owns this arithmetic.

Correcting one claim: the feeds are uniform in ROM cost but NOT in source. All 19
legal configurations (18 equal splits plus the 181 partial region) need their own
three tables -- 5625 initializer entries in total. The cause is the DATA LAYOUT, not
the compiler: q=P*s+p picks the stripe, so 192/2 fills 48 pairs from one stripe while
192/32 fills 3 and moves on. Being generic in stripes requires that. It is a
source-size cost, not a runtime one. Separately, the grammar takes only a literal in
an array extent (`direct_declarator '[' INTEGER ']'`), so a renderer must spell
`[255]` rather than `[3*(TEMPLATE_lines/2)]`; relaxing that is a real readability
win at a few sites and would NOT reduce the table count, since a size expression
cannot change which byte goes in which slot.
`stripe_generic_feed_source_bound.pl` measures the count and keeps the two causes
distinct.

Where the tables come from is settled. A file-scope `const` object whose
initializer is entirely constant is folded at link time and its bytes are then
readable as a constant expression, so a table derived from another table's element
reads is itself link-time ROM: no RAM, no startup copy, no per-count data in the
public authoring form. It is byte-granular and covers plain default-ROM data only.
The named-region exclusion is a correctness boundary, not a limitation: folding a
read of a data-only object erases the reference the linker exists to reject. Scratch
files go in the caller-supplied `VCSC_ALL_FIVE_TMP` and never in the shared system
temporary directory, because concurrent runs in separate checkouts are normal here.
See `.../context-history/2026-10-06.txt`. `test/vcs_const_link_time_table.pl` owns
that fold, and `test/vcs_all_five_stripe_feed_tables.pl` builds the real (192,32)
tables and checks every emitted byte, the page containment, and that nothing costs
RAM. RAM as an alternative is ruled out for good: 288 bytes against 103 used / 25
free / 128 total. `stripe_generic_feed_source_bound.pl` measures all of it.

Positive stripes preserve the frame, handoff, resource, branch, object, phase,
composition, zero-path, and pinned-palette Stella contracts. 192/228 stay
terminal-WSYNC; 170/181 retain score-composable handoffs.

Geometry
--------
`stripe_generic_geometry_bound.pl` is the compile-time geometry and legality
authority. Height H is even with P=H/2 >= 3 (the measured six-scanline minimum);
the packed BL/M1/M0 row is eight pairs, so the supercycle is lcm(P,8). The region
only has to FIT inside `TEMPLATE_lines`, so an odd mode such as 181 is striped by
leaving the odd scanline to a composing component. A whole-multiple region loops;
a 0..7-pair remainder reuses the maintained `VCS_STRIPES2_CERT_TAIL0..7`
certification, not a second scheduler. Equal splits: 170 -> 1,5,17; 181 -> none
odd; 192 -> 1,2,3,4,6,8,12,16,24,32; 228 -> 1,2,3,6,19. `(192,32)` is h=6, P=3,
supercycle 24 pairs, 8 stripes/supercycle, 4 repetitions.

Scheduling invariants
---------------------
`stripe32_sixline_machine_search.pl` is the zero-slack design point: three exact
152-cycle pairs copy all six inactive PF bytes plus both next colours, feed both
players through three-byte service pointers, leave public player Y untouched, and
preserve all 51 ordinary TIA appointments. One frame-wide player index, not
per-stripe pointer motion; Y=95..0, pair-2 CPY/BCS pretriggers one stripe ahead.
<=2 special stripes per player, union <=4. Service-pointer lows are
frame-invariant (page-aligned 351-byte zero slab), so transitions install only the
high byte. Fixed RIOT 123/128. Cadence is one 24-pair (8-stripe) supercycle
repeated four times; taller stripes only add slack.

Event/high-byte handlers compose into that supercycle. Before composing, every
event obligation competed for the single 16-cycle pair-2 tail and needed 21
cycles. Hoisting the install into `p0_mid`'s own 18-cycle span (fits at 13) splits
them into 16 in the tail plus 13 in `p0_mid`; the tail then holds only the
ordinary M0 shift, the frame-wide DEY, `bpl supercycle_start`, and a real
three-cycle exact-cache colour re-bank. Nothing is dropped and no extra cycle
budget or third control byte is needed, so RIOT stays 123/128. The ordinary loop
tail is cycle-neutral at 16, its 15-cycle terminal fall-through absorbed by WSYNC.
`stripe32_transition_high_only_search.pl` is a known-incomplete skeleton: it
installs the service high byte but supplies no pair-2 PF copies, so the next
stripe's PF1R/PF2R are unsupplied and it may not be emitted as-is.
`stripe_supercycle_event_compose_bound.pl` owns the executable proof.

RESOLVED 2026-10-08: the BOUND's rule is canonical -- record stripe s goes in the
pair the layout calls s, with NO rotation.  The user agreed the bound is the more
logical of the two, and it is already the declared authority.

The contradiction, for the record.  Both artifacts place pair q at Y = region-1-q
and both were internally self-consistent, but they disagreed on which record stripe
landed in which pair: the bound used stripe s, while
test/fixtures/all_five_stripe_feed/feed_transposition_probe.c26 and the
vcs_all_five_stripe_feed_tables.pl checking it used record_byte(8*($s+1)+$field), a
+1 rotation modulo the stripe count.  Verified by generating all three (192,32)
tables under each rule: with the rotation all three matched the fixture byte for
byte, without it none did.

Why it had to be settled before the machine was written.  The raster reads feed[Y]
at whatever Y it is on, so the tables and the machine's Y discipline must agree on
this.  A rotation does not crash, does not fail a size check, and cannot be caught
by any test that only counts bytes: it draws every stripe with the NEXT stripe's
colours and playfield, which reads as a renderer bug and is not one.  There is also
no machine yet to catch it.

The bound could not see it either, which is worth noting as a general trap.  Its
claim to "still reproduce it for (192,32)" is
  $out =~ /3x96=288 bytes/ && $out =~ /feed2 has 32 spare pair2 slots/
which compares SIZE STRINGS.  A layout rotation is invisible to a size check, so
"reproduces the maintained proof" was true about sizes and silent about layout.
Both files now say which rule they follow and why the two must not be allowed to
diverge quietly.

Remaining
---------
0. DONE: the fold is landed. A `const` object built from another `const` object's
   element reads is link-time ROM, so the renderer declares its three `page const`
   feed tables as a transposition of the public eight-byte record and no per-count
   data ever reaches the public authoring form. Byte-granular by construction; a
   wider element type keeps its runtime-read behaviour, and an out-of-range read is
   refused rather than folded to an adjacent byte.
1. Emit the generic rolling machine in `all_five.c26` behind a focused probe, then
   remove the `stripes:=2`-only production machinery. Preserve the 4K ROM,
   <=128-byte RAM, frame, PF phase, object-sequence, handoff, and pinned-palette
   Stella contracts. SP save/restore around visible drawing is allowed if the
   emitted form uses TSX as the packed-row-X shadow; no stack accesses in raster.
   The three feed tables are declared and their bytes are certified; what remains is
   the raster body that reads them at Y = region-1-q.
2. Supply the pair-2 PF copies the hoisted path omits, keeping PF0R on its
   ordinary cycle.
3. Relieve the `stripes > 2` guard only once the probe and its regressions are
   green AND the generic path serves 2..32 rather than one count.
4. Promote the public example to `stripes:=32` with the checked-in
   `examples/_common/all_five_stripes32_rainbow_data.c26`. Keep the two-stripe
   example runnable until the renderer accepts 32; never ship a deliberately
   non-building public target.
5. Certify every maintained line mode, including non-divisible 228 and the
   181/170 score-composable handoffs, plus all missile/player-color combinations.
   Document storage, costs, composition, and the `gameplay` name/API migration.
6. Certify stripes in `multisprite`, then `enhanced_multisprite_asymmetric`. Close
   roadmap item 57 only when obsolete paths are gone and the suite is clean.

The old 28/26-scanline result is not a stripe-height limit; it bounds only the
discarded search-ahead strategy (`stripe_dual_uniform_window_bound.pl`). The
design target is six scanlines. Never describe 28 or 26 as a public minimum.
