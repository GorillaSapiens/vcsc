VCSC PROJECT CONTEXT
====================

Purpose
-------
This is the durable handoff file for continuing the project after a chat
restart. It lives at `.top_secret/context.txt`. When asked to "look at
context.txt and figure out what to do next":

1. Read this file first.
2. Inspect the current tree and verify that it agrees with this record.
3. Continue with the first unfinished item in "Immediate TODO" unless the user
   gives newer instructions.
4. Update this file after every meaningful change or decision.
5. Keep `.top_secret/remove.txt` accurate. It contains one repository-relative path
   per intentionally deleted file, suitable for:

       rm `cat .top_secret/remove.txt`

   Exception: when the user explicitly requests erasing a proper name from the
   project, obsolete paths containing that name are not retained in the ledger.

Project goal
------------
Maintain VCSC as a brutally pared-down Atari VCS C-like compiler and companion
toolchain aimed specifically at the Atari 2600/VCS. Compatibility with the old
general-purpose N language or n65 tool names is not a goal. Features are changed
in controlled, testable vertical slices.

Settled final-language decisions
--------------------------------
* Target: Atari 2600/VCS using the 6507 CPU.
* All multibyte values are little-endian.
* Binary literals accept visual digits after `0b`/`0B`: `.` is zero and
  `X`/`x` is one. The lexer normalizes them to ordinary binary digits before
  parsing, so all existing integer semantics and range checks remain shared.
* The stock machine interface exposes eight ordinary binary integer types and
  four unsigned packed-decimal integer types:

      int8_t      uint8_t
      int16_t     uint16_t
      int24_t     uint24_t
      int32_t     uint32_t
      bcd8_t      bcd16_t
      bcd24_t     bcd32_t

  The BCD types store two decimal digits per byte in little-endian digit-pair
  order and have numeric ranges 0..99, 0..9999, 0..999999, and 0..99999999.

* `int`, `char`, and `bool` are ordinary identifiers rather than built-in or
  reserved type names. Programs may introduce them as transparent typedef
  aliases, for example `typedef int16_t int;`.
* String literals are NUL-terminated `uint8_t` arrays stored in cartridge ROM.
  They decay to `uint8_t *` in pointer initializers; writing through such a
  pointer is invalid even though `const` is not yet enforced by the type system.
* No float or double.
* The stock VCS headers expose canonical signed and unsigned 8-, 16-, 24-,
  and 32-bit ordinary types. The compiler core handles user-declared ordinary
  signed or unsigned little-endian integer widths from one through four bytes.
  `bcd32_t` is the largest currently exposed packed-decimal type.
* The stock runtime provides no heap, `sbrk`, `malloc`, or `free`.
* The retained legacy BASIC kernel tree remains source/reference material for
  possible conversion to VCSC; it is intentionally not dead-code pruning
  fodder merely because it is not yet wired into the build. Its exact upstream
  licensing overview remains verbatim in the retained `LICENSE.txt`; project-
  facing names and non-license branding comments are intentionally generic.
* Converted legacy kernels should become source-level VCSC modules included by
  applications. Each module declares and owns the variables and scratch storage
  it needs, and normal compiler/linker allocation should place them unless the
  converted source demonstrably requires a fixed address, alignment, adjacency,
  or page constraint. Describe each kernel or variant with a source-integration
  contract rather than pretending that all retained kernels share one ABI.
* Shared score fonts live under `libraries/vcs/fonts/`, not inside an example.
  Nine 8x8 families are provided as eighteen VCSC modules: one decimal `0-9`
  table and one hexadecimal `0-9A-F` table per family. Every module exports the
  common `score_font` symbol, uses one visual-binary byte per source row, and is
  installed with the VCS support package. Example 03 deliberately selects
  `default_decimal.c26`; this is a settled example choice and must not be
  changed merely to match an older changelog entry.
* void remains a special non-value type.
* Pointers are special 16-bit little-endian values.
* Subtracting compatible pointers yields `int16_t` and a C-style element count.
  Differences outside the representable `int16_t` range are undefined.
* Functions retain normal source-level parameters and lexical scope.
* The final ABI has no software argument/local stack.
* Parameters and automatic locals use statically allocated storage.
* A function has one activation record and is intentionally non-reentrant.
* Direct recursion, mutual recursion, callback re-entry, and any other path that
  activates the same function twice must be rejected.
* Each source-level function name has exactly one signature. Matching prototypes
  and a later definition are legal; ordinary named-function overloading is not.
* JSR/RTS still use the 6502 hardware stack for return addresses.
* Function returns use exact-sized callee-owned zero-page memory:

      void:                         no return object
      8/16/24/32-bit binary integer: function$__return, 1, 2, 3, or 4 bytes
      8/16/24/32-bit packed BCD:    function$__return, 1, 2, 3, or 4 bytes
      pointer:                      function$__return, 2 bytes

  The callee writes `$$`, whose linker-visible symbol is
  `function$__return`, and every value-returning epilogue is plain `RTS`. The
  caller copies directly from the callee object. A, X, and Y are caller-
  clobbered and carry no ordinary language return value.

* All four stock packed-BCD types may be returned. Ordinary binary memory
  returns and stock type names support widths from one through four bytes.
* Struct, union, and array returns remain forbidden even when small. Use an
  explicit result pointer.

Completed vertical slices
-------------------------
1. Value-returning functions own exact-sized zero-page `function$__return`
   objects. Callers consume those objects directly; registers are not part of
   the ordinary return ABI.
2. Every fixed parameter of a directly named function is callee-owned symbol
   storage rather than software-stack storage.
3. Function return types are restricted to void, supported one- through
   four-byte binary and packed-BCD integers, and 16-bit pointers. Aggregates
   and arrays remain forbidden.
4. The VCS linker stopped modeling mirrored $0180-$01FF stack addresses as
   separate physical memory. The first implementation used a fixed $E0-$FF
   reserve; completed slice 24 supersedes that partition with call-graph sizing.
5. Every named automatic local and the hidden `$$` return object now has
   function-qualified fixed-address storage. Automatic initializers still run
   whenever control reaches the declaration on each invocation.
6. The executable `test/software_stack_inventory.pl` regression inventories
   compiler `_pushN`/`_popN` emitters and removed runtime symbols directly from
   the current tree. It detects any reappearance or count drift.
7. Ordinary direct calls evaluate arguments through fixed compiler-generated
   call-site scratch rather than a software-stack call frame. Results are copied
   directly from callee-owned return objects, so return-only scratch is gone.
8. Variadic functions and callable types have been removed. The lexer rejects
   `...`; variadic call lowering, hidden metadata, `stdarg.c26`, `sprintf.c26`, and
   the legacy direct-call software-stack fallback are gone.
9. Function pointers and indirect calls have been removed. Function-pointer
   declarators and function names used as values are rejected; `_callptr0` and
   the final software-stack call frame in `compile_call.c` are gone.
10. General truth-value evaluation and discarded non-call expression results
    now use fixed per-site BSS scratch instead of `_pushN`/`_popN`.
11. Simple assignments into fixed symbols now evaluate and convert through
    fixed per-site `__n65_assigntmp_N` BSS scratch instead of
    `_pushN`/`_popN`.
12. Two-operand comparisons and the main built-in binary operator families now
    use fixed per-site BSS scratch instead of `_pushN`/`_popN`: pointer
    subtraction, scalar/pointer addition and subtraction, shifts, bitwise
    operations, multiplication, division, and remainder.
13. Cast conversion, function-local/global absolute-reference conversion, and
    built-in increment/decrement now use fixed per-site BSS scratch. Fixed
    symbol-to-lvalue helpers cover ordinary, indirect, and bit-field lvalues.
14. Built-in compound assignment, switch-expression comparison, simple
    indirect/absolute/bit-field assignment, runtime local and return-object
    initialization, and local absolute-reference initialization now use fixed
    BSS scratch. `compile_stmt.c` no longer emits `_pushN` or `_popN`.
15. Pointer/index lvalue evaluation, bit-field helper pointer preservation,

    `_popN`.

    fixtures have been removed. Compiler source emits no `_pushN` or `_popN`.
    Ordinary named-function overloading was retained temporarily and removed in
    completed slice 31.
17. Floating-point support has been removed from the language, compiler, driver,
    build, runtime, machine definitions, and positive test suite. Floating-point
    literals and `$float`/`$float:*` type flags remain only as direct rejection
    paths.
18. Big-endian and mixed-endian target support has been removed. All target
    integers, pointers, constants, initializers, conversions, comparisons, and
    runtime helpers are little-endian. `$endian:big`, `($big)`, and `($little)`
    remain only as direct rejection paths.
19. [Superseded by slice 39.] Ordinary binary target integer widths were
    temporarily restricted to exactly one or two bytes while inherited wide
    support was pruned. Slice 39 rebuilt and tested width-generic one- through
    four-byte scalar machinery without yet adding the canonical public names.
20. The stock language and machine interface now use only int8_t, uint8_t,
    int16_t, and uint16_t as built-in integer names. Comparisons and logical
    expressions produce an ordinary uint8_t; there is no special boolean type.
21. Simple transparent typedef aliases are supported. `int`, `char`, and `bool`
    are ordinary identifiers and may be introduced as aliases for canonical

    and verifies as a complete unbanked 4096-byte VCS cartridge with reset code

    map.
23. Inline assembly resolves source-level absolute `ref` names according to the
    opcode's operand access: read instructions use the read address, stores use
    the write address, and read-modify-write instructions require identical
    non-`none` read/write addresses. Illegal side use and split-address RMW are
    compile-time errors. The solid-color kernel now uses TIA register names.
24. The VCS linker configuration declares all 128 physical RIOT RAM bytes and
    marks the region `callstack = callgraph`. After archive selection and
    cross-object cycle validation, vcsc-ld computes the longest linked call path,
    reserves two top-of-RAM bytes per function level, and reports/exports the
    resulting hardware-stack range. A configuration may add `callstack_extra`
    bytes for stack use explicitly declared by an included assembly module but
    hidden from source call metadata. Arbitrary inline-assembly pushes, calls,
    and stack-pointer manipulation are still not inferred.
25. Common VCS byte operations now bypass permanent expression scratch.
    Discarded uint8_t increment/decrement, unsigned byte comparisons, constant
    byte stores, and byte-to-hardware-register stores lower directly. A simple

    retains only its two persistent state bytes.

    reuse a depth slot; nested expressions receive deeper slots; caller and
    callee functions retain distinct physical storage. Leases remain live
    through final copy-out, are released LIFO, and are checked at translation-

31. Ordinary named-function overloading has been removed. Each source name now

Current return ABI
------------------
Relevant code:

    compiler/compile_function.c
        return_type_is_void()
        return_type_is_supported()
        return_type_has_value()
        function_has_return_object()
        function_return_symbol_name()
        validate_function_return_type()

    compiler/compile_call.c
        direct-call argument/result handling

    compiler/abi_meta.c
        return_void / return_memory metadata

Every function declaration and definition is validated. The compiler currently
accepts void, one-through-four-byte ordinary binary integers, one-through-four-
byte packed BCD integers, and 16-bit pointers. It rejects aggregates, arrays, and
other noninteger/nonpointer returns. The stock interface names ordinary widths
through 32 bits.

Inside a non-void function, `$$` is the source-level return object. It is an
exact-sized hidden callee-owned zero-page symbol named `function$__return`.
`return expr;` writes it, and the common epilogue is plain `RTS` for every
current width. Non-static definitions `.zpexport` the symbol. A caller in another
object `.zpimport`s it only when the result is consumed.

After `JSR`, the caller copies directly from `function$__return` into the
enclosing destination. Ordinary generated calls do not push or restore compiler
state. A, X,
and Y are ordinary caller-clobbered registers, not result registers. Ignored
return values cause no copy. There is no `return_value` metadata mode, no
caller-owned return slot, and no register-result scratch lease.

Current direct-parameter ABI
----------------------------
Every fixed parameter of a directly named function has a callee-owned symbol.
At each ordinary direct call, the compiler may lease the caller function's
current scratch-depth slot. The lease selects a fixed `__vcsc_scratch_N` symbol
at compile time. The caller:

1. evaluates every argument left-to-right into one caller-owned staging block;
2. after all argument expressions finish, copies the complete converted set to
   the corresponding callee parameter symbols;
3. executes JSR with no compiler-state pushes;
4. when the result is used, copies directly from the callee-owned
   `function$__return` symbol into the enclosing destination.

Scratch is pooled per function and nesting depth. Sequential uses in one
non-reentrant function reuse the same slot and nested uses receive deeper slots.
The compiler emits scratch, parameters, automatic locals, and return objects as
pieces of the owning logical activation. The linker keeps caller/callee paths
disjoint and overlays sibling activations in each physical memory region. Each
slot is emitted once at the maximum size seen for that depth. LIFO release and
an end-of-compilation zero-depth check reject unsafe lifetime overlap. Parameter
symbols may be ordinary absolute storage or zero-page storage.

Call-graph and call-target rules
--------------------------------
No function body may be active twice because its parameters, automatic locals,
and return object share one fixed activation record. Compiler and linker
call-graph checks reject same-unit and cross-object cycles, including cycles
through zero-parameter functions.

Every call target must be a directly named function. Function-pointer
declarators are rejected, as are bare function names or `&function` used as
values. This keeps every call edge visible to cycle analysis and eliminates the
indirect-call ABI and `_callptr0` runtime trampoline.

The same linker-visible function/edge metadata now drives longest-path stack
sizing. The linker counts nodes on the longest acyclic path after all selected
objects and archive members are known. External assembly functions reached by a
source call appear as one graph node, but calls and pushes inside their assembly
bodies are not visible yet.

Current activation overlay
--------------------------
The compiler emits each ordinary function's parameters, automatic locals,
callee-owned return object, and pooled expression scratch in named activation
segments. Static source locals and globals remain ordinary persistent storage.
At link time, every physical memory region is planned independently from the
complete selected call graph:

* a callee begins after the caller bytes still live in that region;
* sibling functions and unrelated roots may share the same physical bytes;
* source-declared `mem` regions retain their configured placement;
* same-named internal functions in different objects receive object-qualified
  graph identities;
* direct calls stage all converted arguments in caller scratch before writing
  any callee parameter symbol.

The overlay changes physical addresses only; source and assembler symbols remain
function-qualified. Inline expansions inherit their enclosing ordinary
function's activation. Runtime global-initializer scratch remains outside the
overlay because calls hidden in its generated startup path are not yet represented
as ordinary source edges.

Atari 2600 hardware constraints
-------------------------------
* The VCS has 128 physical bytes of RIOT RAM at $80-$FF.
* $180-$1FF is a mirror of the same physical RAM, not separate stack RAM.
* Static storage and JSR/RTS/PHA/PHP stack use therefore compete for one pool.
* Every outstanding JSR consumes two physical RAM bytes until RTS.
* The 6507 has no usable IRQ or NMI inputs, so asynchronous interrupt re-entry
  is not the normal problem; program-controlled re-entry still is.
* Visible kernels have only 76 CPU cycles per scanline. Calls in kernels will
  eventually require an explicit policy or automatic inlining.

Current VCS RAM model
---------------------
File:

    libraries/vcs/vcs_4k.cfg

The linker models one physical RIOT RAM pool rather than independent RAM and
CPUSTACK regions. `vcs_4k.cfg` declares the full block:

    $80-$FF   128 physical bytes, with `callstack = callgraph`

Before layout, vcsc-ld shrinks that region from the top. For a maximum linked
source call depth D, the base reserve is `2 * D` bytes: two bytes for each
active JSR return address, including the assembly startup call into a source
root. If the linked image contains one or more runtime initializer functions,
vcsc-ld adds one fixed two-byte allowance because startup preserves its
init-table cursor while calling them. Ordinary generated calls push no
parameter, return, or scratch-base state.

For `01_solid_color`, D=2, so ordinary allocation receives $80-$FB (124 bytes)
and $FC-$FF is reserved. For the fully source-level Ode player, D=3, so ordinary
allocation receives $80-$F9 (122 bytes) and $FA-$FF is reserved. The bytes are
accessed through their page-1 mirrors by the 6502 stack pointer.

The map reports a `CALL STACK` block and the linker exports:

    __call_stack_depth
    __call_stack_extra
    __call_stack_size
    __call_stack_start
    __call_stack_top

A MEMORY region using `callstack = callgraph` may also set
`callstack_extra = N`. The linker adds those explicitly declared bytes to the
source-call and initializer reserve, rejects the option without call-graph
sizing, and reports it in the map. This covers known stack use hidden inside an
included assembly module without inventing a universal fixed stack partition.
The linker still does not infer arbitrary PHA/PHP/JSR or S manipulation from
inline or included assembly; each integration contract must declare its own
extra requirement.

Tests verify dynamic map sizing, a four-level path, overflow enforcement,
explicit hidden-stack reservation, and that the configuration declares the full
RIOT block without a separate CPUSTACK region.

Software-stack status
---------------------
`test/software_stack_inventory.pl` is the authoritative executable inventory.
Compiler source contains zero `_pushN` allocation sites and zero `_popN` cleanup
paths, and the runtime implementation has now been removed completely:

* `_vcsc_sp` is not allocated, exported, or initialized;
* `_pushN`, `_popN`, and every `sp2ptr*` helper are absent from source and the
  runtime archive;
* linker configurations no longer declare an `ARGSTACK` segment;
* compiled functions have no software-stack entry prologue;
* fixed-width multiplication and division/remainder helpers reuse
  compiler-owned expression scratch and select no private BSS or extra runtime
  zero-page cells.

Pooled fixed scratch is selected by a compile-time lease stack and addressed
directly through linker-resolved `__vcsc_scratch_N` symbols. `_vcsc_fp`, its
startup/runtime storage, the `fp2ptr*` helpers, and call-site save/restore code
are gone. The generic regression scans compiler/runtime source, generated code,
and the rebuilt archive so the removed machinery cannot quietly return.

Test policy
-----------
When a feature is removed:

1. delete positive tests whose purpose is to prove that feature works;
2. keep or add negative tests proving the compiler rejects it cleanly;
3. rewrite tests whose real subject remains useful to use legal types or
   out-parameters;
4. list every intentionally deleted path in `.top_secret/remove.txt`.

For the big/mixed-endian purge:

* target multibyte values are unconditionally little-endian;
* the compiler retains only direct rejection paths for `$endian:big`, `($big)`,
  and `($little)`;
* all big-endian and mixed-endian compiler branches and 37 big-endian nlib
  procedures were removed;
* 24 obsolete positive endian tests were intentionally removed and three direct
  rejection tests were added;
* all removed paths are in `.top_secret/remove.txt`.

For the wide-binary-integer purge:

* ordinary binary target integer declarations may be one through four bytes;
* `$bcd` declarations are the deliberate unsigned one- through four-byte
  packed-decimal family;
* target pointers must be two bytes;
* integer literals may carry up to 32 bits when a typed ordinary destination or
  operation supplies a matching width; the stock untyped default remains int16_t;
* positive 24/32/64-bit arithmetic, promotion, extension, shift, helper, and
  return tests were removed or rewritten to legal widths;
* PetiteFFS was removed because its public model requires a 32-bit DWORD;
* dead add/subtract/increment runtime assembly files were removed;
* host-side `long long`, `uint32_t`, and `uint64_t` used inside the compiler,
  assembler, and MD5 implementation are not target-language types and remain.

Inline assembly absolute-ref rules
----------------------------------
Inline assembly remains single-line and mostly opaque, but source-level
absolute `ref` identifiers in opcode operands are resolved by the compiler.
Official 6502 loads, compares, and arithmetic reads use the ref read address;
stores use the write address; ASL/LSR/ROL/ROR/INC/DEC and recognized unofficial
read-modify-write opcodes require both addresses to exist and normalize to the
same assembler expression.

The compiler rejects:

* a read instruction using a write-only `@[none/write]` ref;
* a store using a read-only `@[read/none]` ref;
* any read-modify-write instruction using a missing or differing side;
* immediate/control-address use of a ref without one identical read/write
  address;
* a ref operand under an opcode whose access behavior is unknown.

Assembler-local `@labels` are never treated as source identifiers. Inline asm
still does not track register or flag clobbers.
