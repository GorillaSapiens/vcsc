VCSC BANKSWITCHING AND SUPERCHIP PLAN
=====================================

Status
------
This is the detailed design and implementation roadmap for the broad project
roadmap items covering 8K-and-larger cartridge bankswitching and Superchip RAM.
It is an internal planning document, not installed user documentation. The
main roadmap in `.top_secret/context.txt` remains authoritative for project
ordering; this file owns the detailed order within those milestones.

The first implementation family is the ordinary full-window Atari schemes:

    F8      2 x 4K banks   8K total
    F6      4 x 4K banks  16K total
    F4      8 x 4K banks  32K total

Their Superchip variants follow after ordinary banking is stable:

    F8SC    2 x 4K banks plus shared 128-byte cartridge RAM
    F6SC    4 x 4K banks plus shared 128-byte cartridge RAM
    F4SC    8 x 4K banks plus shared 128-byte cartridge RAM

Segmented and unusual schemes such as 3F, 3E, E0, E7, FE, UA, and 0840 are not
part of the first implementation. The common model should avoid blocking them,
but it must not pretend that they are merely differently sized F8 cartridges.
DPC, DPC+, CDF, and coprocessor-assisted formats are separate projects.

Core model: use the missing address lines as the bank namespace
---------------------------------------------------------------
The 6507 has a 16-bit internal program counter but exposes only thirteen address
lines to the cartridge. A13-A15 do not reach the cartridge. VCSC can therefore
assign every physical 4K bank a distinct ordinary 16-bit logical range while
the cartridge sees every one of those ranges as the same $1000-$1FFF window.

Three bank identities must be kept separate.  Using the bare phrase "bank 0"
without saying which identity is meant is prohibited in this document and
should be avoided in diagnostics and user documentation:

1. VCSC logical bank name

   This is the source/linker namespace.  BANK0 is deliberately the home bank at
   $F000, BANK1 is at $D000, and so on.  `main`, startup, and the mandatory
   runtime live in VCSC BANK0.

2. Physical/file bank index

   This is the zero-based 4K chunk number in the emitted cartridge image.
   Physical/file bank 0 is the first 4096 bytes on disk.  Because VCSC writes
   banks in ascending logical-address order, physical/file bank 0 is the
   highest-numbered VCSC logical bank, not VCSC BANK0.  VCSC BANK0 is the last
   physical/file bank.

3. Mapper selector hotspot

   F8/F6/F4 selectors increase with physical/file bank index.  The first
   selector chooses the first 4K chunk on disk, the next selector chooses the
   second chunk, and so forth.  Since VCSC logical bank numbers run in the
   opposite direction, selector addresses decrease as VCSC BANKn increases.

Use the established descending VCSC logical convention:

    VCSC logical bank    linker range
    -----------------    ------------
    BANK0                $F000-$FFFF
    BANK1                $D000-$DFFF
    BANK2                $B000-$BFFF
    BANK3                $9000-$9FFF
    BANK4                $7000-$7FFF
    BANK5                $5000-$5FFF
    BANK6                $3000-$3FFF
    BANK7                $1000-$1FFF

Equivalently:

    logical_base(BANKn) = $F000 - (n * $2000)

F8 uses VCSC BANK0 and BANK1. F6 uses BANK0 through BANK3. F4 uses BANK0
through BANK7. Ordinary linker symbols and relocations remain 16-bit. No far
pointer or bank-qualified C pointer is required for this family.

The cartridge file is written in ascending logical-address order, beginning
with the lowest-address bank and ending with the highest-address bank. Therefore
VCSC BANK0 is always the final 4K chunk in the file:

    mapper  file index  VCSC bank  linker range  selector hotspot
    ------  ----------  ---------  ------------  ----------------
    F8      0           BANK1      $D000-$DFFF   $1FF8
            1           BANK0      $F000-$FFFF   $1FF9

    F6      0           BANK3      $9000-$9FFF   $1FF6
            1           BANK2      $B000-$BFFF   $1FF7
            2           BANK1      $D000-$DFFF   $1FF8
            3           BANK0      $F000-$FFFF   $1FF9

    F4      0           BANK7      $1000-$1FFF   $1FF4
            1           BANK6      $3000-$3FFF   $1FF5
            2           BANK5      $5000-$5FFF   $1FF6
            3           BANK4      $7000-$7FFF   $1FF7
            4           BANK3      $9000-$9FFF   $1FF8
            5           BANK2      $B000-$BFFF   $1FF9
            6           BANK1      $D000-$DFFF   $1FFA
            7           BANK0      $F000-$FFFF   $1FFB

The equivalent formulas for these full-window schemes are:

    file_index(BANKn) = bank_count - 1 - n
    hotspot(BANKn)    = first_mapper_hotspot + file_index(BANKn)

where the first mapper hotspot is $1FF8 for F8, $1FF6 for F6, and $1FF4 for
F4.  Thus the startup/home hotspot is always the last hotspot in the mapper's
range: $1FF9 for F8 and F6, and $1FFB for F4.

The linker emits those banks contiguously without the unused logical gaps
between $1FFF and $3000, $3FFF and $5000, and so on. File position, VCSC logical
address, and selector hotspot are three separate facts. The cfg records all
three relationships explicitly and the linker validates the complete table
rather than guessing from a name or relying on declaration order.

This convention also matches the common cartridge layout in which the final
chunk contains the $F000 home/reset code.  Existing ROMs are not normative for
VCSC naming: some assemble both physical banks at $F000, some use other mirrors,
and external documentation may call the first chunk "bank 0".  In VCSC,
uppercase BANK0 always means the $F000 home bank, never merely the first bytes
on disk.

For the first public F8/F6/F4 family, VCSC BANK0 is the required startup/home
bank and `main` always resides there. A later mapper family may revisit the
startup-bank rule as a separate decision.

Configuration model
-------------------
Add separate public linker configurations for the common schemes:

    vcs_8k_f8.cfg
    vcs_16k_f6.cfg
    vcs_32k_f4.cfg
    vcs_8k_f8sc.cfg
    vcs_16k_f6sc.cfg
    vcs_32k_f4sc.cfg

The first implemented cfg spelling uses `CARTRIDGE` and `BANKS` blocks plus a
`bank=NAME` property on cartridge-output `MEMORY` regions:

    CARTRIDGE {
        mapper = F8;
        fillval = $FF;
        trampoline = $0F00;
        trampolinesize = $00E0;
        vectorbridge = $0FE0;
    }

    BANKS {
        BANK0: start=$F000, size=$1000, hotspot=$1FF9, startup=yes;
        BANK1: start=$D000, size=$1000, hotspot=$1FF8, startup=no;
    }

    MEMORY {
        bank1:              start=$D000, size=$0F00, type=ro, bank=BANK1;
        BANK1_TRAMPOLINE:    start=$DF00, size=$00E0,          bank=BANK1;
        BANK1_VECTOR_BRIDGE: start=$DFE0, size=$0012,          bank=BANK1;
        BANK1_TAIL:          start=$DFF2, size=$0008,          bank=BANK1;
        BANK1_VECTORS:       start=$DFFA, size=$0006,          bank=BANK1;
        ROM:                 start=$F000, size=$0F00, type=ro, bank=BANK0;
        BANK0_TRAMPOLINE:    start=$FF00, size=$00E0,          bank=BANK0;
        BANK0_VECTOR_BRIDGE: start=$FFE0, size=$0012,          bank=BANK0;
        BANK0_TAIL:          start=$FFF2, size=$0008,          bank=BANK0;
        BANK0_VECTORS:       start=$FFFA, size=$0006,          bank=BANK0;
        /* shared RAM regions omitted */
    }

A bank description tells the linker the VCSC logical bank name and 16-bit range,
its mapper selector hotspot, whether it is the startup bank, and the full 4K
physical-bank size.  The output writer derives physical/file index from
ascending logical address, not from the numeric suffix in `BANKn`.  `MEMORY`
entries subdivide each full physical unit into allocatable ROM and
non-allocatable holes such as hotspots, vectors, and the common trampoline
corridor. `CARTRIDGE trampoline` gives the corridor's low-twelve-bit start and
`trampolinesize` gives its reserved capacity. Both are required for banked
profiles, must fit inside one 4K bank, and may not overlap the vector bridge,
vectors, or any selector hotspot.

The cfg parser rejects unknown blocks and properties. Silently ignoring a
misspelled bank or hotspot property would create a plausible-looking but dead
cartridge. MEMORY, SEGMENTS, and BANKS storage is dynamically sized rather than
limited to sixteen entries.

Every selector hotspot is reserved at the same low twelve-bit offset in every
physical bank, not merely in the bank selected by that hotspot. The linker
rejects a configuration when any ordinary allocatable code/data segment region
covers any declared selector byte. Vector-only ownership may use fixed bytes
which overlap mapper hotspots where the mapper requires it, but ordinary code
must never be placed there.

The implementation should model a physical bank as one 4K output unit even when
its allocatable ROM is split into ordinary code, a bridge area, reserved hotspot
bytes, and vectors. A bank may contain non-allocatable holes, but its emitted
file chunk remains exactly 4096 bytes.

Per-bank vectors and reset bridges
----------------------------------
Per-bank vectors and reset bridges are an early foundation item, not cleanup at
the end. Power-up bank state must not be assumed.

The implemented `CARTRIDGE vectorbridge` property gives one low-twelve-bit
corridor offset. The first implementation reserves eighteen bytes there in every
physical bank and emits three byte-identical six-byte entries:

    NMI entry:      BIT BANK0_HOTSPOT; JMP __nmi
    RESET entry:    BIT BANK0_HOTSPOT; JMP __reset
    IRQ/BRK entry:  BIT BANK0_HOTSPOT; JMP __irqbrk

Every physical bank also receives the same six vector bytes at its final six
physical offsets. All three vector words use BANK0's logical mirror of the
common entries, for example $FFE0, $FFE6, and $FFEC when `vectorbridge=$0FE0`.
The currently selected physical bank ignores those upper logical address bits,
fetches the identical entry at the same cartridge offset, and the entry selects
BANK0 before jumping to the ordinary runtime handler. BANK0 runs the same
sequence; selecting the already selected bank is harmless.

Using one identical vector image is deliberate. F4's $1FFA and $1FFB selector
hotspots overlap the NMI vector bytes.  Under the table above, the low-byte
fetch at $1FFA selects physical/file bank 6, which is VCSC BANK1; the high-byte
fetch at $1FFB then selects physical/file bank 7, which is VCSC BANK0.  Every
bank contains the same vector bytes, so the word is deterministic despite the
mid-vector bank changes, and the NMI fetch itself finishes with BANK0 selected.
The common NMI entry selects BANK0 again defensively before entering `__nmi`.
RESET and IRQ/BRK follow the same general bridge path, so BRK remains safe even
though the 6507 package exposes no ordinary NMI/IRQ inputs.

Ordinary placement must never consume the vector corridor, the six final vector
bytes, or any mapper hotspot. The linker rejects an allocatable code/data region
covering the configured eighteen-byte corridor or any selector byte, and it
rejects generated bridge/vector output which would overwrite placed material.
The normal DATA/BSS initialization and `main` entry live only in BANK0 rather
than being duplicated wholesale.

Bank-aware relocation rules
---------------------------
A cfg-defined bank identity, not just an arithmetic test on upper address bits,
determines whether two ROM locations are in the same physical bank. This also
handles Superchip banks whose allocatable ROM begins at $x100.

References from banked ROM obey these rules:

* A reference to ROM in the same bank is emitted normally.
* A reference to RIOT RAM, TIA, RIOT registers, or another explicitly shared
  nonbanked address is emitted normally from every bank.
* A direct cross-bank JSR is redirected through a generated call bridge.
* A direct cross-bank JMP is redirected through a generated one-way bridge.
* A cross-bank conditional branch is an error.
* A cross-bank ROM load, address constant relocation, pointer initializer, or
  other data reference is an error.
* Programmer-authored indirect cross-bank control flow remains unsupported.
  The linker-generated call/jump machinery may use an indirect JMP internally,
  but VCSC still rejects function pointers, so ordinary compiled calls remain
  visible to the linker.

The assembler/object format identifies direct control-transfer relocations as
JSR, JMP, or relaxed conditional branch. The two otherwise-unused low bits of
the o26 relocation type carry this intent without changing relocation
arithmetic or the version-2 object format. The linker does not infer semantics
by peeking at an opcode byte next to a generic word relocation. Existing
low-byte, high-byte, and word data relocations remain ordinary data references
and therefore cannot cross banks. Ordinary two-byte relative branches remain in
the B26 branch table and are checked from their final source and target
addresses after placement.

Roadmap items 5 and 6 install direct cross-bank JMP and JSR trampolines. A
proven direct transfer is rewritten to the source bank's logical mirror of a
deduplicated entry in the common replicated table. JMP entries are deduplicated
by final target and destination hotspot. JSR entries also include the statically
known source hotspot because their embedded return stub must restore that bank.
The linker never emits a raw mirrored cross-bank target address. This generated
control-flow support is intentionally different from the permanent prohibition
on cross-bank ROM data and conditional branches.

A programmer can always defeat relocation checks with a manually written raw
numeric address. That does not make such access supported; diagnostics cover
symbolic relocations the toolchain can prove.

Cross-bank call and jump bridges
--------------------------------
The complete linker-generated bridge table must occupy the same low twelve-bit
cartridge offsets and contain exactly the same bytes in every physical bank.
It is one common replicated image, not a separately generated per-bank table.
After a hotspot access changes the selected bank, instruction fetching continues
at the next byte in the newly selected bank; byte-for-byte identity is therefore
what makes every continuation safe.

The 6502 has no indirect JSR instruction, but a normal JSR can call a fixed
entry whose own JSR creates the synthetic return address before the entry
ultimately performs an indirect JMP. That is the generic cross-bank call
mechanism. The implemented fifteen-byte entry is:

    generated entry for source BANKs and target $DABC:
        JSR  body
    return_to_source:
        STA  source_hotspot
        RTS
    body:
        STA  destination_hotspot
        JMP  (BANK0-mirror address of inline_target)
    inline_target:
        .word $DABC

The call site's ordinary JSR first places its real return address on the
hardware stack. The generated entry's JSR then places the address immediately
before `return_to_source` above it, without modifying A, X, Y, or the processor
flags. `body` selects the target bank and enters the callee with the indirect
JMP. The target function's RTS increments the synthetic address and reaches the
identical return stub. That stub stores A to the caller's hotspot, preserving A
and flags while restoring the source bank, and executes a second RTS through the
call site's original return address.

Both the internal JSR operand and indirect-JMP pointer are encoded through
BANK0's logical mirror of the common table. The CPU may therefore change its
upper logical address bits while the cartridge continues to see the same low
twelve-bit offset. Every physical bank contains the same bytes at that offset,
so the entry remains valid before and after either bank switch. Entries are
deduplicated by source hotspot, destination hotspot, and final target. Nested
cross-bank calls naturally nest the two return addresses in LIFO order.

The implemented direct-JMP entry does not need a shared RAM pointer. Each
specialized eight-byte table entry carries its own immutable target word:

    generated entry for target $DABC:
        STA  destination_hotspot
        JMP  (BANK0-mirror address of inline_target)
    inline_target:
        .word $DABC

`STA` is deliberate: F8/F6/F4 switch on an access to the hotspot, and a store
changes neither A nor the processor flags. A direct JMP therefore preserves the
machine state that the original instruction would have preserved. The indirect
pointer operand always uses BANK0's logical mirror of the inline word. A13-A15
do not reach the cartridge, so that address reads the same low-twelve-bit table
offset from whichever physical bank is selected after the hotspot store. The
complete entry bytes are consequently identical in every bank.

The linker deduplicates entries by final target address and destination hotspot.
Every call site to one target jumps to its own source bank's logical mirror of
the same entry offset. The table allocator inserts a fill byte when needed so an
inline target word never begins at page offset $FF and cannot trigger the NMOS
6502/6507 indirect-JMP page-wrap bug. Corridor exhaustion is a link error which
reports the reserved range, target, entry count, and consumed bytes.

A cross-bank JMP never restores the source bank. It selects the destination and
continues at the final logical target. A cross-bank JSR restores the source bank
through its embedded synthetic return stub.

The linker reserves the common bridge corridor at the same physical offset in
every bank and emits one byte-identical table into every bank. Eight-byte JMP
entries and fifteen-byte source-aware JSR entries share that corridor. The map
reports occupied and total replicated bytes, separate entry counts and sizes,
and each transfer's source/destination identity. Exhausting the corridor is a
clear link error. The allocator inserts fill when either entry's inline target
word would begin at page offset `$FF`, avoiding the NMOS indirect-JMP wrap bug.

A cross-bank call keeps one additional hardware-stack return address live while
the destination function runs. For compiler-described call edges, the linker
computes both the ordinary longest function depth and a weighted depth which
adds one return-address slot for every simultaneously active cross-bank edge.
`callstack = callgraph` reserves two bytes per weighted slot and exports
`__call_stack_weighted_depth` and `__call_stack_bank_extra_slots` alongside the
existing stack symbols. Calls hidden in hand-written or separately assembled
code remain the integration's responsibility through `callstack_extra`.

Cross-bank data policy
----------------------
The first implementation deliberately has no far ROM data reads. Code and the
ROM tables it directly uses must live in the same bank. Data shared by multiple
banks may be duplicated or deliberately placed with each caller. A relocation
from one bank to a const object in another bank is a hard error, not an implicit
bank switch.

Ordinary C pointers stay 16-bit and bank-local for ROM. Taking the address of a
ROM object in another bank is rejected when represented by a relocation. No
hidden bank byte is added to pointer objects or function parameters.

Bank placement policy
---------------------
VCSC already has named `mem` regions and uses a region name as a declaration
modifier for objects. The same mechanism is now the source spelling for explicit
function placement; do not add special `bank0` through `bank7` language keywords.
For an ordinary F8 bank:

    mem bank1 { $start:0xD000 $size:0x0F00 $ro };

    bank1 void some_function(void) {
        /* ... */
    }

For a Superchip profile, the source `mem` declaration describes the allocatable
ROM interval, not the complete emitted physical bank. The RAM-port prefix and
the common `$xF00` trampoline corridor are excluded, leaving `$x100-$xEFF`:

    mem bank1 { $start:0xD100 $size:0x0E00 $ro };

The cfg/image model still emits the complete 4K physical bank and fills its
reserved `$D000-$D0FF` prefix separately. A `$size:0x0F00` region would collide
with the trampoline corridor; `$size:0x1000` would run beyond the logical bank.

Named region modifiers work on function definitions and produce private
layouts such as `CODE.bank1.__vcsc_function$some_function`. The assembler keeps
procedures in any `CODE` or `CODE.*` segment independently movable, and the
linker resolves the longest matching segment rule so `CODE.bank1` controls that
private layout. A declaration and its definition must use the same named region.
An inline function cannot use a region modifier because inline expansion has no
independently placeable linker layout.

Named `$ro` regions also pin constant ROM objects. For example:

    bank1 const uint8_t level_table[4] := { 1, 2, 3, 4 };

is emitted as `RODATA.bank1.__vcsc_object$level_table`. A definition in a `$ro`
region must be `const` and must have a link-time initializer; it cannot fall back
to DATA/BSS plus startup writes. This keeps the source declaration, o26 private
layout, and linker bank affinity honest. Ordinary writable named regions retain
their existing DATA/BSS behavior.

Unmarked private `CODE.__vcsc_function$...` and
`RODATA.__vcsc_object$...`/`RODATA.__vcsc_page$...` layouts are candidates for
automatic placement. `main` may be unmarked or explicitly marked `bank0`; an
explicit numbered nonzero bank on `main` is rejected. The linker pins unmarked
`main`, startup/non-private runtime material, and private runtime functions whose
reserved implementation names begin with `_` to the configured startup bank,
which is BANK0 in the public full-window profiles.

The implemented placement policy is constrained and deterministic:

* Named `mem` modifiers are hard pins for functions and ROM objects. A pinned
  private layout keeps the exact named MEMORY region, not merely the bank.
* Cross-bank ROM data is forbidden. Every relocation between ROM layouts other
  than a trampoline-eligible direct JSR/JMP, plus every retained branch edge,
  forms a hard same-bank relation. The linker collapses the transitive closure
  into indivisible placement components before assigning addresses.
* A hard component inherits any explicit or mandatory bank pin carried by one
  of its members. Conflicting pins in one component are a fatal diagnostic that
  names the component, layout, object, and incompatible banks.
* Direct JSR and direct JMP edges are soft relations because the replicated
  trampoline table can implement them. Repeated edges accumulate; the initial
  cost uses the actual per-entry replicated-table payload, 15 for JSR and 8 for
  JMP. This is a deterministic placement heuristic, not a claim about dynamic
  call frequency.
* Before packing movable components, the linker charges each ordinary ROM
  region for fixed initialized-data images and generated copy/zero/init tables.
  The largest `type=ro` MEMORY region owned by each bank is that bank's default
  automatic-placement region; named pins still use their exact region.
* Pinned components are assigned first in stable input order. Unpinned
  components are considered by decreasing byte size, then decreasing soft-edge
  degree, then stable object/layout order. Among banks with enough preliminary
  capacity, the chosen bank minimizes weighted edges cut against components
  already assigned. Ties prefer the startup bank, then the higher logical bank
  address, then the bank name.
* The preliminary budget catches clear capacity failures early. The normal
  layout allocator remains authoritative for alignment, page containment,
  branch-page constraints, and any holes those rules create.
* If no bank can hold a component, the diagnostic reports its size and the free
  ordinary-ROM capacity in every candidate bank. The linker never breaks a hard
  component, moves a hard pin, duplicates a function, or invents a cross-bank
  ROM-data access to make the image fit.

This first placer intentionally has no second placement language, explicit
same-bank-group attribute, translation-unit preference, profile-guided call
frequency, or local-search pass. Those can be added only when measured programs
show a need. Existing hard data edges already express the most important
same-bank grouping, while named `mem` modifiers give programmers a direct
steering wheel for timing-critical or architectural decisions.

The call graph alone is insufficient: ROM-data edges, explicit pins, reserved
trampoline/vector space, generated startup tables, and per-bank capacity all
matter. Conversely, requiring programmers to place everything manually throws
away whole-program information the linker already has. The hybrid policy keeps
normal use sane while preserving precise control for timing-critical code,
fixed architecture, debugging, and reproducible experiments.

A ROM table used by functions in several banks pulls those functions and the
table into one hard component unless the table is explicitly duplicated. If
that component carries incompatible pins or cannot fit, the link fails. The
linker never silently synthesizes a far ROM read. Functions and objects are not
duplicated automatically in this implementation.

Archive selection remains normal symbol-driven selection. Placement runs only
after the final object/archive-member set is known. The map's `BANK PLACEMENT`
section reports every component, pinned versus automatic assignment, owning
bank and concrete MEMORY region, component byte cost, incident cut weight, and
originating object. The `TRAMPOLINES` section then reports the actual generated
bridges. This makes placement reproducible and auditable rather than linker
astrology.

Superchip RAM using existing split-address references
-----------------------------------------------------
VCSC already supports split read/write absolute references:

    ref uint8_t object@[read_address/write_address];

Loads use the first address and stores use the second. Taking the address of a
split-address ref is already rejected. That is enough for explicit Superchip
RAM aliases without inventing a new pointer representation.

The SC cfg profiles reserve the bank prefix used by the RAM ports and keep
ordinary ROM code/data out of it by beginning each bank's allocatable ROM at
$x100, for example $F100 in BANK0 and $D100 in BANK1. Vectors remain at the top
of each logical bank. Even though allocation begins at $x100, the output writer
still emits a complete 4K bank and fills the reserved $x000-$x0FF prefix, so the
finished F8SC/F6SC/F4SC images remain 8K/16K/32K respectively.

The 128 bytes of cartridge RAM are shared across bank switches. Explicit refs
may name each byte or array using the scheme's read and write windows. The
scheme-specific VCS header should provide constants or helpers so applications
do not repeat magic port addresses.

Automatic allocation of variables into Superchip RAM is a required later
roadmap item, not a prerequisite for the first explicit-ref SC cartridge. It
will require more than cfg entries because an allocated object has one logical
identity but separate load and store addresses. The compiler/object/linker
contract must preserve both aliases for each allocated object:

* loads relocate against the read alias;
* stores relocate against the write alias;
* initializers and BSS clearing write through the write alias;
* address-taking and ordinary pointer decay are rejected until a sound split-
  address reference ABI exists;
* activation-overlay use is deferred until persistent globals and arrays are
  proven;
* map usage counts the shared 128 physical bytes once, not once per alias or
  once per bank.

Automatic allocation uses the existing named-memory declaration model rather
than adding a built-in `superchip` type or keyword.  An SC machine/profile
header will define a split-address region conceptually as:

    mem superchip {
        $read_start:  0xF080
        $write_start: 0xF000
        $size:        0x80
        $rw
    };

Applications then request ordinary allocated objects in that region:

    superchip uint8_t foo;
    superchip uint8_t buffer[32];

The ordering is deliberately the same as the already implemented explicit-ref
syntax: `@[read_address/write_address]`.  Thus the explicit spelling equivalent
to the first allocated byte is:

    ref uint8_t foo@[0xF080/0xF000];

Loads use `$F080+offset`; stores, BSS clearing, and initializer copies use
`$F000+offset`.  The source header supplies the region name and aliases so an
application does not repeat mapper constants.  The linker treats this as one
shared 128-byte physical allocation, not BANK0-owned storage merely because the
canonical aliases use the `$Fxxx` mirror.  Code in every selected bank may use
the same allocated object without a bank switch.

Normal cold-start startup initializes automatically allocated SC DATA/BSS just
as it initializes RIOT RAM, but stores through the write window. Bank switching
must not disturb SC RAM contents. Warm-reset behavior should follow the normal
VCSC startup contract unless a later explicit no-reinitialize entry point is
added.

Map, listing, and diagnostics
-----------------------------
A banked map should report at least:

* mapper/profile name and exact output size;
* each bank's logical range, selector hotspot, startup status, physical file
  offset, used bytes, free bytes, and reserved bytes;
* output order, proving that the lowest logical bank is written first and BANK0
  is written last;
* every per-bank vector and reset bridge;
* the byte-identical common trampoline table, its physical offset, reserved
  capacity, occupied and replicated size, inline target-passing ABI, direct-JMP
  entries, and later source entries/return stubs;
* every generated call/jump target entry, its source bank, destination bank,
  target, logical addresses, and byte cost;
* bridge corridor occupancy;
* weighted hardware-stack depth including cross-bank call edges;
* every placement component, its pinned or automatic status, capacity cost,
  and weighted call edges cut by the placer;
* every rejected or unresolved cross-bank data relocation with source and
  target symbols;
* Superchip RAM physical occupancy and read/write aliases when present.

Listings and symbol sidecars should retain ordinary 16-bit logical addresses.
Where ambiguity matters, they should additionally show the bank name and output
file offset. The raw `.bin` remains a contiguous cartridge image in the
ascending-logical-address bank order defined above.

Testing strategy
----------------
Every implementation slice needs both structural and execution tests.

Structural tests should verify exact image size, bank order, fill bytes, vectors,
hotspot reservations, logical symbol addresses, physical file offsets, bridge
bytes, deterministic placement, map output, and useful errors. Tests must prove
that BANK0 is the final physical bank in F8, F6, and F4 output.

Stella is the authoritative end-to-end execution environment for bank
switching and Superchip behavior.  `vcsc-sim` now consumes the public cfg
`CARTRIDGE`/`BANKS` descriptions and executes raw F8/F6/F4 images, which gives
fast deterministic RAM-signature and forced-start-bank diagnostics.  That
VCSC-owned mapper model is not independent evidence: finished cartridge images
must also run in Stella's F8/F6/F4 and later F8SC/F6SC/F4SC implementations.

Create a visible diagnostic cartridge, parameterized or separately built for
F8, F6, and F4, which:

* is run once with every physical/file bank forced as the initial power-on bank
  and also in repeated developer-mode runs with randomized startup-bank state;
* resets correctly from every initial bank, enters BANK0, and calls `main` there;
* exercises every possible ordered source-bank to destination-bank transition,
  including self-selection where useful, through direct selector accesses,
  cross-bank JMP, cross-bank JSR/return, and nested cross-bank calls;
* writes known source-bank, destination-bank, transition-number, and phase
  values into RIOT RAM before and after each switch, and verifies those values,
  the restored source bank, and the hardware-stack balance after each return;
* renders a distinctive PASS or FAIL sprite for every transition in a stable
  frame.  A failure indication should identify at least the source bank,
  destination bank, and failed phase so a screenshot is diagnostically useful;
* emits a final unmistakable all-pass frame only after every transition has
  completed, allowing the existing Stella screenshot/oracle machinery to grade
  the actual cartridge;
* retains exact frame length and performs mapper changes outside critical
  visible timing.

The Superchip versions of the diagnostic must additionally write distinct
patterns through the write window, read them back through the read window,
carry them across every tested bank transition, and display separate PASS/FAIL
results for alias direction, persistence, initialization, and bounds.  Stella
must be used to test both bank switching and Superchip operation; a local
interpreter that repeats VCSC's own assumptions is not sufficient certification.

Negative tests should cover cross-bank ROM reads, pointers, low/high-byte data
relocations, conditional branches, indirect control flow, bridge exhaustion,
invalid or duplicate hotspots, overlapping banks, malformed output order,
missing per-bank vectors, unknown cfg properties, and ROM placement in an SC
RAM-port prefix.

Detailed roadmap
----------------
The first unfinished leaf in this file is the next bankswitching-specific action
when main roadmap item 29 becomes active.

[x] 0. Record and lock the initial full-window design decisions.

       * Keep ordinary 16-bit symbols and bank-local ROM pointers.
       * Reject cross-bank ROM data references.
       * Write physical banks from lowest logical address to highest, placing

       * Use existing split-address refs as the explicit Superchip baseline.

[x] 5. Add the byte-identical common trampoline table and cross-bank JMP.

[ ] 15. Add Superchip-backed function return storage.

[ ] 16. Generalize function region modifiers into a code-region set and one

Decisions intentionally deferred
--------------------------------
The following are not settled by this document:

* the exact size/location of the common bridge corridor;
* whether non-public or future mapper profiles may use a startup bank other
  than BANK0 while still keeping public full-window profiles and `main` in BANK0;
* whether a later split-address allocated object can participate in ordinary
  `ref` parameter passing;
* whether measured programs justify profile-guided edge weights, explicit
  same-bank groups, translation-unit preferences, or a deterministic local-search
  pass beyond the completed greedy placer.

Those choices should be made in the roadmap slice that can implement and test
them, not guessed here and fossilized without evidence.
