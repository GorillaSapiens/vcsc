VCSC BANKSWITCHING AND SUPERCHIP PLAN
=====================================

Status
------
This is the detailed design and implementation roadmap for the broad project
roadmap items covering 8K-and-larger cartridge bankswitching and Superchip RAM.
It is an internal planning document, not installed user documentation. The
main roadmap in `.top_secret/context.txt` remains authoritative for project
ordering; this file owns the detailed order within those milestones.

The first implementation family is the ordinary full-window Atari schemes:

    F8      2 x 4K banks   8K total
    F6      4 x 4K banks  16K total
    F4      8 x 4K banks  32K total

Their Superchip variants follow after ordinary banking is stable:

    F8SC    2 x 4K banks plus shared 128-byte cartridge RAM
    F6SC    4 x 4K banks plus shared 128-byte cartridge RAM
    F4SC    8 x 4K banks plus shared 128-byte cartridge RAM

Segmented and unusual schemes such as 3F, 3E, E0, E7, FE, UA, and 0840 are not
part of the first implementation. The common model should avoid blocking them,
but it must not pretend that they are merely differently sized F8 cartridges.
DPC, DPC+, CDF, and coprocessor-assisted formats are separate projects.

Core model: use the missing address lines as the bank namespace
---------------------------------------------------------------
The 6507 has a 16-bit internal program counter but exposes only thirteen address
lines to the cartridge. A13-A15 do not reach the cartridge. VCSC can therefore
assign every physical 4K bank a distinct ordinary 16-bit logical range while
the cartridge sees every one of those ranges as the same $1000-$1FFF window.

Use the established descending logical convention:

    logical bank    linker range
    ------------    ------------
    BANK0           $F000-$FFFF
    BANK1           $D000-$DFFF
    BANK2           $B000-$BFFF
    BANK3           $9000-$9FFF
    BANK4           $7000-$7FFF
    BANK5           $5000-$5FFF
    BANK6           $3000-$3FFF
    BANK7           $1000-$1FFF

Equivalently:

    bank_base = $F000 - (bank_number * $2000)

F8 uses BANK0 and BANK1. F6 uses BANK0 through BANK3. F4 uses BANK0 through
BANK7. Ordinary linker symbols and relocations remain 16-bit. No far pointer or
bank-qualified C pointer is required for this family.

The cartridge file is written in ascending logical-address order, beginning
with the lowest-address bank and ending with the highest-address bank. Therefore
BANK0 is always the final 4K bank in the file:

    F8 file order:  BANK1, BANK0
    F6 file order:  BANK3, BANK2, BANK1, BANK0
    F4 file order:  BANK7, BANK6, BANK5, BANK4,
                    BANK3, BANK2, BANK1, BANK0

The linker must emit those banks contiguously without the unused logical gaps
between $1FFF and $3000, $3FFF and $5000, and so on. File position and logical
CPU address are separate facts, but file position is deterministic from the
ascending logical-bank order rather than an arbitrary bank-number ordering.

For the first public F8/F6/F4 family, BANK0 is the required startup/home bank
and `main` always resides there. The cfg still records the startup bank and its
hotspot explicitly so the linker validates rather than guesses the selector.
A later mapper family may revisit the startup-bank rule as a separate decision.

Configuration model
-------------------
Add separate public linker configurations for the common schemes:

    vcs_8k_f8.cfg
    vcs_16k_f6.cfg
    vcs_32k_f4.cfg
    vcs_8k_f8sc.cfg
    vcs_16k_f6sc.cfg
    vcs_32k_f4sc.cfg

The exact new cfg spelling is not yet locked, but a bank description must tell
the linker at least:

* the bank name and logical 16-bit range;
* the mapper/scheme family;
* the hotspot that selects that bank;
* whether it is the startup/home bank;
* the full physical bank size and output fill value;
* its ordinary ROM allocation range;
* its per-bank vector range;
* mapper-reserved addresses, including hotspots;
* the common same-offset area reserved for linker-generated bridges.

The cfg parser must reject unknown properties. Silently ignoring a misspelled
bank or hotspot property would create a plausible-looking but dead cartridge.
The current fixed limits on MEMORY and SEGMENTS entries must be replaced or
raised enough for an eight-bank configuration and its per-bank vectors,
reserved areas, and output regions.

The implementation should model a physical bank as one 4K output unit even when
its allocatable ROM is split into ordinary code, a bridge area, reserved hotspot
bytes, and vectors. A bank may contain non-allocatable holes, but its emitted
file chunk remains exactly 4096 bytes.

Per-bank vectors and reset bridges
----------------------------------
Per-bank vectors and reset bridges are an early foundation item, not cleanup at
the end. Power-up bank state must not be assumed.

Every physical bank receives its own six vector bytes at that bank's logical
mirror, for example $FFFA-$FFFF in BANK0 and $DFFA-$DFFF in BANK1. The vector
values must use that bank's logical high bits. Ordinary placement must never
consume vector bytes or mapper hotspot bytes. Some mapper hotspot ranges touch
or overlap otherwise conventional vector offsets, so the cfg and linker must
reserve them according to the selected scheme instead of applying one hardcoded
layout blindly.

Every bank also receives a tiny reset bridge at the same low twelve-bit offset.
Its reset vector points to the bridge using that bank's logical address. For the
first public full-window profiles, the bridge selects BANK0 and then continues
at the matching offset there, where it enters the normal VCSC startup path.
BANK0 uses the same bridge sequence; selecting the already selected bank is
harmless.

This gives deterministic startup regardless of which bank happened to be
selected before the reset vector fetch. The normal DATA/BSS initialization and
`main` entry live in BANK0 rather than being duplicated wholesale.
NMI and IRQ/BRK vector treatment must be defined per mapper and tested even
though the 6507 package does not expose ordinary IRQ/NMI inputs; BRK still uses
the IRQ vector.

Bank-aware relocation rules
---------------------------
A cfg-defined bank identity, not just an arithmetic test on upper address bits,
determines whether two ROM locations are in the same physical bank. This also
handles Superchip banks whose allocatable ROM begins at $x100.

References from banked ROM obey these rules:

* A reference to ROM in the same bank is emitted normally.
* A reference to RIOT RAM, TIA, RIOT registers, or another explicitly shared
  nonbanked address is emitted normally from every bank.
* A direct cross-bank JSR is redirected through a generated call bridge.
* A direct cross-bank JMP is redirected through a generated one-way bridge.
* A cross-bank conditional branch is an error.
* A cross-bank ROM load, address constant relocation, pointer initializer, or
  other data reference is an error.
* Programmer-authored indirect cross-bank control flow remains unsupported.
  The linker-generated call/jump machinery may use an indirect JMP internally,
  but VCSC still rejects function pointers, so ordinary compiled calls remain
  visible to the linker.

The assembler/object format must identify control-transfer relocations as JSR,
JMP, or conditional branch. The linker should not infer semantics by peeking at
an opcode byte next to a generic word relocation. Existing low-byte, high-byte,
and word data relocations remain ordinary data references and therefore cannot
cross banks.

A programmer can always defeat relocation checks with a manually written raw
numeric address. That does not make such access supported; diagnostics cover
symbolic relocations the toolchain can prove.

Cross-bank call and jump bridges
--------------------------------
The complete linker-generated bridge table must occupy the same low twelve-bit
cartridge offsets and contain exactly the same bytes in every physical bank.
It is one common replicated image, not a separately generated per-bank table.
After a hotspot access changes the selected bank, instruction fetching continues
at the next byte in the newly selected bank; byte-for-byte identity is therefore
what makes every continuation safe.

The 6502 has no indirect JSR instruction, but a normal JSR can call a fixed
bridge which ultimately performs an indirect JMP. That is the generic
cross-bank call mechanism. Conceptually:

    void jsr_trampoline(uint16_t target) {
        push_return_address(return_to_callers_bank);
        select_bank(bank_of(target));
        asm jmp (target);
    }

The caller's ordinary JSR has already placed its real return address on the
hardware stack. The trampoline pushes a synthetic return address above it,
switches to the target bank, and executes JMP through the target pointer. The
target function's RTS reaches the synthetic return stub. That stub selects the
caller's bank and executes a second RTS, which consumes the caller's original
return address.

A practical first implementation may reserve one two-byte RIOT RAM pointer such
as `__bank_target`. A direct cross-bank call is redirected to a generated target
entry in the common table. The entry stores the target's ordinary 16-bit logical
address in `__bank_target`, then jumps to an entry associated with the statically
known source bank:

    generated entry for source BANK0 and target $DABC:
        LDA  #<$DABC
        STA  __bank_target
        LDA  #>$DABC
        STA  __bank_target+1
        JMP  jsr_from_bank0

    jsr_from_bank0:
        LDA  #>(return_to_bank0 - 1)
        PHA
        LDA  #<(return_to_bank0 - 1)
        PHA
        ; Decode the high bits of __bank_target and select its bank.
        ...
        JMP  (__bank_target)

    return_to_bank0:
        BIT  bank0_hotspot
        RTS

The manually pushed address is one less than the return-stub address because
RTS increments the pulled address. Its logical high bits identify the source
bank's mirror of the common table. When the destination function returns, the
destination bank is still selected, but that bank contains the identical return
stub at the same physical offset. The BIT selects the source bank, and the final
RTS returns to the original caller.

The destination selector may be chosen by a common decoder using the target's
logical high bits. The linker may later specialize or fold that decoder for a
known target, but it must preserve the same indirect-JMP call semantics and the
single identical replicated table. A target entry can be shared by all call
sites with the same source bank and target symbol. Nested cross-bank calls work
because each active call contributes its own synthetic return address.

A cross-bank JMP uses the same target-pointer and destination-selection machinery
without pushing a synthetic return address:

    void jmp_trampoline(uint16_t target) {
        select_bank(bank_of(target));
        asm jmp (target);
    }

A direct cross-bank JMP is redirected to a generated target entry which fills
`__bank_target` and enters the common jump dispatcher. It never restores the
source bank.

The linker must reserve the common bridge corridor at the same physical offset
in every bank, emit one byte-identical table into every bank, place source-bank
entry points and return stubs within that table, and report its total replicated
cost. Exhausting the corridor is a clear link error. A cross-bank call keeps one
additional hardware-stack return address live while the destination function
runs, so whole-program hardware-stack sizing charges that edge two additional
bytes and reports the longest weighted path.

Cross-bank data policy
----------------------
The first implementation deliberately has no far ROM data reads. Code and the
ROM tables it directly uses must live in the same bank. Data shared by multiple
banks may be duplicated or deliberately placed with each caller. A relocation
from one bank to a const object in another bank is a hard error, not an implicit
bank switch.

Ordinary C pointers stay 16-bit and bank-local for ROM. Taking the address of a
ROM object in another bank is rejected when represented by a relocation. No
hidden bank byte is added to pointer objects or function parameters.

Bank placement policy
---------------------
VCSC already has named `mem` regions and uses a region name as a declaration
modifier for objects. The same mechanism is now the source spelling for explicit
function placement; do not add special `bank0` through `bank7` language keywords.
For an ordinary F8 bank:

    mem bank1 { $start:0xD000 $size:0x1000 $ro };

    bank1 void some_function(void) {
        /* ... */
    }

For a Superchip profile, the source `mem` declaration describes the allocatable
ROM interval, not the complete emitted physical bank. The RAM-port prefix is
therefore excluded with a 0x0F00-byte region:

    mem bank1 { $start:0xD100 $size:0x0F00 $ro };

Using `$size:0x1000` at `$D100` would incorrectly extend the allocatable range
through `$E0FF`; the cfg/image model still emits the complete 4K physical bank
and fills its reserved `$D000-$D0FF` prefix separately.

Named region modifiers now work on function definitions and produce private
layouts such as `CODE.bank1.__vcsc_function$some_function`. The assembler keeps
procedures in any `CODE` or `CODE.*` segment independently movable, and the
linker resolves the longest matching segment rule so `CODE.bank1` controls that
private layout. A declaration and its definition must use the same named region.
An inline function cannot use a region modifier because inline expansion has no
independently placeable linker layout.

The same names continue to place ROM objects, so programmers use one vocabulary
for code and data. Unmarked functions and objects remain candidates for
constrained automatic placement. `main` may be unmarked or explicitly marked
`bank0`; an explicit numbered nonzero bank on `main` is rejected. The eventual
bank-aware linker must pin unmarked `main`, the normal startup path, and mandatory
home-bank runtime material to BANK0.

Programmers may eventually need explicit same-bank groups or translation-unit
preferences, but those should extend named-memory metadata rather than introduce
a second bank-placement syntax. The intended policy is constrained automatic
placement:

* Named `mem` modifiers are hard pins for functions and ROM objects.
* Unpinned layouts are assigned automatically by the linker.
* Cross-bank ROM data references are forbidden, so every function and every ROM
  object it directly reads form hard same-bank constraints. The linker should
  collapse those constraints into indivisible placement components before
  packing.
* Direct call-graph edges are soft constraints. Keeping a caller and callee in
  one bank avoids a trampoline; cutting the edge is legal and incurs bridge ROM,
  cycles, and two bytes of live hardware stack while the callee runs.
* Explicit bank pins constrain the component containing the pinned layout. Two
  incompatible pins in one hard component are a link error.

The first automatic placer need not solve an expensive global optimization
problem. It should be deterministic, place hard components without overflow,
respect all pins, keep the `main` component in BANK0, and use a documented greedy
cost function which prefers fewer or more heavily weighted cross-bank calls.
Stable tie-breaking by symbol/object order is more valuable than a clever but
nondeterministic result. A later heuristic pass may improve packing without
changing the source contract.

The call graph alone is insufficient: ROM-data edges, hard placement groups,
assembly/layout constraints, reserved bridge space, and per-bank capacity all
matter. Conversely, requiring programmers to place everything manually throws
away whole-program information the linker already has. The hybrid policy keeps
normal use sane while preserving precise control for timing-critical code,
fixed architecture, debugging, and reproducible experiments.

A ROM table used by functions in several banks either pulls those functions
into one hard component, is explicitly duplicated, or causes an unsatisfied
placement error. The linker must never silently invent a cross-bank data read.
Functions are not duplicated automatically in the first implementation.

Archive selection remains normal symbol-driven selection. After members are
selected, every selected layout must have one legal bank placement. The map
must identify the owning object/archive member, whether each placement was
pinned or automatic, its hard component, and every resulting bridge.

Superchip RAM using existing split-address references
-----------------------------------------------------
VCSC already supports split read/write absolute references:

    ref uint8_t object@[read_address/write_address];

Loads use the first address and stores use the second. Taking the address of a
split-address ref is already rejected. That is enough for explicit Superchip
RAM aliases without inventing a new pointer representation.

The SC cfg profiles reserve the bank prefix used by the RAM ports and keep
ordinary ROM code/data out of it by beginning each bank's allocatable ROM at
$x100, for example $F100 in BANK0 and $D100 in BANK1. Vectors remain at the top
of each logical bank. Even though allocation begins at $x100, the output writer
still emits a complete 4K bank and fills the reserved $x000-$x0FF prefix, so the
finished F8SC/F6SC/F4SC images remain 8K/16K/32K respectively.

The 128 bytes of cartridge RAM are shared across bank switches. Explicit refs
may name each byte or array using the scheme's read and write windows. The
scheme-specific VCS header should provide constants or helpers so applications
do not repeat magic port addresses.

Automatic allocation of variables into Superchip RAM is a required later
roadmap item, not a prerequisite for the first explicit-ref SC cartridge. It
will require more than cfg entries because an allocated object has one logical
identity but separate load and store addresses. The compiler/object/linker
contract must preserve both aliases for each allocated object:

* loads relocate against the read alias;
* stores relocate against the write alias;
* initializers and BSS clearing write through the write alias;
* address-taking and ordinary pointer decay are rejected until a sound split-
  address reference ABI exists;
* activation-overlay use is deferred until persistent globals and arrays are
  proven;
* map usage counts the shared 128 physical bytes once, not once per alias or
  once per bank.

A likely future source model is a named Superchip memory region with separate
read and write bases, but its spelling is intentionally not fixed here. The
existing `@[read/write]` behavior is the semantic baseline.

Normal cold-start startup initializes automatically allocated SC DATA/BSS just
as it initializes RIOT RAM, but stores through the write window. Bank switching
must not disturb SC RAM contents. Warm-reset behavior should follow the normal
VCSC startup contract unless a later explicit no-reinitialize entry point is
added.

Map, listing, and diagnostics
-----------------------------
A banked map should report at least:

* mapper/profile name and exact output size;
* each bank's logical range, selector hotspot, startup status, physical file
  offset, used bytes, free bytes, and reserved bytes;
* output order, proving that the lowest logical bank is written first and BANK0
  is written last;
* every per-bank vector and reset bridge;
* the byte-identical common trampoline table, its physical offset, replicated
  size, reserved target pointer, source entries, return stubs, and destination
  decoder;
* every generated call/jump target entry, its source bank, destination bank,
  target, logical addresses, and byte cost;
* bridge corridor occupancy;
* weighted hardware-stack depth including cross-bank call edges;
* every placement component, its pinned or automatic status, capacity cost,
  and weighted call edges cut by the placer;
* every rejected or unresolved cross-bank data relocation with source and
  target symbols;
* Superchip RAM physical occupancy and read/write aliases when present.

Listings and symbol sidecars should retain ordinary 16-bit logical addresses.
Where ambiguity matters, they should additionally show the bank name and output
file offset. The raw `.bin` remains a contiguous cartridge image in the
ascending-logical-address bank order defined above.

Testing strategy
----------------
Every implementation slice needs both structural and execution tests.

Structural tests should verify exact image size, bank order, fill bytes, vectors,
hotspot reservations, logical symbol addresses, physical file offsets, bridge
bytes, deterministic placement, map output, and useful errors. Tests must prove
that BANK0 is the final physical bank in F8, F6, and F4 output.

Execution tests should use the VCSC simulator after it learns the selected
mapper, plus Stella where appropriate. A minimal diagnostic cartridge should:

* reset correctly no matter which bank is selected initially;
* enter BANK0 and call `main` there;
* call into every other bank through the replicated indirect-JMP trampoline
  table and return correctly;
* perform nested cross-bank calls;
* perform a one-way cross-bank jump;
* preserve RIOT RAM and, for SC variants, cartridge RAM across switches;
* expose a distinct visible or RAM signature from every bank;
* retain exact frame length while switching outside critical visible timing.

Negative tests should cover cross-bank ROM reads, pointers, low/high-byte data
relocations, conditional branches, indirect control flow, bridge exhaustion,
invalid or duplicate hotspots, overlapping banks, malformed output order,
missing per-bank vectors, unknown cfg properties, and ROM placement in an SC
RAM-port prefix.

Detailed roadmap
----------------
The first unfinished leaf in this file is the next bankswitching-specific action
when main roadmap item 29 becomes active.

[x] 0. Record and lock the initial full-window design decisions.

       * Use descending mirrored logical ranges with BANK0 at $F000.
       * Keep ordinary 16-bit symbols and bank-local ROM pointers.
       * Reject cross-bank ROM data references.
       * Write physical banks from lowest logical address to highest, placing
         BANK0 last in the cartridge file.
       * Use existing split-address refs as the explicit Superchip baseline.

[x] 1. Extend existing named `mem` region modifiers to function code.

       * Emit a function marked `bank1` into `CODE.bank1` and preserve each
         procedure as an independent private o26 layout.
       * Resolve `CODE.bank1.__vcsc_function$NAME` through the exact
         `CODE.bank1` linker segment rule before falling back to `CODE`.
       * Emit and validate the same source mem-region metadata used by objects.
       * Require declarations and definitions to agree on their region.
       * Reject region modifiers on inline functions and explicit numbered
         nonzero-bank placement of `main`.
       * Test ordinary and Superchip-sized function regions, including the
         correct `$D100+$0F00` allocatable SC interval.

[ ] 2. Extend the cfg parser and linker image model for multiple full 4K banks.

       * Add explicit mapper/bank/startup/hotspot metadata.
       * Remove fixed table limits that prevent an eight-bank configuration.
       * Reject unknown cfg properties and conflicting bank definitions.
       * Group allocatable regions, reserved holes, and vectors into exact 4K
         physical output units.
       * Emit bank units in ascending logical-address order with no logical gaps
         in the file; prove BANK0 is last.
       * Preserve the current unbanked `vcs_4k.cfg` output byte-for-byte.

[ ] 3. Add per-bank vectors and same-offset reset bridges.

       * Emit valid vectors in every selected physical bank.
       * Point each reset vector at that bank's logical mirror of a common bridge
         offset.
       * Select BANK0 and enter the normal startup path containing `main`.
       * Test reset from every possible initial bank before adding ordinary
         cross-bank calls.
       * Reserve mapper hotspots correctly even where they touch vector offsets.

[ ] 4. Add bank-aware relocation classification and validation.

       * Preserve JSR, JMP, and conditional-branch relocation intent in o26.
       * Identify same-bank, shared-memory, and cross-bank references from cfg
         bank identities.
       * Continue emitting same-bank ROM and shared RAM/hardware references
         normally.
       * Reject cross-bank branches, data reads, address constants, pointer
         initializers, and low/high/word data relocations with source-located
         diagnostics.

[ ] 5. Add the byte-identical common trampoline table and cross-bank JMP.

       * Reserve one deterministic bridge corridor at the same physical offset
         in every bank and copy exactly the same table bytes into every bank.
       * Reserve one shared two-byte target pointer or define an equally precise
         target-passing ABI.
       * Redirect a direct cross-bank JMP to a generated target entry, select the
         destination bank, and finish with `JMP (target)`.
       * Deduplicate equivalent target entries, report replicated and per-entry
         costs, and diagnose bridge-corridor exhaustion.

[ ] 6. Add JSR-to-indirect-JMP cross-bank calls and return stubs.

       * Redirect a direct cross-bank JSR to a generated target entry in the
         common replicated table.
       * Push a synthetic return-stub address for the statically known source
         bank, select the target bank, and enter the callee with `JMP (target)`.
       * Restore the caller's bank in the identical common return stub, then RTS
         through the original call-site return address.
       * Support nested cross-bank calls and add two bytes of weighted hardware-
         stack cost for every active cross-bank edge.

[ ] 7. Add placement constraints and deterministic automatic bank placement.

       * Pin `main`, startup, and mandatory home-bank runtime material to BANK0.
       * Use existing named `mem` modifiers for hard function/object affinity;
         design only any additional same-bank grouping or translation-unit
         preference metadata that measured programs require.
       * Build hard placement components from cross-bank-forbidden ROM-data
         edges and explicit grouping/pinning constraints.
       * Automatically place unpinned components with a deterministic greedy
         call-graph-aware cost function while respecting capacity and pins.
       * Report pinned versus automatic placement, cut call edges, bridge cost,
         and clear overflow or contradictory-pin diagnostics.

[ ] 8. Add and certify `vcs_8k_f8.cfg`.

       * Build a two-bank diagnostic with BANK1 first and BANK0 last in the file.
       * Verify reset from either initial bank, `main` in BANK0, automatic and pinned
         placement, cross-bank JMP, JSR-to-indirect-JMP calls, nested return,
         vectors, selector use, map output, and exact 8192-byte
         image size.

[ ] 9. Add F6 and F4 through the same implementation.

       * Add `vcs_16k_f6.cfg` and `vcs_32k_f4.cfg` without mapper-specific linker
         forks.
       * Exercise every bank, every selector, per-bank reset, nested calls, file
         order, reserved hotspots, and exact 16K/32K sizes.
       * Keep BANK0 at $F000 and last in both files.

[ ] 10. Make archive selection, listings, map output, and simulator execution
       fully bank-aware.

       * Preserve normal lazy archive-member selection.
       * Report each selected member's bank placement and every bridge.
       * Teach `vcsc-sim` to execute F8/F6/F4 using the same mapper description
         or an equivalent generated sidecar.
       * Add Stella-backed visible signatures and stable-frame tests.

[ ] 11. Add explicit-ref Superchip profiles.

       * Add `vcs_8k_f8sc.cfg`, `vcs_16k_f6sc.cfg`, and `vcs_32k_f4sc.cfg`.
       * Begin ordinary ROM allocation at $x100 in every bank, reserve the RAM
         port prefix, and still emit a complete 4K physical bank.
       * Publish scheme constants/helpers for existing
         `ref uint8_t object@[read/write]` declarations.
       * Verify shared 128-byte persistence across every bank switch and exact
         8K/16K/32K output sizes.

[ ] 12. Add Automatic allocation of variables into Superchip RAM.

       * Define a named allocated-memory contract with separate read and write
         bases for one shared 128-byte physical region.
       * Preserve both aliases through compiler metadata, o26, linker layout,
         loads, stores, initialization, and map output.
       * Start with persistent globals and arrays.
       * Reject address-taking, pointer decay, and unsupported `ref` passing.
       * Count physical occupancy once and provide deterministic overflow
         diagnostics.

[ ] 13. Integrate automatic Superchip initialization and lifecycle tests.

       * Clear SC BSS and copy SC DATA through the write window during normal
         startup.
       * Prove that bank switches preserve SC contents.
       * Define reset/reinitialization behavior explicitly.
       * Add map, simulator, Stella, and installed-toolchain coverage.
       * Consider activation-overlay placement only after persistent allocation
         is stable and measured.

[ ] 14. Add banked renderer or multisprite profiles only after the generic
       cartridge tests are stable.

       * Keep mapper behavior out of renderer timing code except for explicit
         switch points outside beam-critical paths.
       * Measure bridge, ROM, RIOT RAM, Superchip RAM, and hardware-stack costs.
       * Do not multiply cfg files into every renderer x mapper combination
         without first defining a maintainable composition mechanism.

[ ] 15. Improve automatic placement heuristics without changing semantics.

       * Measure whether call-frequency weighting, component ordering, or local
         moves materially reduce bridge count, cycles, and hardware-stack cost.
       * Keep all explicit pins and hard ROM-data components inviolate.
       * Preserve deterministic output and offer a diagnostic mode which explains
         why each component was placed where it was.
       * Permit a simple-placement mode for debugging and reproducibility; never
         fall back to invented cross-bank data access.

[ ] 16. Design the next mapper family separately.

       * Choose among fixed-plus-switchable-window schemes such as 3F/3E or
         segmented schemes such as E0/E7 based on an actual project need.
       * Reuse logical mirror, vector, output, relocation, and reporting pieces
         where honest, but add a true window model rather than forcing the
         mapper into the full-window F8/F6/F4 abstraction.

Decisions intentionally deferred
--------------------------------
The following are not settled by this document:

* the final cfg property names and punctuation;
* the exact size/location of the common bridge corridor;
* whether non-public or future mapper profiles may use a startup bank other
  than BANK0 while still keeping public full-window profiles and `main` in BANK0;
* whether a later split-address allocated object can participate in ordinary
  `ref` parameter passing;
* the first deterministic automatic-placement cost function and whether later
  optimization passes justify their complexity.

Those choices should be made in the roadmap slice that can implement and test
them, not guessed here and fossilized without evidence.
