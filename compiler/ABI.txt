If you're not respecting the ABI, you're one segfault away from chaos.

Current transitional function ABI
---------------------------------

This document describes the ABI while the compiler is being reduced for the
Atari 2600. Fixed parameters and named automatic locals use callee-owned
symbols. Ordinary direct calls, truth tests, comparisons, simple fixed-symbol
assignments, casts, absolute-binding conversion, built-in increment/decrement,
compound assignment, pointer/index lvalues, braced and runtime-global
initializers, bit-field helpers, switch expressions, and all builtin operator
families use function/depth-pooled fixed scratch. Compiler source emits no
`_pushN` or `_popN`.

Function returns
----------------

Every legal function return is one of:

* `void`: no returned value;
* one- through four-byte ordinary little-endian integer;
* one- through four-byte packed-BCD little-endian integer;
* 16-bit pointer.

Functions may not return aggregates, arrays, floating-point values, or other
non-scalar objects. The stock interface and compiler/memory-return ABI expose
ordinary binary integers through 32 bits. `bcd24_t` and `bcd32_t` are also legal return types.

Inside a value-returning function, `$$` is the source-level return object. It is
an exact-sized hidden callee-owned symbol named `function$__return`. By default
that symbol is in zero page. One writable `mem` modifier on the function instead
selects the return object's region; the region may be ordinary or split-address:

```
mem ports { $read_start:0x3003 $write_start:0x5007 $size:0x0008 $rw };
ports uint16_t sample(void);
```

This changes only the storage of the existing memory-return ABI; it does not
introduce register returns or a second calling convention. `return expr;`
writes the converted value to `$$`; `return;` leaves any value explicitly
written there intact. Ordinary named result storage uses the declared address
and may be zero-page or absolute. For split storage, writes use the region's
write alias and reads of `$$` use its read alias. The common epilogue for every
value width is simply:

rts

The callee does not load A, X, or Y with the result. The return-object symbol is
exported with every non-static definition. A separately compiled caller imports
it only when it consumes the call result. Default and named zero-page return
symbols use zero-page imports. Named absolute and split return symbols use
absolute imports. Function ABI metadata records the result-region identity and
address class, or for split storage the region, read-start, and write-start.

Returned-local coalescing
-------------------------

A non-inline value-returning function may use the hidden return object as the
backing storage for one automatic local when every return expression is exactly
that same local. The local and `$$` then name one allocation and the compiler
omits the final local-to-return copy. This is an internal allocation
optimization, not a second ABI: the externally visible symbol remains
`function$__return`, callers use the same read address and width, and replicated
function bodies still share the same one result object.

The compiler proves exact compatibility before coalescing. Value type,
declarator shape, top-level const qualification, pointer access capability,
size, named-memory identity, zero-page/absolute placement, and the complete
split read/write mapping must all match. An explicit local region and function
result region must have the same name even if two declarations currently use
identical numeric addresses. The optimization is disabled when returns name
different locals or an expression, when source explicitly accesses `$$`, when
the local's address may escape through address-taking or `ref`, or when inline
assembly prevents typed escape analysis. Passing the local by value does not
itself prevent coalescing.

For split-address storage, the one allocation retains its two aliases: local and
`$$` reads use the read window, while initialization and later writes use the
write window. Linker metadata is reporting-only and records the function, source
local, ABI return symbol, region, width, and the relocated allocation address.

Replicated immutable object contract
------------------------------------

A file-scope `const` object with more than one named `$ro` modifier is one logical
object with one physical ROM copy in each listed region. Its ABI metadata records
`replicated_ro(regions=[...])` using a sorted region set, so declaration order is
not significant. Every reference is relocated to the copy in the referencing
function's bank. A bank-pinned reference with no local copy is invalid; no
cross-bank data load or fat address is synthesized. The copies may have different
low-twelve-bit offsets. Mutable duplication, writable or split-address regions,
and duplicate region names are rejected.

Function region contract
------------------------

Named function modifiers are classified by their `mem` attributes, never by
special spellings. Read-only modifiers form an order-insensitive code-placement
set. One writable modifier, when present, selects the hidden return object's
storage independently of code placement. Thus declarations equivalent to
`bank0 cartram uint8_t sample(void)` and
`cartram bank0 uint8_t sample(void)` have the same ABI contract: code in
`bank0`, result storage in `cartram`.

With no read-only modifier, code placement remains automatic. With no writable
modifier, return storage remains the ordinary default. A writable modifier is
invalid on `void`, and at most one writable region is permitted.

A code-region set containing more than one `$ro` region is an explicit
replication contract. The compiler emits one logical function definition plus
replication metadata for every region; the linker materializes an identical body
in each listed ROM region. A direct call binds to the copy in the caller's bank
when one exists. Otherwise the normal cross-bank call machinery may target the
deterministic primary copy. One optional writable result region remains a single
shared hidden return object for all bodies. It is never replicated as code.

Same-translation-unit compatibility and linker metadata compare the
order-insensitive code-region set and result-storage region as separate facts.
Changing either is an ABI mismatch. Function pointers remain unsupported, so no
runtime representation for selecting among replicated body addresses is defined.

For selector-controlled cartridge profiles, `$bankcall` opts into the
public cross-bank direct-call ABI defined by `../BANKSWITCHING.md`. The target
ABI uses a six-byte `JSR` plus three-byte `.banktarget` payload: a 16-bit target
CPU address followed by one mapper-defined destination descriptor byte. Source
bank identity is supplied by a descriptor baked into the caller bank's
trampoline instance and carried on the hardware stack; neither source nor
destination bank identity is inferred from a 16-bit PC. Same-bank calls remain
ordinary JSRs. The generic return path preserves A:X return values and performs
the final RTS to the unchanged logical continuation PC.

The compiler/assembler/linker implement the three-byte `.banktarget` field.
F8/F6/F4(+SC), FA, DPC, FA2-24/28, JANE, 0840, UA/UASW, 0FA0, and WD
consume the descriptor end-to-end. Experimental earlier bank-call encodings are not accepted
as compatibility ABIs. `../BANKSWITCHING.md` is the authoritative public ABI.

Before an ordinary direct call, arguments are evaluated left-to-right. A
converted argument is copied directly into its callee-owned parameter as soon
as it is safe. Only an earlier value which must survive a function call in a
later argument remains in caller-owned scratch. Call-free argument lists use one
reusable conversion slot sized for the largest argument rather than a block
sized for the whole list. A scratch lease is a compile-time choice of a fixed
symbol; it has no runtime pointer and emits no activation/deactivation
instructions.

If the enclosing expression consumes the return value, the caller copies the
exact width from the callee's return object's read address into its destination.
For split storage the callee wrote the corresponding write alias. No register
preservation and no return-only scratch lease are required. Ignored return
values require no copy.

Scratch is lifetime-colored within its runtime activation owner. Every
compiler-owned temporary receives a compile-time lease that remains live through
its final copy-out or side effect. Sequential statements, mutually exclusive
branches, loop iterations, and separate inline expansions therefore reuse the
same depth slot; nested leases that are live together receive deeper disjoint
slots. Inline expansions inherit the caller's activation owner, so textual
expansion names do not create permanent scratch groups. Parameters, automatic
locals, scratch, and the return object are emitted as pieces of one logical
function activation. At link
time, a weighted whole-program call graph keeps every caller/callee pair
disjoint while overlaying siblings and other mutually exclusive activations.
Each scratch slot is emitted at the maximum size observed for that lifetime
depth. Scratch leases are compile-time LIFO records, and compilation fails if
any lease remains live at the end of code generation. Compiler scratch cannot
be named, addressed, made volatile, or referenced by inline assembly, so no
scratch value can escape its lease or remain live across a statement join or
loop back-edge.

Function entry has no software-stack prologue. Named automatic locals and the
return object already have fixed symbols. Expression temporaries are addressed
directly through their linker-resolved `__vcsc_scratch_N` symbols. A purpose-
specific `ptr0`/`ptr1` indirect address is prepared only when a dynamic or
out-of-range offset actually requires one.

Every entry through reset/startup initializes the 6502 hardware stack. The full
startup copies DATA, clears BSS, and walks init tables. When the linked program
has no DATA, runtime initializer, or startup-zero requirement outside ordinary
RIOT RAM, the linker instead selects the compact startup, which clears the whole
RIOT RAM block directly. Copy and zero records in the full path carry the runtime
write address, so split-address storage is initialized through its write alias;
its readable alias is reporting and subsequent-load metadata. Mapper bank
switches do not run startup and preserve shared writable storage, while a reset
reestablishes every allocated object's declared initial state. There is no
runtime frame pointer or software stack pointer. The runtime exposes
exactly eight independently linked zero-page bytes: one byte each for `arg0`
and `arg1`, plus two bytes each for `ptr0` through `ptr2`. Startup selects the
complete set. Fixed-width shifts, multiplication, division, and remainder use
those pointers plus compiler-owned expression scratch; no scalar helper owns
private BSS or selects additional runtime workspace.
The linker reserves two hardware-stack bytes per active JSR return address.
Startup tail-jumps to `main`, so `main` itself contributes no impossible entry
return slot; calls made by `main` contribute normally. If one or more runtime
initializer functions are linked, the linker also reserves one fixed two-byte
allowance because full startup preserves its init-table cursor while calling each
initializer. Selecting the full table-driven startup also reserves its real
two-byte transient PHA/PLA workspace; the compact startup needs neither allowance.

A, P, X, and Y are caller-clobbered across ordinary function calls. None carries
a language-level return value. Special assembly APIs may document stronger
register contracts, but ordinary VCSC calls do not.

The program entry point has exactly the signature `void main(void)`. `main` is
non-returning at the ABI level: stock startup enters it with `JMP`, and every
source-level `return;` or fall-through from `main` reaches `JMP ($FFFC)`, which
re-enters the reset vector rather than executing `RTS`.

The decimal-mode flag is not part of the call ABI. Startup executes CLD, and
compiler-generated packed-BCD addition/subtraction emits a local SED/CLD pair
around only its ADC/SBC chain. Packed-BCD multiplication, division, and
remainder by a constant power of ten, remainder by two or five, and fused digit
windows use inline byte/nibble moves, shifts, and masks and do not set decimal
mode. Cheap constant multiplication represented as two shifted decimal terms
uses one local SED/CLD pair for its final add or subtract.
Compiled code therefore enters and leaves normal expression and call
boundaries with decimal mode clear. Inline assembly
that sets decimal mode must clear it before returning control to generated code.

NOTE: If a special-case wrapper needs to preserve both A and P, and wants P
exactly as it was, it must pull P last:

PHP      ; save status
PHA      ; save A
...
PLA      ; restore A (and flags get set from A)
PLP      ; restore original status flags, including N/Z

Source-level inline functions
-----------------------------

Inline functions do not have a callable ABI. The complete source definition is
expanded at each call site after the normal direct-call type and argument
checks. Each expansion receives private parameter, automatic-local, return, and
label symbols. Arguments are evaluated left-to-right; a ref parameter receives
an address and dereferences it in the body. Returns converge on a private join
label.

No inline function symbol, parameter export, return-object export, ABI metadata,
JSR, RTS, or hardware-stack level is emitted for the inline function itself.
Ordinary calls appearing in the expanded body still use this document's normal
ABI and count as calls made by the enclosing ordinary function. Recursive and
mutually recursive inline-expansion cycles are compile-time errors.

Expansion storage is intentionally not shared or overlaid. This is conservative
in RAM but prevents an ordinary call inside one expansion from corrupting that
expansion if the callee contains a different expansion of the same inline
helper. Inline assembly has no additional ABI protection merely because it is
inside an inline function.

Direct fixed-parameter ABI
--------------------------

Every non-void parameter of a directly named function has a
callee-owned symbol. Ordinary parameters use BSS-backed absolute symbols;
parameters explicitly assigned to a zero-page memory region use zero-page
symbols. A value parameter may also select any named split-address writable
region.

The caller evaluates argument expressions from left to right. After conversion,
an argument is copied immediately to its callee-owned parameter object unless
its value must survive a function call in a later argument. Only those earlier
values remain staged in caller-owned scratch. Once all argument expressions
finish, the caller copies the staged values and issues JSR. Call-free argument
lists therefore use one reusable conversion slot sized for the largest
argument, rather than one block sized for the complete list. For a split
parameter every final copy, immediate or delayed, uses the region's write
alias; callee loads use the read alias and callee stores use the write alias.

Parameters may use ordinary binary integers through four bytes and `bcd8_t`,
`bcd16_t`, `bcd24_t`, or `bcd32_t`. Linker-visible ABI fingerprints distinguish
packed-BCD storage from same-sized ordinary unsigned integers and include a
split value parameter's region identity plus read/write aliases, so separately
compiled declarations cannot silently disagree about either representation or
storage.

Every `ref` parameter has one pointer-sized callee-owned symbol. `ref const T`
receives the argument's read address, `ref writeonly T` receives its write
address, and ordinary `ref T` requires both locations to exist and be identical.
Thus a genuinely split or one-sided object may bind to the matching directional
contract without changing the one-address ABI, but it cannot bind to ordinary
`ref T`. The selected address is determined from the formal parameter type at
the call site, not from callee-body analysis.

A direct call therefore places no fixed parameter bytes on the software stack
and allocates no software-stack call frame. Argument conversion uses a live
caller-function `__vcsc_scratch_N` lease when needed; its reserved size is the
bytes which must survive later calls plus one reusable slot for the largest
remaining argument. Return values are read directly from the callee-owned
`function$__return` symbol; scratch belongs to the caller and is not part of the
callee ABI.

Every function body owns one logical activation record containing its
parameters, automatic locals, expression scratch, and return object when
present. Automatic locals may select an ordinary writable memory region or a
split-address region such as Superchip RAM. Split locals retain one physical
allocation while generated loads use the read alias and stores and declaration
initializers use the write alias. Inline-expansion-private locals obey the same
rule. The linker overlays records by weighted call-graph lifetime independently
within each physical memory region. No function may be active twice. The compiler rejects
direct and mutual cycles inside a translation unit, and the linker rejects
cycles completed across objects.

Function pointers and indirect calls are not part of the VCS ABI. Every call
target is directly named, allowing compiler/linker call-graph analysis to see
every edge. Function-pointer declarators and function names used as values are
compile-time errors, and the `_callptr0` runtime trampoline no longer exists.


One-address pointer and reference access qualification
-----------------------------------------------------

Ordinary `T *`, `const T *`, and `writeonly T *` all use the target's normal
16-bit pointer representation. The corresponding `ref T`, `ref const T`, and
`ref writeonly T` contracts also pass exactly one 16-bit address. The qualifier
constrains access through that address rather than changing storage width or
byte order:

* `T *` permits reads, writes, and read-modify-write operations.
* `const T *` permits reads but rejects stores through the pointer.
* `writeonly T *` permits pure stores but rejects loads and every operation
  which performs a hidden read, including compound assignment,
  increment/decrement of the pointed-to object, and packed-bitfield updates.

An ordinary pointer or read/write ref may implicitly lose capability by
conversion to either restricted form. A restricted pointer or ref cannot
implicitly regain read/write capability, and `const` and `writeonly` forms do
not implicitly convert to one another. Pointer arithmetic, comparison, and
copying preserve pointer qualification; forwarding a ref preserves or narrows
its contract.

Access qualification is part of the canonical type fingerprint for globals,
function returns, value parameters, ref parameters, use contracts, and
aggregate members. Ref parameter metadata records `ref(access=const)`,
`ref(access=writeonly)`, or `ref(access=read/write)`. The linker therefore
rejects separately compiled declarations which disagree on access capability
even though all forms occupy the same two bytes. The qualifier is not a storage
region and does not alter call-graph activation accounting.

Directional address projection
------------------------------

Unary `&<` and `&>` preserve the one-address pointer ABI while selecting one
side of an lvalue's generic address metadata. `&<lvalue` yields the exact read
address as `const T *`; `&>lvalue` yields the exact write address as
`writeonly T *`. Forming either pointer evaluates the lvalue location once and
performs no object load or store.

The selected address may be an ordinary object symbol, a split-region symbolic
alias, or an absolute external binding term. Constant initializers retain the
same relocatable expression and offset used at runtime. No region name, alias
ordering, spacing, or contiguity is encoded in the operator. A missing selected
side is a compile-time error. Plain `&` yields ordinary `T *` only when the
lvalue has one conventional address compatible with read/write access; distinct
or one-sided addresses require an explicit directional projection.

The result's `const` or `writeonly` capability participates in the same type and
ABI fingerprints described above. The operators add no fat-pointer object,
hidden second address, calling-convention field, or storage allocation.


Absolute external binding ABI
-----------------------------

A file-scope or block-scope object declared with `@[read/write]` is a non-owning
absolute external binding. The annotation itself supplies the object's access
locations; `ref` is not an object-storage modifier and is reserved for function
parameters. Absolute bindings allocate no BSS, DATA, zero-page, or named-region
bytes and cannot have initializers or allocation/linkage modifiers.

Every absolute binding also emits a range record containing its canonical read
address, write address, and complete object size. Before layout, the linker
rejects a readable range which overlaps any configured allocator-managed
read/ordinary `MEMORY` window, or a writable range which overlaps any configured
allocator-managed write/ordinary window. This rule is directional for split
windows and applies equally to file-scope and block-scope bindings. Allocator-
owned storage must use a named `mem` region instead of an absolute binding.

Every file-scope absolute binding emits ordinary global ABI metadata as a
declaration. Its canonical storage mode contains both address terms, with
numeric spellings normalized to 16-bit hexadecimal form, followed by the normal
object type fingerprint. The linker therefore rejects separately compiled
translation units which disagree about either address or the object type even
though the binding has no allocated program symbol. `none` is preserved
independently for the read and write side.

The metadata records are carried as absolute `.o26` exports. The object format
already stores the export count in 16 bits; the assembler writer accepts that
full range so installed hardware-binding headers do not impose a 255-export
ceiling on translation units which also emit substantial function ABI metadata.


Authoritative memory-region metadata
------------------------------------

Every complete source-level `mem` declaration emits one reserved absolute
`.o26` export beginning with `__memdecl$V4$`, whether or not that translation
unit currently places an object in the region. The canonical record contains
the region name, read/ordinary start, write start, physical size, split-address
bit, read-only/read-write type, signed priority, data-only bit, optional topology
data-bank name, optional CPU-mapped output `$bank:NAME` owner, and declaration
source location. Numeric values use fixed-width hexadecimal fields. Empty
policy-only `mem name { };` declarations emit no allocator record. The linker
still accepts V1-V3 records for compatibility.

The linker merges byte-identical records after archive selection and rejects
conflicts with both original C26 locations. These records are authoritative for
allocator geometry and ordinary segment routing; legacy cfg MEMORY entries may
retain only migration-era operational properties. The metadata prefix is
reserved and never becomes a program global. Older use-site `__memmeta$V1$` and
`__memmeta$V2$` records remain accepted as consistency metadata during the cfg
transition.

Cartridge topology metadata
---------------------------

File-scope `cartridge` and `bank` declarations emit reserved absolute `.o26`
exports. They describe output packaging and physical mapping; they do not create
source-visible objects, storage, or executable instructions.

The current output-wide record begins with `__cartmeta$V2$` and canonically
records the presence mask, fill byte, optional offset/size pairs for the
trampoline, vector bridge, and vectors, plus the four raw cartridge-signature
bytes. The linker continues to accept legacy `__cartmeta$V1$` records, which
carry no signature. Each current bank record begins with `__bankmeta$V3$` and
records the bank name, physical image size, physical file index, mapped image
offset, synthetic link start, CPU-visible start, mapped size, optional selector
access address, startup bit, data-only bit, and optional one-byte mapper-defined
bank-call descriptor. Numeric values are normalized to
fixed-width hexadecimal fields, so byte-identical declarations from separate
translation units produce identical exports. The linker still accepts
`__bankmeta$V1$`, whose banks are always CPU-mapped.

`bank` and `mem` names occupy separate namespaces. A topology bank name has no
placement or ABI meaning for source declarations. The linker merges matching
records after archive selection and rejects conflicting declarations. These
metadata prefixes are reserved and are excluded from ordinary global-symbol and
ABI/type matching.

A command-line object containing complete cartridge, bank, or memory-region
metadata is configuration-bearing even when it defines no referenced ordinary
symbol. The linker retains such an object before normal lazy archive selection.
This makes a standalone C26 profile semantically equivalent to including the
same declarations, except that source placement modifiers must still be visible
inside the translation unit which uses them.

Variadic functions
------------------

Variadic functions and callable types are not part of the VCSC language.
The lexer rejects `...` with a direct diagnostic. There is no variadic call
frame, hidden metadata, `va_list`, `va_start`, `va_arg`, or `va_end` ABI.

Frame-phase storage metadata
----------------------------
The compiler emits reserved absolute exports beginning with
`__phaseuse$V1$M` for writable-object references seen while lowering proven VCS
lifecycle code. The two hexadecimal mask digits encode VSYNC=`01`, VBLANK=`02`,
visible draw=`04`, and overscan=`08`; `M00` means an unscoped use and permanently
disqualifies that object from phase sharing. Multiple scoped records for one
symbol are unioned, then conservatively expanded by the linker to the contiguous
frame interval between the first and last observed phase.

A phase-use set is not by itself permission to destroy a file-scope value between
frames. Storage is reusable only when it also carries the reserved
`__phaseworkspace$V1$symbol` eligibility record, which promises that prior-frame
contents are disposable outside the inferred interval. Fully phase-scoped
compiler scratch gets this record automatically because compiler temporaries are
written before use. Reusable renderer/application workspaces may emit the same
internal contract explicitly; ordinary source objects do not become eligible
merely because all observed accesses happen in one phase.

Lifecycle suffixes are accepted only for instantiation-owned `require` hooks; plain
functions do not gain lifetime semantics from names alone. Recognized inline
assembly contributes the same object-use metadata as high-level access. These
records affect storage placement only and are reserved implementation metadata,
not program globals.

Declaration-use contract metadata
---------------------------------
Contracted file-scope objects and functions emit reserved absolute-export
records beginning with `__contractmeta$V1$`.  Each record preserves the merged
`require`/`recommend` strength, logical assembler symbol, translation-unit owner,
declaration source file/line/column, instantiation identity, and a
canonical type or function-signature fingerprint. Non-instantiated declarations use
`none`; declarations produced by `instantiate ... as instance` use the stable
`instance@invocation-file:line:column` identity.  True inline functions emit these records even though they have no
ordinary callable object symbol.  The assembler retains the records in `.o26`
exports; the linker treats the prefix as metadata rather than a program global.

Direct source-level calls, including true-inline expansions that leave no `JSR`
or relocation, emit reserved `__usemeta$V1$call$...` records. Contracted file-scope object reads, writes, address-taking operations,
and `ref` arguments emit corresponding
`read`, `write`, `address`, and `ref` records. Each semantic-use record preserves
the referenced logical symbol, referencing translation-unit owner, containing
function, source file/line/column, and instantiation identity. The records
are emitted before peephole optimization and survive even when code generation leaves no ordinary
relocation. After archive selection and ordinary relocation resolution, the
linker computes reachability from `main` and runtime initializer roots using the
same compiler and hidden-assembly call-graph edges used for activation planning.
A contract is satisfied only by a reachable semantic use from a different
translation-unit/instantiation owner. Unused `require` records are fatal;
unused `recommend` records produce warnings. Object diagnostics carry the
source-level declared type spelling (for example `uint8_t` or a typedef name);
the separate canonical ABI fingerprint remains unchanged for machine checking.
Metadata in unselected archive members remains silent.
