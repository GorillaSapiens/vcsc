Project goal
------------
Reduce the existing general-purpose N 6502 toolchain to a small C-like language
and toolchain aimed specifically at the Atari 2600/VCS. The current source is a
starting point, not a compatibility contract. Unsupported features will be
removed in controlled slices after their replacements work end to end.

Agreed final-language decisions
-------------------------------
These are settled unless the user explicitly changes them:

* Target: Atari 2600/VCS, using the 6507 CPU.
* All multibyte values are little-endian.
* The only user-visible basic integer types will be:

      int8_t
      uint8_t
      int16_t
      uint16_t

* No float or double.
* No int32_t, uint32_t, or wider integers.
* void remains a special non-value type.
* Pointers remain special 16-bit little-endian values.
* Functions use normal source-level parameters and lexical scope.
* There will be no software argument/local stack in the final ABI.
* Parameters and automatic locals will use statically allocated storage.
* Static activation records intentionally make functions non-reentrant.
* Direct recursion, mutual recursion, callback re-entry, and any other way to
  activate the same parameterized function twice must be rejected.
* JSR/RTS still use the 6502 hardware stack for return addresses.
* Function return values use A:X:

      8-bit result:  A contains the value; X is unspecified
      16-bit result: A contains the low byte; X contains the high byte
      pointer result: same 16-bit A:X convention

* No legal function return value may be larger than two bytes.
* Struct, union, and array returns are therefore not part of the final language,
  even when an aggregate happens to occupy one or two bytes. Use an explicit
  result pointer for aggregate output.

Current implementation state
----------------------------
Two vertical slices are complete:

1. One- and two-byte little-endian scalar and pointer returns use A:X.
2. Every fixed parameter of a directly named function is symbol-backed by
   default rather than stack-backed.

This is still transitional. Automatic locals, expression temporaries, caller
argument-evaluation scratch, variadic blobs, and some runtime helpers still use
_nl_sp/_nl_fp and _pushN/_popN.

The compiler still contains a legacy caller-owned return-slot path for returns
larger than two bytes, aggregates, arrays, and big-endian values. That path is
not approved language behavior; it remains only so those old features can be
removed in a controlled later slice. The newly settled two-byte maximum is not
yet enforced everywhere.

A:X return implementation details
---------------------------------
Relevant helpers:

    compiler/compile_function.c
        return_type_uses_ax()
        function_uses_ax_return()

A return type currently uses A:X when it is:

* one or two bytes;
* not an aggregate or array;
* little-endian when two bytes.

Inside such a function, the reserved source-level return object $$ is a hidden
callee-local scratch object. `return expr;` stores the converted expression
there. At the common epilogue, after _popN removes current locals, the compiler
loads:

    high byte -> X, when size is two
    low byte  -> A

and executes RTS.

The caller saves fp on the hardware stack. After JSR, A is temporarily moved
through Y while fp is restored with PLA; X is left untouched. A is then restored
from Y.

The existing expression engine still expects a memory slot for most values.
Therefore a caller that consumes an A:X result may reserve private scratch in
its own software-stack frame and copy A:X into it before running the old
conversion/copy machinery. This scratch is not a callee return slot and is not
part of the function ABI.

Important frame-layout rule discovered during the A:X slice:

* caller-private result scratch must be below any stack-resident call data,
  occupying the same low-address position formerly used by the return slot;
* stack-resident call data must remain at the high-address end of a pushed call
  frame because old callees locate it backward from fp.

Direct fixed-parameter implementation
-------------------------------------
Every non-void, non-ellipsis parameter of a directly named function now has a
callee-owned symbol.

* Ordinary parameters use BSS-backed absolute symbols.
* A parameter assigned to a zero-page memory region uses a zero-page symbol.
* The old `static` parameter spelling remains accepted but is now redundant.
* Other named memory-region modifiers continue to use the existing symbol
  allocation machinery.

At a direct call site the compiler:

1. Determines the largest fixed parameter size.
2. Reserves one reusable caller-owned software-stack scratch area of that size,
   if necessary.
3. Evaluates arguments left-to-right.
4. Converts each argument in the scratch area.
5. Copies it into the corresponding callee-owned symbol.
6. Executes JSR.
7. Releases the scratch after consuming the result.

No fixed direct-call parameter bytes are placed on the software argument stack.
Automatic locals and expression scratch are unchanged in this slice.

Re-entry and call-graph rules
-----------------------------
Every parameterized direct function now counts as having static parameters.
Existing compiler and linker call-graph checks therefore reject:

* direct recursion;
* mutual recursion inside one translation unit;
* cycles completed only after separate objects are linked.

The diagnostics still say "symbol-backed parameters", which accurately
describes the storage model even though symbol backing is now the default.

Function pointers during the transition
---------------------------------------
A plain function pointer contains only a code address and cannot identify the
callee-owned symbols that receive parameters. Therefore:

* taking the address of a parameterized direct function is a compile-time error;
* parameterized indirect calls are no longer accepted silently;
* zero-parameter function pointers still work through the legacy indirect-call
  path and have a simulator-level test;
* function pointers are not currently promised as part of the final minimal VCS
  subset.

This restriction was intentionally added rather than allowing wrong code.
`compile_init.c` returns "not a constant" during speculative initializer
checking; the real expression lowering path emits the precise user diagnostic.

Hand-written runtime ABI note
-----------------------------
The previous A:X slice changed libraries/nlib/asm/sbrk.asm so _sbrk returns its
pointer in A:X. Its argument handling still belongs to the old runtime/software-
stack world. Heap/sbrk support is not part of the intended final VCS subset and
was not migrated to symbol-backed parameters in this slice.

Atari 2600 hardware constraints
-------------------------------
* The VCS has 128 physical bytes of RIOT RAM at $80-$FF, mirrored elsewhere,
  including $180-$1FF.
* The 6502 stack pointer addresses page 1, but on the VCS those stack addresses
  alias the same physical 128 bytes used by ordinary variables.
* Static variables and JSR/RTS/PHA/PHP stack use must therefore share one
  physical allocation.
* Each outstanding JSR consumes two stack bytes until RTS. PHA/PHP consume
  additional bytes.
* The 6507 has no usable IRQ or NMI inputs, so asynchronous interrupt re-entry
  is not a normal concern. Program-controlled re-entry still is.
* Visible scanline kernels are cycle-critical. JSR+RTS alone costs 12 cycles,
  so a future kernel policy may require inlining or prohibit calls.

Known VCS configuration defect not yet fixed
--------------------------------------------
File:

    libraries/vcs/vcs_4k.cfg

It currently models these as independent memory:

    RAM:      $0080-$00FF
    CPUSTACK: $0180-$01FF

They are mirrors of the same physical RIOT RAM. The configuration double-counts
RAM and can hide collisions. The final configuration must model one physical
pool and reserve its upper portion for worst-case hardware-stack use.

Open implementation questions
-----------------------------
These are not yet settled:

* Whether static frames will later be overlaid using whole-program liveness and
  call-graph analysis. Start with distinct storage.
* Exact fixed or calculated hardware-stack reserve in RIOT RAM.
* Expression scratch allocation strategy after the software stack is removed.
* Whether separate compilation remains throughout simplification or whole-
  program compilation is temporarily required.
* Kernel-function syntax and cycle checking/inlining policy.
* Final fate of zero-argument function pointers. Parameterized function pointers
  are already incompatible with the direct static-parameter ABI.
