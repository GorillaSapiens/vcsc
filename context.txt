Project goal
------------
Reduce the existing general-purpose n 6502 toolchain to a small C-like language
and toolchain aimed specifically at the Atari 2600/VCS. The current source is a
starting point, not a compatibility contract. Unsupported features will be
removed after the replacement ABI works end to end.

Agreed final-language decisions
-------------------------------
These are settled unless the user explicitly changes them:

* Target: Atari 2600/VCS, using the 6507 CPU.
* All multibyte values are little-endian.
* The only user-visible basic integer types will be:

      int8_t
      uint8_t
      int16_t
      uint16_t

* No float or double.
* No int32_t, uint32_t, or wider integers.
* void remains a special non-value type.
* Pointers remain special 16-bit little-endian values.
* Functions use normal source-level parameters and lexical scope.
* There will be no software argument/local stack in the final ABI.
* Parameters and automatic locals will use statically allocated storage.
* Static activation records intentionally make functions non-reentrant.
* Direct recursion, mutual recursion, callback re-entry, and any other way to
  activate the same function twice must be rejected.
* JSR/RTS still use the 6502 hardware stack for return addresses.
* Function return values use A:X:

      8-bit result:  A contains the value; X is unspecified
      16-bit result: A contains the low byte; X contains the high byte
      pointer result: same 16-bit A:X convention

Current implementation state
----------------------------
The first vertical slice is complete: one- and two-byte little-endian scalar
and pointer returns now use A:X.

This is deliberately transitional. Parameters, automatic locals, and
expression temporaries still use the old _nl_sp/_nl_fp software stack. Larger,
aggregate, array, and big-endian return types temporarily retain the old
caller-owned memory return slot so the still-present legacy feature tests do
not silently miscompile. Those types/features are not part of the intended
final language and will be removed later.

Current A:X return implementation details
-----------------------------------------
Relevant helpers:

    compiler/compile_function.c
        return_type_uses_ax()
        function_uses_ax_return()

A return type currently uses A:X when it is:

* one or two bytes;
* not an aggregate or array;
* little-endian when two bytes.

Inside such a function, the reserved source-level return object $$ is a hidden
callee-local scratch object. `return expr;` stores the converted expression
there. At the common epilogue, after _popN removes current locals, the compiler
loads:

    high byte -> X, when size is two
    low byte  -> A

and executes RTS.

The caller saves fp on the hardware stack. After JSR, A is temporarily moved
through Y while fp is restored with PLA; X is left untouched. A is then restored
from Y.

The existing expression engine still expects a memory slot for most values.
Therefore a caller that consumes an A:X result currently reserves a private
scratch area in its own software-stack frame and copies A:X into it before
running the old conversion/copy machinery. This scratch is not a callee return
slot and is not part of the function ABI.

Important frame-layout rule discovered during implementation:

* caller-private result scratch must be below the arguments, occupying the same
  low-address position formerly used by the return slot;
* arguments must remain at the high-address end of the pushed call frame,
  because the callee locates them backward from its fp, which is set to sp.

Placing result scratch above the arguments made the callee read scratch bytes
as parameters. This bug was found by the broad end-to-end suite and fixed.

ABI metadata now emits return mode `return_ax` for eligible returns and retains
`return_value` for the temporary legacy path.

Hand-written runtime ABI updates
--------------------------------
The hand-written libraries/nlib/asm/sbrk.asm routine formerly wrote its pointer
result into the old caller-owned return slot. It now returns the pointer in A:X
(A low, X high). Its argument remains at fp-2 under the temporary stack-based
parameter ABI.

Atari 2600 hardware constraints
-------------------------------
* The VCS has 128 physical bytes of RIOT RAM at $80-$FF, mirrored elsewhere,
  including $180-$1FF.
* The 6502 stack pointer addresses page 1, but on the VCS those stack addresses
  alias the same physical 128 bytes used by ordinary variables.
* Static variables and JSR/RTS/PHA/PHP stack use must therefore share one
  physical allocation.
* Each outstanding JSR consumes two stack bytes until RTS. PHA/PHP consume
  additional bytes.
* The 6507 has no usable IRQ or NMI inputs, so asynchronous interrupt re-entry
  is not a normal concern. Program-controlled re-entry still is.
* Visible scanline kernels are cycle-critical. JSR+RTS alone costs 12 cycles,
  so a future kernel policy may require inlining or prohibit calls.

Known VCS configuration defect not yet fixed
--------------------------------------------
File:

    libraries/vcs/vcs_4k.cfg

It currently models these as independent memory:

    RAM:      $0080-$00FF
    CPUSTACK: $0180-$01FF

They are mirrors of the same physical RIOT RAM. The configuration double-counts
RAM and can hide collisions. The final configuration must model one physical
pool and reserve its upper portion for worst-case hardware-stack use.

placed in a named memory region. Existing compiler and linker machinery also
checks call cycles involving such parameters.

Old software-stack machinery still present
------------------------------------------
The compiler still uses _nl_sp/_nl_fp and _pushN/_popN for:

* stack-backed function arguments;
* automatic locals;
* expression temporaries and spill slots;
* aggregate copies;
* variadic machinery;
* some hand-written runtime helpers.

    export LD_LIBRARY_PATH=/mnt/data/vcsc_toolroot/usr/lib/x86_64-linux-gnu:${LD_LIBRARY_PATH:-}

* Expression scratch allocation strategy after the software stack is removed.
* Whether separate compilation remains throughout simplification or whole-
  program compilation is temporarily required.
* Kernel-function syntax and cycle checking/inlining policy.
* Final fate of aggregate types and returns; current legacy fallback is only a
  bridge, not approval to retain them.
