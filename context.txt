Project goal
------------
Reduce the existing general-purpose N 6502 toolchain to a small C-like language
and toolchain aimed specifically at the Atari 2600/VCS. Compatibility with the
old general-purpose language is not a goal. Features are being removed in
controlled, testable vertical slices.

Settled final-language decisions
--------------------------------
* Target: Atari 2600/VCS using the 6507 CPU.
* All multibyte values are little-endian.
* The only user-visible basic integer types will be:

      int8_t
      uint8_t
      int16_t
      uint16_t

* No float or double.
* No int32_t, uint32_t, or wider integers.
* void remains a special non-value type.
* Pointers are special 16-bit little-endian values.
* Functions retain normal source-level parameters and lexical scope.
* The final ABI has no software argument/local stack.
* Parameters and automatic locals use statically allocated storage.
* A function has one activation record and is intentionally non-reentrant.
* Direct recursion, mutual recursion, callback re-entry, and any other path that
  activates the same function twice must be rejected.
* JSR/RTS still use the 6502 hardware stack for return addresses.
* Function returns:

      void:            no value
      8-bit integer:   A; X unspecified
      16-bit integer:  A low byte, X high byte
      pointer:         A low byte, X high byte

* No function may return a value larger than two bytes.
* Struct, union, and array returns are forbidden even when the aggregate is one
  or two bytes. Use an explicit result pointer.

Completed vertical slices
-------------------------
1. One- and two-byte little-endian integer and pointer returns use A:X.
2. Every fixed parameter of a directly named function is callee-owned symbol
   storage rather than software-stack storage.
3. Function return types are now restricted to void, supported 8/16-bit
   little-endian integers, and 16-bit pointers. The old caller-owned return-slot
   ABI has been deleted.
4. The VCS linker now exposes only $80-$DF as allocatable RIOT RAM and reserves
   $E0-$FF for the 6502 hardware stack. The mirrored $0180-$01FF window is no
   longer modeled as separate physical memory.
5. Every named automatic local and the hidden `$$` return object now has
   function-qualified fixed-address storage. Automatic initializers still run
   whenever control reaches the declaration on each invocation.
6. Every remaining compiler `_pushN` allocation site has been inventoried and
   classified in top-level software_stack_inventory.txt. A regression test
   detects unrecorded additions, removals, or count changes.
7. Ordinary direct calls now evaluate arguments and consume A:X through fixed
   compiler-generated call-site scratch rather than allocating a software-stack
   call frame.
8. Variadic functions and callable types have been removed. The lexer rejects
   `...`; variadic call lowering, hidden metadata, `stdarg.n`, `sprintf.n`, and
   the legacy direct-call software-stack fallback are gone.
9. Function pointers and indirect calls have been removed. Function-pointer
   declarators and function names used as values are rejected; `_callptr0` and
   the final software-stack call frame in `compile_call.c` are gone.
10. General truth-value evaluation and discarded non-call expression results
    now use fixed per-site BSS scratch instead of `_pushN`/`_popN`.
11. Simple assignments into fixed symbols now evaluate and convert through
    fixed per-site `__n65_assigntmp_N` BSS scratch instead of
    `_pushN`/`_popN`.
12. Two-operand comparisons and the main built-in binary operator families now
    use fixed per-site BSS scratch instead of `_pushN`/`_popN`: pointer
    subtraction, scalar/pointer addition and subtraction, shifts, bitwise
    operations, multiplication, division, and remainder.
13. Cast conversion, function-local/global absolute-reference conversion, and
    built-in increment/decrement now use fixed per-site BSS scratch. Fixed
    symbol-to-lvalue helpers cover ordinary, indirect, and bit-field lvalues.
14. Built-in compound assignment, switch-expression comparison, simple
    indirect/absolute/bit-field assignment, runtime local and return-object
    initialization, and local absolute-reference initialization now use fixed
    BSS scratch. `compile_stmt.c` no longer emits `_pushN` or `_popN`.
15. Pointer/index lvalue evaluation, bit-field helper pointer preservation,
    braced assignments, and runtime global initializers now use fixed BSS
    scratch. `compile_lvalue.c` and `compile_init.c` no longer emit `_pushN` or
    `_popN`.
16. Operator overloading, `$exactops`, weak built-in operator dispatch, the
    weak-operator generator/runtime members, and generated exact-operator float
    fixtures have been removed. Compiler source emits no `_pushN` or `_popN`.
    Ordinary named-function overloading remains supported.
17. Floating-point support has been removed from the language, compiler, driver,
    build, runtime, machine definitions, and positive test suite. Floating-point
    literals and `$float`/`$float:*` type flags remain only as direct rejection
    paths.
18. Big-endian and mixed-endian target support has been removed. All target
    integers, pointers, constants, initializers, conversions, comparisons, and
    runtime helpers are little-endian. `$endian:big`, `($big)`, and `($little)`
    remain only as direct rejection paths.
19. Target integer widths are restricted to exactly one or two bytes. Untyped
    integer literals must fit in 16 bits. Positive 24/32/64-bit compiler,
    runtime, library, and test support has been removed. The machine files now
    define int8_t, uint8_t, int16_t, and uint16_t; legacy internal names remain
    temporarily until the compiler is switched to the canonical four names.

Current return ABI
------------------
Relevant code:

    compiler/compile_function.c
        return_type_is_void()
        return_type_is_supported()
        return_type_uses_ax()
        function_uses_ax_return()
        validate_function_return_type()

    compiler/compile_call.c
        direct-call argument/result handling

    compiler/abi_meta.c
        return_void / return_ax metadata

Every function declaration and definition is validated. The compiler rejects:

* aggregate and array returns;
* integers larger than two bytes;
* any other noninteger, nonpointer value return.

Pointers to aggregate or otherwise unsupported pointee types are legal because
the returned value is still a 16-bit pointer.

There is no compiler `return_value` metadata mode and no caller-owned return
storage. An ordinary direct caller that must feed A:X into the still-memory-
based expression engine copies it to fixed compiler-generated call-site scratch.
That scratch is not part of the callee ABI. Indirect calls are unsupported.

Inside a non-void function, `$$` is the source-level return object. It is a
hidden callee-owned fixed-address symbol. The epilogue loads it into A:X.

Current direct-parameter ABI
----------------------------
Every fixed parameter of a directly named function has a callee-owned symbol.
At each ordinary direct call, the compiler emits one private BSS
scratch symbol named `__n65_calltmp_N`. The caller:

1. saves the current `fp` on the 6502 hardware stack;
2. temporarily points `fp` at the fixed call-site scratch;
3. evaluates each argument left-to-right and copies the converted value to the
   corresponding callee parameter symbol;
4. restores `fp` after each argument;
5. executes JSR while preserving the returned A:X across `fp` restoration;
6. copies A:X through the same fixed scratch only when the enclosing expression
   needs a memory-backed converted value.

The scratch size is the maximum temporary depth observed while compiling any
argument at that call site, or the consumed return width when larger. Nested
calls are safe because scratch is allocated per call site rather than once per
function. Scratch is not overlaid yet, so this intentionally trades RAM for a
clean stack-free direct-call path. Parameter symbols may be ordinary absolute
storage or zero-page storage.

Call-graph and call-target rules
--------------------------------
No function body may be active twice because its parameters, automatic locals,
and return object share one fixed activation record. Compiler and linker
call-graph checks reject same-unit and cross-object cycles, including cycles
through zero-parameter functions.

Every call target must be a directly named function. Function-pointer
declarators are rejected, as are bare function names or `&function` used as
values. This keeps every call edge visible to cycle analysis and eliminates the
indirect-call ABI and `_callptr0` runtime trampoline.

Atari 2600 hardware constraints
-------------------------------
* The VCS has 128 physical bytes of RIOT RAM at $80-$FF.
* $180-$1FF is a mirror of the same physical RAM, not separate stack RAM.
* Static storage and JSR/RTS/PHA/PHP stack use therefore compete for one pool.
* Every outstanding JSR consumes two physical RAM bytes until RTS.
* The 6507 has no usable IRQ or NMI inputs, so asynchronous interrupt re-entry
  is not the normal problem; program-controlled re-entry still is.
* Visible kernels have only 76 CPU cycles per scanline. Calls in kernels will
  eventually require an explicit policy or automatic inlining.

Current VCS RAM model
---------------------
File:

    libraries/vcs/vcs_4k.cfg

The linker now models one physical RIOT RAM pool rather than independent RAM
and CPUSTACK regions. The current conservative partition is:

    $80-$DF   96 bytes available to ZEROPAGE, DATA, BSS, and the
              transitional upward-growing N software stack
    $E0-$FF   32 bytes reserved for the downward-growing 6502 hardware stack

The reserved bytes are mirrored at $01E0-$01FF, where JSR/RTS/PHA/PHP actually
address them through the 6502 stack pointer. They are intentionally absent from
the linker MEMORY list, so ordinary storage cannot be allocated there.

The linker-generated `__stack_top` for the N software stack is therefore $00DF.
This is a fixed provisional reserve; exact call-depth-based sizing remains a
later optimization.

Tests verify both the map and enforcement:

* a VCS link map must show RAM start $0080, size $0060, and stack top $00DF;
* a BSS allocation that would cross into the reserved hardware-stack bytes must
  fail at link time;
* a configuration guard rejects any reintroduced CPUSTACK memory region and
  requires ARGSTACK to share RAM.

Test policy
-----------
When a feature is removed:

1. delete positive tests whose purpose is to prove that feature works;
2. keep or add negative tests proving the compiler rejects it cleanly;
3. rewrite tests whose real subject remains useful to use legal types or
   out-parameters;
4. list every intentionally deleted path in remove.txt.

For the big/mixed-endian purge:

* target multibyte values are unconditionally little-endian;
* the compiler retains only direct rejection paths for `$endian:big`, `($big)`,
  and `($little)`;
* all big-endian and mixed-endian compiler branches and 37 big-endian nlib
  procedures were removed;
* 24 obsolete positive endian tests were intentionally removed and three direct
  rejection tests were added;
* all removed paths are in top-level remove.txt.

For the wide-integer purge:

* target integer declarations must be exactly one or two bytes;
* target pointers must be two bytes;
* untyped integer literals larger than 16 bits are rejected;
* positive 24/32/64-bit arithmetic, promotion, extension, shift, helper, and
  return tests were removed or rewritten to legal widths;
* PetiteFFS was removed because its public model requires a 32-bit DWORD;
* dead add/subtract/increment runtime assembly files were removed;
* host-side `long long`, `uint32_t`, and `uint64_t` used inside the compiler,
  assembler, and MD5 implementation are not target-language types and remain.

Open implementation questions
-----------------------------
* Whether static frames will later be overlaid using whole-program call/liveness
  analysis. Start with distinct storage.
* Whether the provisional 32-byte hardware-stack reserve should eventually be
  replaced by exact link-time call-depth sizing.
* Expression scratch allocation after the software stack is removed.
* Existing defect: in some simple assignments such as `old := value++`, the
  assignment-expression fast path can copy the lvalue without applying the
  increment. Standalone `value++`/`--value` works and is covered here; fix this
  independently rather than conflating it with scratch removal.
* Whether separate compilation remains throughout simplification.
* Kernel-function syntax and cycle checking/inlining policy.
