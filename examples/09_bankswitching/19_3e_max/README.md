# Maximum-size 3E diagnostic

This is the Stella-compatible stress version of the Tigervision 3E PASS/FAIL
diagnostic. It combines the maximum 3E ROM shape with Stella's complete 3E RAM
capacity:

- 256 physical 2K ROM banks = 512K ROM. Physical banks 0 through 254 are
  selectable at `$1000-$17FF`; bank 255 is fixed/startup at `$1800-$1FFF`.
- 32 physical 1K RAM banks = 32K RAM, matching Stella's `3E` implementation.
  RAM reads use `$1000-$13FF`; writes use the split `$1400-$17FF` alias.

The ROM self-test executes every ordered source/destination pair among the 255
lower banks: 255 x 255 = 65,025 calls. Same-bank pairs use direct JSR. Cross-bank
pairs use VCSC's real generic 3E descriptor trampoline through a seven-byte
inline-call stub copied into RIOT RAM. Every lower bank also calls the fixed bank
once, and the fixed bank calls every lower bank once, for 65,535 counted target
calls total. Destinations validate physical-bank identity, callers verify source
restoration, and the diagnostic checks 6507 hardware-stack balance.

## 32K RAM torture

After the ROM matrix completes, fixed-bank code fills every byte in RAM banks
0 through 31 and then reads every byte back. The data stream is generated by a
maximal 16-bit Galois LFSR using
`x^16 + x^14 + x^13 + x^11 + 1`, right-shift tap mask `$B400`, with seed
`$ACE1`. `make_torture.pl` independently walks the recurrence and refuses to
generate the diagnostic unless its period is exactly 65,535 states.

The LFSR is **not restarted at RAM-bank boundaries**. One continuous 32,768-byte
stream is written across all 32 banks, then the LFSR is reset to `$ACE1` and the
same walk is used for readback verification. That matters: equal offsets in
different RAM banks receive different expected data, so a mirrored, aliased, or
incorrectly selected RAM bank cannot pass merely because every bank was filled
with the same pattern.

This torture intentionally uses the mapper's raw `$3E` selector and split RAM
aliases from fixed ROM. Compiler-managed `$swapram` semantics are covered by the
separate 3E acceptance/restoration/helper regressions; this diagnostic is the
hardware-capacity oracle and must begin rendering before a huge automatic zero
initializer could run.

## Display and progress

While either the ROM or RAM torture is running, the cartridge keeps a stable
262-scanline NTSC frame with the `$84` blue background from
`01_basic/01_blank_screen`. The big status line reads `wait ` plus a spinner
cycling `/`, `-`, `\`, `|` every 15 frames (one quarter second). Work is sliced
only into VBLANK and overscan. ROM batches are 10/8 operations; RAM batches are
20/12 bytes, the largest current verified budgets that keep every measured frame
at 262 scanlines.

After all tests complete, the display changes to the standard big/wide `pass` or
`FAIL` line with exactly `3E max` beneath it. The big WAIT and PASS/FAIL glyphs
are embedded in lower ROM banks 253 and 254. The small `3E max` glyphs live in
bank 251; one deliberate blank scanline switches to that bank between visible
components while preserving a 192-line visible region. One-time torture setup
lives in bank 252 to leave enough room in the fixed 2K startup bank for the RAM
verifier.

In Stella, force the cartridge type if necessary:

```sh
stella -bs 3E 3e_max_diagnostic.bin
```

The committed `3e_max_torture_*.s26` files are generated by `make_torture.pl`, so
normal builds do not require Perl. `make torture` regenerates the torture
assembly; `make fonts` regenerates the committed display-font subsets and then
the embedded font payloads.
